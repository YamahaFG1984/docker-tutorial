第 19 章

CI/CD 流水线

到目前为止，镜像都是在你自己电脑上 docker build、docker push 的。在团队里，这件事应该交给机器： 每次推送代码，自动构建镜像、跑测试、扫描漏洞、打上正确的标签、推送到仓库并签名。 本章用 GitHub Actions 一步步搭出这条流水线，把第 6、8、16 章学到的知识串起来。

本章目标

  • 理解一条镜像流水线由哪些环节组成，以及为什么要按这个顺序
  • 用 Docker 官方的 GitHub Actions 构建并推送镜像到 GHCR 或 Docker Hub
  • 用 metadata-action 根据分支、PR、版本号自动生成标签
  • 用 GitHub Actions 缓存让构建提速
  • 在流水线里跑测试、做漏洞扫描、构建多架构镜像
  • 生成 SBOM 和来源证明，并用 Cosign 无密钥签名

一条镜像流水线长什么样

我们用 GitHub Actions 来实现，因为它和代码仓库集成最紧密，Docker 官方也维护了一整套 action。 思路同样适用于 GitLab CI、Jenkins 等其他平台 —— 本质上都是在 CI 机器上执行第 8 章的 docker buildx build。

Docker 官方 action 一览

Action作用对应的本地命令
docker/setup-buildx-action@v4创建 Buildx 构建器（docker-container 驱动）docker buildx create --use
docker/setup-qemu-action@v4安装 QEMU，用于构建其他架构的镜像—
docker/login-action@v4登录镜像仓库docker login
docker/metadata-action@v6根据 Git 事件生成镜像标签和 OCI 标签手动 docker tag
docker/build-push-action@v7构建（并可选推送）镜像docker buildx build --push
ⓘ 版本号

上表是 2026 年 9 月的最新主版本。这些 action 升级很频繁，写工作流时去各自的 GitHub 页面确认最新版本即可，用法基本不变。

第一个工作流：构建并推送到 GHCR

GitHub Container Registry（ghcr.io）是最省事的选择：不用额外注册账号，工作流自带的 GITHUB_TOKEN 就能推送，镜像会显示在仓库的 Packages 里。 在仓库里新建 .github/workflows/docker.yml： 

name: docker

on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write                # 允许 GITHUB_TOKEN 推送到 ghcr.io

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: docker/setup-buildx-action@v4

      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:latest

推送到 main 之后，在仓库的 Actions 页面能看到运行过程；成功后镜像就能拉取了：

$ docker pull ghcr.io/你的用户名/你的仓库:latest
💡 推送到 Docker Hub

在 Docker Hub 的 Account settings → Personal access tokens 创建一个令牌，保存为仓库的 Secret DOCKERHUB_TOKEN，用户名保存为变量 DOCKERHUB_USERNAME。 登录步骤改成 username: ${{ vars.DOCKERHUB_USERNAME }}、password: ${{ secrets.DOCKERHUB_TOKEN }}，去掉 registry，标签写成 用户名/仓库名:标签。 永远用访问令牌，不要用账号密码。

ⓘ 注意 checkout 这一步

build-push-action 默认使用 Git 上下文（直接从仓库的提交构建），这种情况下之前步骤对文件的修改都会被忽略。 我们先 actions/checkout 再指定 context: .，用的是工作目录上下文，.dockerignore 和前面步骤生成的文件都会生效，行为和你本地构建一致。

自动生成标签

只打 latest 是远远不够的（第 6 章讲过它的问题）。好的做法是让每个镜像都能追溯到来源： 来自哪个分支、哪个 PR、哪个版本号、哪个提交。docker/metadata-action 会根据触发事件自动算出这些标签： 

      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha

      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

它同时生成符合 OCI 规范的镜像标签（labels），比如 org.opencontainers.image.source（源码仓库）、revision（提交 SHA）、created（构建时间），用 docker inspect 就能看到镜像从哪里来。

构建缓存：让 CI 快起来

CI 机器每次都是全新的，第 8 章讲的本地构建缓存在这里根本不存在 —— 每次都从零下载依赖，一个 Node 项目可能要构建好几分钟。 解决办法是把 BuildKit 的缓存导出到外部，下次再导入： 

      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
缓存后端写法适合
GitHub Actions 缓存type=ghaGitHub Actions，最简单，有容量上限（超出会淘汰旧缓存）
镜像仓库type=registry,ref=ghcr.io/x/app:buildcache任何 CI；缓存较大时；多个仓库或流水线共享缓存
Docker Build Cloud用 cloud 驱动的构建器团队共享缓存 + 原生多架构，付费
⚠ 只读权限下写缓存会失败

来自 fork 的 PR 等只有只读权限的运行，写入 gha 缓存可能报 failed to reserve cache。官方建议：这类运行只保留 cache-from，由 main 分支的 push 负责写缓存；或者给 cache-to 加上 ignore-error=true。

PR 构建：验证但不推送

PR 阶段的目的是“这次改动能不能构建、测试能不能过”，不应该往仓库推镜像（尤其是来自 fork 的 PR 拿不到写权限）。一个 push 条件就能搞定：

on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:

# ...

      - uses: docker/login-action@v4
        if: github.event_name != 'pull_request'     # PR 不登录
        # ...

      - uses: docker/build-push-action@v7
        with:
          push: ${{ github.event_name != 'pull_request' }}   # PR 只构建不推送
          # ...

在流水线里跑测试

第 18 章的 Dockerfile 有 dev 和 prod 两个目标。可以再加一个 test 目标，让测试在和生产相同的基础镜像里运行：

FROM dev AS test
RUN npm test          # 测试失败 → 这一步失败 → 整个构建失败

流水线里先构建 test 目标，通过了再构建并推送 prod 目标。两次构建共享同一个缓存，重复的层不会重新构建：

      - name: 运行测试
        uses: docker/build-push-action@v7
        with:
          context: .
          target: test
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: 构建并推送生产镜像
        uses: docker/build-push-action@v7
        with:
          context: .
          target: prod
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
💡 需要数据库的集成测试

集成测试要连真实的 Postgres？直接复用第 18 章的 Compose 文件： docker compose run --rm --build api npm run test:integration，Compose 会先启动 db、等待健康检查通过，再运行测试。 跑完用 docker compose down -v 清理。GitHub 托管的 Ubuntu 运行器已经预装了 Docker 和 Compose。

漏洞扫描：把关质量门

第 16 章讲了漏洞扫描，在 CI 里它变成了一道质量门：发现严重漏洞就让构建失败，有问题的镜像根本到不了仓库。

      - name: 构建镜像并载入本地（先不推送）
        uses: docker/build-push-action@v7
        with:
          context: .
          target: prod
          load: true
          tags: app:scan
          cache-from: type=gha

      - name: 扫描漏洞
        uses: aquasecurity/trivy-action@v0.36.0
        with:
          image-ref: app:scan
          severity: CRITICAL,HIGH
          ignore-unfixed: true         # 暂时没有修复版本的漏洞先不阻断
          exit-code: "1"               # 发现漏洞时让这一步失败

也可以用 Docker 官方的 docker/scout-action，它能直接和上一个版本或基础镜像做对比，把结果评论到 PR 里（需要 Docker 账号登录）。 无论用哪个工具，都建议配合 Dependabot / Renovate 自动提交基础镜像和依赖的升级 PR —— 大多数漏洞只要升级基础镜像就能修复。

多架构构建

团队里有人用 M 系列 Mac，服务器是 x86，还有 ARM 云主机？在 CI 里一次性构建多架构镜像（原理见第 6 章 manifest list、第 8 章多架构构建）：

      - uses: docker/setup-qemu-action@v4
      - uses: docker/setup-buildx-action@v4

      - uses: docker/build-push-action@v7
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
💡 QEMU 太慢怎么办

用 QEMU 模拟 ARM 构建，编译型项目可能慢好几倍。GitHub 提供了原生 ARM 运行器（runs-on: ubuntu-24.04-arm）， 可以用矩阵在 amd64 和 arm64 运行器上分别原生构建，再合并成一个 manifest list（官方文档 “Distribute build across multiple runners” 有完整示例）；或者使用 Docker Build Cloud。

SBOM、来源证明与签名

证明（attestations）

第 16 章提到，BuildKit 可以在构建时生成两类证明并随镜像一起推送：SBOM（镜像里有哪些软件）和来源证明 provenance（镜像是在哪里、用什么源码、怎样构建的）。 build-push-action 默认就会添加来源证明（公开仓库为 mode=max，私有仓库为 mode=min），SBOM 需要显式打开： 

      - uses: docker/build-push-action@v7
        with:
          # ...
          sbom: true
          provenance: mode=max

# 查看推送后镜像附带的 SBOM
$ docker buildx imagetools inspect ghcr.io/you/app:main --format '{{json .SBOM}}'
⚠ 不要把机密当作构建参数

mode=max 的来源证明会记录构建参数。如果你用 build-args 传了令牌，它会被写进公开的证明里！构建期机密一律用 secrets: 输入（对应 Dockerfile 中的 RUN --mount=type=secret）。

用 Cosign 无密钥签名

在 CI 里签名最推荐无密钥（keyless）方式：Cosign 用 GitHub Actions 的 OIDC 身份向 Sigstore 申请一张短期证书完成签名，签名记录在公开的透明日志里。 你不需要生成、保管、轮换任何私钥，验证方只需要检查“这个镜像是不是由某仓库的某个工作流签的”。 

permissions:
  contents: read
  packages: write
  id-token: write                          # 允许获取 OIDC 身份令牌，签名需要

# ...
      - id: build
        uses: docker/build-push-action@v7
        with:
          # ...
          push: true

      - uses: sigstore/cosign-installer@v4

      - name: 签名镜像
        if: github.event_name != 'pull_request'
        run: cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}

注意签名的对象是摘要（steps.build.outputs.digest），而不是标签 —— 标签可以被移动，摘要不会（第 6 章）。验证时指定签名者身份：

$ cosign verify ghcr.io/you/app:main \
    --certificate-identity-regexp 'https://github.com/you/app/.github/workflows/.*' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com

完整工作流

把前面的内容组合起来，就是一条可以直接用于真实项目的流水线：

name: docker

on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:

permissions:
  contents: read
  packages: write
  id-token: write

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: docker/setup-qemu-action@v4
      - uses: docker/setup-buildx-action@v4

      - uses: docker/login-action@v4
        if: github.event_name != 'pull_request'
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha

      # 1. 测试：构建 test 目标，失败即停止
      - uses: docker/build-push-action@v7
        with:
          context: .
          target: test
          cache-from: type=gha
          cache-to: type=gha,mode=max,ignore-error=true

      # 2. 构建生产镜像并载入本地，用于扫描
      - uses: docker/build-push-action@v7
        with:
          context: .
          target: prod
          load: true
          tags: app:scan
          cache-from: type=gha

      # 3. 质量门：有可修复的高危漏洞就失败
      - uses: aquasecurity/trivy-action@v0.36.0
        with:
          image-ref: app:scan
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"

      # 4. 多架构构建并推送（PR 只构建不推送），附带 SBOM 和来源证明
      - id: build
        uses: docker/build-push-action@v7
        with:
          context: .
          target: prod
          platforms: linux/amd64,linux/arm64
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          sbom: true
          provenance: mode=max
          cache-from: type=gha

      # 5. 无密钥签名
      - uses: sigstore/cosign-installer@v4
        if: github.event_name != 'pull_request'
      - if: github.event_name != 'pull_request'
        run: cosign sign --yes ${{ env.IMAGE }}@${{ steps.build.outputs.digest }}

部署：最后一公里

镜像推送到仓库之后，怎么让服务器用上新版本？常见的几种方式，由简到繁（第一种会在第 20 章完整演示）：

方式做法适合
SSH + Compose流水线最后一步 SSH 到服务器，执行 docker compose pull && docker compose up -d单台服务器、小项目
Swarmdocker stack deploy 或 docker service update --image，自动滚动更新（第 12 章）几台服务器的小集群
Kubernetes + GitOps流水线只负责更新配置仓库里的镜像版本，由 Argo CD / Flux 自动同步到集群中大型团队
托管平台Cloud Run、ECS、Azure Container Apps、Fly.io 等，直接指定镜像地址部署不想管服务器
★ 部署时用摘要，而不是标签

生产环境部署 app:main，你没法确定跑的到底是哪次构建。部署清单里写 app@sha256:…（或者 sha-3f2a9c1 这种不会被覆盖的标签）， 回滚时换回上一个摘要即可。再配合 cosign verify 或 Kubernetes 的准入策略，只允许运行你的流水线签过名的镜像。

流水线自身的安全

CI 流水线手握仓库写权限和各种凭据，本身就是攻击者的重要目标：

  • 最小权限：在工作流顶部显式声明 permissions，只给需要的权限（如本章的 contents: read、packages: write、id-token: write）。
  • 固定第三方 action 的版本：标签可以被移动（和镜像标签一样！），安全要求高的项目把 action 固定到完整的 commit SHA，例如 uses: docker/build-push-action@<40 位 SHA> # v7.4.0，并让 Dependabot 帮你更新。
  • 凭据用 Secrets，令牌用最小作用域：Docker Hub 令牌只给“读写”而非“管理员”；能用 GITHUB_TOKEN 或 OIDC 就不用长期令牌。
  • 小心 pull_request_target：它会在有写权限的上下文里运行，绝不要在其中构建或执行来自 fork 的代码。

本章小结

  • 镜像流水线的典型顺序：准备 → 算标签 → 构建 → 测试 → 扫描 → 推送 → 签名 → 部署；PR 只走到扫描为止。
  • Docker 官方的 setup-buildx、login、metadata、build-push 几个 action 覆盖了绝大部分需求。
  • metadata-action 按分支、PR、版本号、提交自动生成标签，让每个镜像都可追溯。
  • CI 机器没有本地缓存，用 type=gha 或仓库缓存把 BuildKit 缓存持久化下来。
  • 测试可以作为 Dockerfile 的一个构建目标；漏洞扫描作为推送前的质量门。
  • 开启 SBOM 和来源证明，用 Cosign 对摘要做无密钥签名；部署时用摘要并验证签名。
  • 流水线本身也要安全：最小权限、固定 action 版本、谨慎处理 fork 的 PR。

✎ 动手练习

  1. 把第 18 章的 todo 项目推到一个 GitHub 仓库，加上本章的最小工作流，确认镜像出现在仓库的 Packages 里并能 docker pull。
  2. 加入 metadata-action，分别推送到 main、开一个 PR、打一个 v0.1.0 的 tag，观察生成了哪些镜像标签。
  3. 加上 type=gha 缓存，对比第一次和第二次运行的构建耗时。
  4. 故意把基础镜像换成一个很老的版本（如 node:16-alpine），看看 Trivy 质量门是否拦住了它。
  5. 完成签名步骤后，在本地用 cosign verify 验证你的镜像；再试试把 --certificate-identity-regexp 改成别人的仓库，确认验证会失败。

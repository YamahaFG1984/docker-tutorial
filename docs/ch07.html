第 7 章

容器

镜像是模板，容器是从模板启动的活生生的实例。本章带你走完容器的一生：启动、进入、查看、修改、停止、重启、删除； 搞清楚容器怎么知道该运行哪个程序；学会用 Docker Debug 调试“什么工具都没有”的精简容器；最后用重启策略让容器自我修复。

本章目标

  • 理解容器的可写层，以及它和镜像只读层的关系
  • 分清 ENTRYPOINT、CMD 和命令行参数三者的关系
  • 熟练使用 run、ps、exec、logs、inspect、stop、restart、rm
  • 理解 PID 1 与“主进程退出，容器就退出”
  • 理解 docker stop 背后的 SIGTERM / SIGKILL 和退出码
  • 会用 Docker Debug 和重启策略

一句话概括

容器是镜像的运行时实例，一个镜像可以启动多个容器。你可以像操作虚拟机一样启动、停止、重启、删除容器， 但容器更小、更快、更便携。而且容器在设计上有几个和虚拟机完全不同的理念：

💨

无状态、短暂

容器被设计成随时可以丢弃和重建。虚拟机则是长期运行、连同状态一起迁移的。

🔒

不可变

部署后就不要再改它。出了问题就用新容器替换，而不是登进去在线修补。

☝

一个容器一个进程

一个有 Web、认证、目录、商店四个功能的应用，就是四个容器 —— 这就是微服务。

ⓘ 容器与虚拟机

第 1 章已经比较过两者：虚拟机虚拟化硬件，容器虚拟化操作系统。Hypervisor 把 CPU、内存等切成虚拟版本打包成虚拟机； 容器运行时把进程树、文件系统、网络栈等操作系统资源切成虚拟版本打包成容器。虚拟机看起来像一台物理服务器，容器看起来像一个普通的操作系统。

镜像与容器：可写层

一个镜像可以启动多个容器。镜像是只读的，但每个容器都可读写。Docker 的做法是：为每个容器创建一个薄薄的读写层，放在共享的镜像之上。

容器通过自己的读写层看到并访问镜像里的文件和程序。容器做出的任何修改都写进自己的读写层（这叫写时复制，copy-on-write： 第一次修改镜像里的某个文件时，先把它复制到读写层再改）。这样每个容器都能保留自己的修改，又不需要对共享镜像有写权限。

确认 Docker 在运行

docker version 同时检查 CLI 和引擎，是很好的“体检”命令。如果 Server 部分报错，通常有两种原因：

  1. 没有权限：Docker API 通过特权 Unix 套接字 /var/run/docker.sock 暴露。Linux 上需要把用户加入 docker 组（sudo usermod -aG docker <用户名>，然后重新登录），或者每条命令加 sudo。
  2. 守护进程没运行：在使用 systemd 的 Linux 上检查一下：
$ systemctl is-active docker
active
$ sudo systemctl start docker     # 如果没在运行，就启动它

容器怎么知道该运行哪个程序？

刚才的容器启动了一个 Web 应用，可我们并没有告诉它要运行什么。它是怎么知道的？告诉 Docker 如何启动容器里的应用，有三种方式：

  1. 镜像里的 ENTRYPOINT 指令
  2. 镜像里的 CMD 指令
  3. 命令行参数（docker run <镜像> <命令> 里镜像名后面的部分）

ENTRYPOINT 和 CMD 都是可选的镜像元数据，用来存储默认启动命令。规则是：

💡 真的要换掉 ENTRYPOINT 怎么办？

ENTRYPOINT 不会被普通命令行参数覆盖，但可以用 --entrypoint 标志显式替换，比如 docker run --entrypoint sh -it 镜像名。

看看 web0.1 这个镜像用的是哪种方式（Windows PowerShell 用户把 grep 换成 Select-String -Pattern 'Entrypoint' -Context 0,3）：

$ docker inspect nigelpoulton/ddd-book:web0.1 | grep Entrypoint -A 3
            "Entrypoint": [
                "node",
                "./app.js"
            ],

镜像里写着 ENTRYPOINT ["node", "./app.js"]，意思是让 Node.js 运行 app.js。如果镜像既没有 ENTRYPOINT 也没有 CMD，就必须在命令行上给出命令：

# 在 alpine 容器里运行 sleep 60，60 秒后容器退出；--rm 让容器退出后自动删除
$ docker run --rm -d alpine sleep 60

60 秒内运行 docker ps 能看到它，60 秒后它就消失了。大多数生产镜像都会设置 ENTRYPOINT 或 CMD。

连接到运行中的容器

docker exec 在运行中的容器里执行命令，有两种模式：

交互模式：docker exec -it
$ docker exec -it webserver sh
/src # ls
Dockerfile  README.md  app.js
node_modules  package.json  views
/src # vim app.js
sh: vim: not found
/src # exit
远程执行模式：docker exec
$ docker exec webserver ps
PID   USER     TIME  COMMAND
    1 root      0:00 node ./app.js
   42 root      0:00 ps

交互模式把你的终端连到容器里的一个 shell 进程上，体验像 SSH；-i 保持标准输入打开，-t 分配一个终端。 远程执行模式把命令发给容器，把输出打印到你本地终端。无论哪种，命令必须在容器里存在才行 —— 所以上面 vim 失败了。

容器里的进程：PID 1

大多数容器只运行一个进程，那就是容器的主应用进程，它的 PID 永远是 1。在交互式 exec 会话里运行 ps：

/src # ps
PID   USER     TIME  COMMAND
    1 root      0:00 node ./app.js      <<---- 主进程
   13 root      0:00 sh                 <<---- 你的 exec 会话
   22 root      0:00 ps                 <<---- 刚刚执行的 ps
★ 容器的生死由 PID 1 决定

容器只在它的主进程运行时才运行。杀掉 PID 1，容器就停了 —— 主进程都没了，容器也就没有存在的理由了。 exec 进去的 shell 退出不会影响容器，因为它不是 PID 1。

查看日志

容器应用应该把日志写到标准输出（STDOUT）和标准错误（STDERR），Docker 会收集它们，用 docker logs 查看：

$ docker logs webserver           # 查看全部日志
$ docker logs -f webserver        # 持续跟踪（像 tail -f），Ctrl+C 退出
$ docker logs --tail 20 -t webserver   # 最后 20 行，带时间戳

往容器里写数据（反面教材）

⚠ 仅供演示

真实世界里不应该这样修改运行中的容器。需要改动时，应该构建并测试一个包含改动的新容器，然后用它替换旧容器。 这里演示只是为了让你理解容器读写层的行为。这种“能用但不是好做法、可能带来意外后果”的做法叫反模式（anti-pattern）。

进入容器，用 vi 修改首页模板 views/home.pug 第 8 行 h1 后面的文字：

$ docker exec -it webserver sh
/src # vi views/home.pug

不熟悉 vi？按这个步骤：

  1. 按 i 进入插入模式；
  2. 用方向键移到第 8 行，删除 h1 后面的文字，输入新内容；
  3. 按 Esc 回到命令模式，输入 :wq 回车保存并退出。

刷新浏览器就能看到变化。输入 exit 退出容器。

停止、重启、删除

$ docker stop webserver           # 优雅停止，最多等 10 秒
webserver
$ docker ps                       # 运行中的容器列表里没有它了
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES
$ docker ps -a                    # -a 能看到已停止的容器
CONTAINER ID   IMAGE         COMMAND           STATUS                       NAMES
b5594b3b8b3f   nigelpou...   "node ./app.js"   Exited (137) 1 minute ago    webserver
$ docker restart webserver        # 重启
webserver

刷新浏览器 —— 你的修改还在！也可以直接从容器文件系统里读取确认：

$ docker exec webserver cat views/home.pug
<Snip>
      div.jumbotron
        h1 Everybody loves containers!     <<---- 我改的这一行

停止和重启不会丢失修改，而且重启非常快。现在删除容器：

$ docker rm webserver -f
webserver

-f 会强制删除，不给应用通常的 10 秒宽限期来刷新缓冲区、优雅退出，而且 Docker 不会要求确认。 删除之后，容器的一切痕迹都没了，你改的内容也随着读写层一起消失。用同一个镜像 docker run 一个新容器，它不会有你的改动。

docker stop 背后发生了什么：信号与退出码

🔬 深入：为什么上面显示 Exited (137)？

退出码 137 = 128 + 9（SIGKILL 的编号），说明容器是被强制杀死的，而不是自己优雅退出的。 原因是：Linux 内核对 PID 1 特殊对待 —— 如果 PID 1 进程没有为 SIGTERM 注册处理函数，这个信号会被直接忽略。 很多 Node.js、Python 应用作为 PID 1 运行时都没处理 SIGTERM，于是只能干等 10 秒被 SIGKILL。 解决办法：在代码里处理 SIGTERM（比如 Node.js 的 process.on('SIGTERM', …)），或者运行时加 --init， 让 Docker 自带的迷你 init 进程（tini）当 PID 1，负责转发信号和回收僵尸进程。

杀死主进程会怎样

来验证“杀掉主进程就会杀掉容器”。启动一个交互式 Ubuntu 容器，让 Bash 作为主进程：

$ docker run --name ddd-ctr -it ubuntu:24.04 bash
root@d3c892ad0eb3:/# ps
  PID TTY          TIME CMD
    1 pts/0    00:00:00 bash
    9 pts/0    00:00:00 ps
root@d3c892ad0eb3:/# exit
$ docker ps -a
CONTAINER ID   IMAGE          COMMAND   STATUS                  NAMES
d3c892ad0eb3   ubuntu:24.04   "bash"    Exited (0) 3 secs ago   ddd-ctr

输入 exit 结束了 Bash（PID 1），容器随之退出，退出码 0 表示正常退出。重启它，并用 docker attach 把终端重新连到主进程：

$ docker restart ddd-ctr
$ docker attach ddd-ctr
root@d3c892ad0eb3:/#
★ Ctrl+P Ctrl+Q：离开但不杀死

想从容器里出来又不杀死主进程？依次按 Ctrl+P、Ctrl+Q，终端会显示 read escape sequence 并回到本地， 容器继续运行。attach 连的是主进程（PID 1），在里面 exit 会杀死容器；exec 开的是新进程，在里面 exit 不影响容器。

用 Docker Debug 调试精简容器

部署精简镜像是公认的好做法：只含应用代码和依赖，不带 shell 和调试工具，镜像更小、更安全。但这也让出问题时很难排查。 前面的 ddd-ctr 容器里，ping、nslookup、vim 统统不存在： 

root@d3c892ad0eb3:/# ping nigelpoulton.com
bash: ping: command not found
root@d3c892ad0eb3:/# nslookup nigelpoulton.com
bash: nslookup: command not found

Docker Debug 就是为此而生：它能为没有 shell 的镜像和容器提供 shell，并无缝注入强大的调试工具。 原理是把一个装满工具的“工具箱”以 /nix 目录的形式挂进调试会话里 —— 只在调试会话中可见，容器本身永远看不到它，退出调试后就被移除。 

$ docker debug ddd-ctr
This is an attach shell, i.e.:
- Any changes to the container filesystem are visible to the container directly.
- The /nix directory is invisible to the actual container.
root@d3c892ad0eb3 / [ddd-ctr]
docker > ping nigelpoulton.com
PING nigelpoulton.com (192.124.249.126) 56(84) bytes of data.
64 bytes from cloudproxy10126.sucuri.net: icmp_seq=1 ttl=63 time=58.3 ms
^C
docker > nslookup nigelpoulton.com
zsh: command not found: nslookup
docker > install bind                <<---- 从 search.nixos.org 安装任意包
installing 'bind-9.18.19'
docker > nslookup nigelpoulton.com
Name:    nigelpoulton.com
Address: 192.124.249.126
docker > entrypoint --print          <<---- 查看/检查镜像的启动命令
node ./app.js
docker > exit

调试运行中的容器和调试镜像（或已停止的容器）行为不同：

调试对象会话类型你做的修改
运行中的容器attach shell立即对容器可见，并且在容器重启后依然保留
镜像 / 已停止的容器sandbox shell（临时加一个读写层）退出调试会话后全部丢弃

无论哪种情况，你安装的工具都只存在于工具箱中，永远不会成为容器或镜像的一部分。

✨ 关于 Docker Debug 的可用性

Docker Debug 随 Docker Desktop 提供（docker debug CLI 插件），需要 docker login。原书写作时它需要 Pro/Team/Business 订阅， 具体的订阅要求请以官方文档为准。 如果你用的是纯 Docker Engine，可以用一个替代思路：启动一个带工具的“调试容器”，与目标容器共享命名空间： docker run -it --rm --pid container:ddd-ctr --network container:ddd-ctr nicolaka/netshoot。

用重启策略实现自我修复

重启策略是一种简单的自我修复机制，让本机的 Docker 引擎自动重启失败的容器。重启策略是按容器设置的，Docker 支持四种：

策略非零退出码
（出错了）		零退出码
（正常退出）		docker stop守护进程重启后
no（默认）✗✗✗✗
on-failure[:N]✓✗✗✓
always✓✓✗✓（即使之前被手动停止过）
unless-stopped✓✓✗✓（手动停止过的不启动）

演示 always 策略：启动一个交互式容器，然后 exit 杀死主进程（正常退出，退出码 0）：

$ docker run --name neversaydie -it --restart always alpine sh
/ # exit
$ docker ps
CONTAINER ID   IMAGE    COMMAND   CREATED          STATUS         NAMES
1933623830bb   alpine   "sh"      35 seconds ago   Up 2 seconds   neversaydie
$ docker inspect neversaydie | grep RestartCount
        "RestartCount": 1,

容器 35 秒前创建，但只运行了 2 秒 —— 因为你让它退出后，Docker 自动重启了它。注意 Docker 重启的是同一个容器，而不是新建一个， 所以 RestartCount 变成了 1。

always 有个有趣的特性：如果你用 docker stop 停止了容器，然后 Docker 守护进程重启（比如服务器重启）， 守护进程起来后会把这个容器也启动。如果你不想要这种行为，就用 unless-stopped。

✨ 更正原书：Compose 和 Swarm 的写法不同

原书把两种写法混在了一起。实际上：

  • Docker Compose（第 9 章）用服务级的 restart: 键：restart: unless-stopped，取值和 docker run --restart 一样。
  • Docker Swarm（第 12 章）用 deploy.restart_policy.condition，取值是 none、on-failure、any。
services:
  web:
    image: nginx
    restart: unless-stopped        # Compose：单机
  worker:
    image: my-worker
    deploy:
      restart_policy:              # Swarm：集群
        condition: on-failure
        max_attempts: 3

给容器设置资源上限

原书在第 16 章才提到 cgroups，但限制资源是日常就会用到的，这里先学两个最常用的参数：

$ docker run -d --name limited --memory 512m --cpus 1.5 nginx   # 最多 512MB 内存、1.5 个 CPU
$ docker stats --no-stream                                      # 查看各容器实时资源占用
CONTAINER ID   NAME      CPU %     MEM USAGE / LIMIT   MEM %
a1b2c3d4e5f6   limited   0.00%     8.1MiB / 512MiB     1.58%

容器内存用超上限会被内核 OOM Killer 杀掉（docker inspect 里 OOMKilled: true，退出码 137）。

清理

$ docker rm $(docker ps -aq) -f     # 删除所有容器（不会确认，慎用！）
$ docker rmi $(docker images -q)    # 删除所有镜像
$ docker container prune            # 或者：只删除所有已停止的容器

要先删容器，再删镜像 —— 被容器使用的镜像删不掉。

本章小结

  • 容器是镜像的运行时实例：共享只读镜像，各自拥有一个薄的读写层。停止/重启不丢修改，删除则读写层一起消失。
  • 容器启动哪个程序，由镜像的 ENTRYPOINT / CMD 或命令行参数决定：参数覆盖 CMD、追加到 ENTRYPOINT。
  • 容器通常只运行一个主进程（PID 1），它退出容器就退出。
  • docker stop 先发 SIGTERM，宽限期后发 SIGKILL；退出码 137 意味着被强制杀死。
  • Docker Debug 能在不修改容器的前提下为精简容器注入调试工具。
  • 重启策略（no / on-failure / always / unless-stopped）让容器能自动从故障中恢复。

✎ 动手练习

  2. 分别用 docker run alpine echo hi、docker run --entrypoint ls alpine / 验证 CMD 被覆盖、ENTRYPOINT 被替换的效果。

  4. 用 docker run --memory 20m alpine sh -c "tail /dev/zero" 触发一次 OOM，然后用 docker inspect 找到 OOMKilled 字段。

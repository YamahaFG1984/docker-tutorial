第 17 章

排错实战

学 Docker 最让人沮丧的时刻，不是概念听不懂，而是“命令敲了，就是不工作”。 本章把初学者最常遇到的八类问题整理成症状 → 排查命令 → 常见原因 → 解决办法的格式，并教你一套通用的排错思路。 遇到问题时，把这一章当成手册来查。

本章目标

  • 掌握一套通用的排错五步法，以及每一步用什么命令
  • 看懂容器退出码，快速判断“为什么一启动就退出”
  • 解决“容器在跑但访问不到”“容器之间连不上”这两类网络问题
  • 解决构建失败、拉取失败、磁盘占满、权限不足等常见问题

排错五步法

不管遇到什么问题，都可以按同一个顺序排查：从外到内、从简单到复杂。大多数问题在前三步就能找到原因。

排错工具箱

命令什么时候用
docker ps -a第一步永远是它：容器在不在、状态、退出码、端口映射
docker logs --tail 50 -t 容器看应用最后输出了什么；-f 持续跟踪
docker inspect 容器完整配置：State（含 ExitCode、OOMKilled、Error）、Mounts、NetworkSettings、Config.Env
docker events实时查看引擎事件：容器反复重启、被 OOM 杀掉，一眼可见
docker exec -it 容器 sh进入运行中的容器检查文件、进程、网络
docker debug 容器容器里没有 shell 或工具时使用（第 7 章）
docker run --rm -it --network container:目标 nicolaka/netshoot共享目标容器的网络命名空间，用满满一箱网络工具排查
docker stats / docker system df资源占用 / 磁盘占用
docker compose config / logs / psCompose 应用：看最终配置、看所有服务日志、看状态
docker build --progress=plain构建失败时看完整输出
💡 用 --format 只看关键字段

docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' 容器 能一行看完“怎么死的”。 docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}' 能让列表清爽很多。

问题一：容器一启动就退出

症状：docker run -d 返回了容器 ID，但 docker ps 里没有它；docker ps -a 显示 Exited (x) 2 seconds ago，或者 Restarting 反复出现。

先记住第 7 章的核心规则：容器只在 PID 1 运行时才运行。容器退出了，说明主进程结束了，要找的就是“它为什么结束”。而退出码是最重要的线索：

退出码含义典型原因
0正常结束主进程本来就是一次性任务（如 echo），或者是 shell 却没有 -it，读到 EOF 就退出了
1 等应用自己报错退出配置错误、缺少环境变量、连不上数据库 —— 看 docker logs
125docker run 本身失败参数写错、端口已被占用、名字冲突，容器根本没启动
126命令无法执行文件没有执行权限、是目录而不是程序
127命令找不到CMD/ENTRYPOINT 拼错、镜像里没有这个程序、脚本的 #!/bin/bash 在 alpine 里不存在
137被 SIGKILL（128+9）内存超限被 OOM 杀掉，或 docker stop 超时后被强杀
139段错误（128+11）程序崩溃，常见于架构或 C 库不匹配（glibc 程序跑在 musl/alpine 上）
143被 SIGTERM（128+15）被正常停止，通常不是问题

几个经典案例

# 案例 A：运行 ubuntu 却秒退
$ docker run -d ubuntu
$ docker ps -a
... ubuntu  "/bin/bash"  Exited (0) 1 second ago
# 原因：ubuntu 的默认命令是 bash，没有 -it 时读不到输入，立刻结束。
# 解决：交互用 docker run -it ubuntu；想让它挂着就给一个长期运行的命令：
$ docker run -d ubuntu sleep infinity

# 案例 B：退出码 1，日志里写着原因
$ docker run -d --name db postgres:17
$ docker logs db
Error: Database is uninitialized and superuser password is not specified.
       You must specify POSTGRES_PASSWORD to a non-empty value for the superuser.
# 解决：按提示传入环境变量
$ docker run -d --name db -e POSTGRES_PASSWORD=secret postgres:17

# 案例 C：exec format error —— 架构不匹配
$ docker logs myapp
exec /app/server: exec format error
# 原因：在 M 系列 Mac（arm64）上构建的镜像，拿到 amd64 服务器上运行（或反过来）。
# 解决：构建时指定平台，或构建多架构镜像（第 8 章）
$ docker build --platform linux/amd64 -t myapp .
⚠ Windows 用户的隐形杀手：CRLF 换行

在 Windows 上编辑的 entrypoint.sh 默认是 CRLF 换行，复制进 Linux 容器后，第一行会变成 #!/bin/sh\r， 报错往往是莫名其妙的 no such file or directory（明明文件就在那里）。把编辑器改成 LF 换行，或在仓库里加 .gitattributes：*.sh text eol=lf。

问题二：容器在运行，但浏览器访问不到

症状：docker ps 显示 Up，但浏览器打开 localhost:8080 转圈、拒绝连接或返回空响应。

请求要经过三关，逐关检查：

第 3 关详解：监听地址

这是最让初学者抓狂的问题。很多开发服务器（Flask、Vite、Rails、Next.js 的某些模式……）默认只监听 127.0.0.1。在你电脑上直接运行没问题，放进容器就访问不到了：

# 进容器看看应用到底在听哪个地址、哪个端口
$ docker exec web sh -c "netstat -tlnp 2>/dev/null || ss -tlnp"
Proto  Local Address      State    PID/Program
tcp    127.0.0.1:5000     LISTEN   1/python          <<---- 问题在这里

# 常见框架的修复方式
$ flask run --host=0.0.0.0
$ npx vite --host 0.0.0.0
$ uvicorn app:app --host 0.0.0.0 --port 8000
ⓘ 其他几个“访问不到”的原因
  • 端口被占用：docker run 报 port is already allocated 或 address already in use。换一个主机端口，或者找出占用者：lsof -i :8080（Mac/Linux）、netstat -ano | findstr 8080（Windows）。
  • 应用还没启动完：Java、大型 Node 应用可能要十几秒才开始监听，先 docker logs -f 看到“Listening on…”再访问。
  • 用了 Multipass / 远程主机：localhost 指的是你的电脑，要换成虚拟机或服务器的 IP。

问题三：容器之间连不上

症状：后端日志里出现 Connection refused、Name or service not known、getaddrinfo ENOTFOUND db、could not translate host name。

用一个临时容器，站在“同一个网络里”测试连通性，能快速定位问题：

# 1. 两个容器在不在同一个网络？
$ docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}' api db
myapp_default
myapp_default

# 2. 在同一个网络里起一个工具容器：名字能解析吗？端口通吗？
$ docker run --rm -it --network myapp_default nicolaka/netshoot
~ # nslookup db               # DNS 解析
~ # nc -zv db 5432            # 端口连通性
db (172.20.0.3:5432) open

容器访问宿主机上的服务

另一种常见需求是反过来：容器里的应用要访问宿主机上运行的数据库或 API。这时同样不能用 localhost：

环境容器里用什么地址访问宿主机
Docker Desktop（Mac / Windows / Linux）host.docker.internal（开箱即用）
Linux 上的 Docker Engine启动时加 --add-host=host.docker.internal:host-gateway，然后同样用 host.docker.internal
⚠ 宿主机服务也要监听对地址

宿主机上的数据库如果只监听 127.0.0.1，容器照样连不上 —— 和图 17-4 是同一个道理，只是方向反过来了。

“连接被拒绝”但过一会儿又好了

这通常是启动顺序问题：后端先起来了，数据库还在初始化。depends_on 的简单写法只等容器“启动”，不等服务“就绪”。 解决办法是第 9 章讲过的 healthcheck + condition: service_healthy，同时让应用自己具备重试能力（生产环境里依赖随时可能短暂不可用）。

    docker build --no-cache --progress=plain -f - .

# 查看最近一次构建的详细日志
$ docker buildx history ls
$ docker buildx history logs

问题五：镜像拉取失败

报错原因解决
manifest unknown / not found标签不存在（拼错了、或者这个库没有 latest）去 Docker Hub 页面确认标签名
pull access denied ... repository does not exist or may require 'docker login'镜像名写错，或者是私有镜像检查名字；私有镜像先 docker login
toomanyrequests: You have reached your pull rate limitDocker Hub 匿名拉取次数超限docker login；CI 里使用登录凭据或镜像缓存
no matching manifest for linux/arm64这个镜像没有你机器架构的版本找支持多架构的镜像；或 --platform linux/amd64 走模拟
超时、TLS handshake timeout网络问题：代理、防火墙、访问 Docker Hub 受限配置 Docker 代理；在 daemon.json 里配置 registry-mirrors 使用镜像加速
{
  "registry-mirrors": ["https://mirror.example.com"],
  "proxies": {
    "http-proxy": "http://proxy.example.com:3128",
    "https-proxy": "http://proxy.example.com:3128",
    "no-proxy": "localhost,127.0.0.1"
  }
}

修改后执行 sudo systemctl restart docker。Docker Desktop 用户在 Settings → Resources → Proxies 和 Docker Engine 页面里修改。

问题六：磁盘被占满

症状：no space left on device；Docker Desktop 的虚拟磁盘越来越大；服务器根分区告急。

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          48        6         21.3GB    18.9GB (88%)
Containers      12        3         1.2GB     1.1GB (91%)
Local Volumes   9         4         3.4GB     1.8GB (52%)
Build Cache     214       0         15.7GB    15.7GB          <<---- 构建缓存常常是大头

另外两个容易忽视的“磁盘杀手”：

  • 容器日志：默认的 json-file 驱动不限制大小。用 docker inspect -f '{{.LogPath}}' 容器 找到日志文件，看看它有多大；按第 13 章配置 max-size。
  • Docker Desktop 的虚拟磁盘：清理后空间不会立刻还给宿主机时，可以在 Settings → Resources 里调整磁盘上限，或在 Troubleshoot 里清理 / 重置。

问题七：权限问题

permission denied … docker.sock

permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock

你的用户不在 docker 组里（第 3 章）。sudo usermod -aG docker $USER 后必须重新登录（或 newgrp docker）才生效 —— 很多人卡在“加了组还是不行”，就是因为没重新登录。

绑定挂载的目录写不进去

  • 让容器用你的 UID 运行：docker run --user "$(id -u):$(id -g)" …，Compose 里写 user: "1000:1000"；
  • 或者在 Dockerfile 里创建一个 UID 与宿主机一致的用户；
  • 生产数据用卷而不是绑定挂载，可以在 Dockerfile 里提前 chown 好挂载点目录，避开大部分权限问题；
  • Fedora / RHEL 等启用 SELinux 的系统上，绑定挂载可能需要加 :z 或 :Z 标签：-v ./data:/data:Z。

问题八：又慢又卡

症状排查常见原因与解决
容器莫名重启，退出码 137docker inspect -f '{{.State.OOMKilled}}'、docker events内存上限太低或内存泄漏；调大 --memory 或修复程序
整台机器变卡docker stats某个容器吃满 CPU/内存；给它加 --cpus、--memory 限制
Mac / Windows 上 npm install、编译极慢对比在卷里和在绑定挂载目录里的速度绑定挂载要跨越虚拟机边界。把 node_modules 等放进命名卷；Docker Desktop 开启 VirtioFS / 同步文件共享
Apple 芯片 Mac 上某个镜像特别慢docker inspect -f '{{.Architecture}}' 镜像跑的是 amd64 镜像，靠模拟运行。换用 arm64 / 多架构镜像

本章小结

  • 排错按五步走：看状态 → 看日志 → 看配置 → 进去看 → 缩小范围。docker logs 能解决大部分问题。
  • 退出码是“容器为什么退出”的关键线索：127 命令找不到、137 被强杀（多半是 OOM）、1 看日志。
  • “访问不到”最隐蔽的原因是应用只监听 127.0.0.1；容器里的 localhost 只属于容器自己。
  • 容器之间用服务名 + 容器端口通信，并且必须在同一个自定义网络上。
  • 用 netshoot 这类工具容器加入目标网络或命名空间，是排查网络问题的利器。
  • 磁盘满了先看 docker system df，从风险最低的构建缓存开始清理，卷最后再动。

✎ 动手练习：故意把它弄坏

  1. 运行 docker run -d -p 8000:8000 python:3.13-slim python -m http.server --bind 127.0.0.1 8000，确认浏览器访问不到 localhost:8000；再把 --bind 改成 0.0.0.0 重新运行，对比结果，并用图 17-4 解释原因。
  2. 运行 docker run -d --name oops alpine lss，用本章的方法找出退出码和原因。
  3. 启动两个容器，一个在默认 bridge 网络，一个在自定义网络，用 netshoot 分别测试名字解析，写下你的结论。
  4. 用 docker run --memory 20m alpine sh -c "tail /dev/zero" 制造一次 OOM，在另一个终端用 docker events 观察发生了什么事件。

第 8 章

应用容器化

Docker 让“把应用打包成镜像、再作为容器运行”变得非常简单，这个过程叫容器化（containerization）。 本章完整走一遍：写 Dockerfile、构建镜像、推送到 Docker Hub、运行；然后学习生产级技巧 —— 多阶段构建、构建缓存、多架构构建，以及一系列最佳实践。

本章目标

  • 掌握容器化的五个步骤
  • 读懂 Dockerfile 的常用指令，知道哪些指令产生层、哪些只产生元数据
  • 理解构建上下文和 .dockerignore
  • 用 docker tag / docker push 把镜像推送到仓库
  • 用多阶段构建把镜像从几百 MB 压到几 MB
  • 理解 Buildx、BuildKit、构建器和多架构构建
  • 写出能充分利用构建缓存、安全又精简的 Dockerfile

容器化的五个步骤

容器化一个单容器应用

我们要容器化一个简单的 Node.js Web 应用，它在 8080 端口提供一个网页。

获取应用代码

$ git clone https://github.com/nigelpoulton/ddd-book.git
$ cd ddd-book/node-app
$ ls -l
-rw-r--r--    1 nigel  staff    341  app.js
drwxr-xr-x  103 nigel  staff   3296  node_modules
-rw-r--r--    1 nigel  staff  39975  package-lock.json
-rw-r--r--    1 nigel  staff    355  package.json

这个目录就是构建上下文（build context），因为它包含了应用源代码和依赖清单。要容器化它，还缺一个 Dockerfile。

ⓘ 没有 docker init？

纯 Docker Engine 安装可能没有 docker init 插件。没关系，仓库里有一个现成的 sample-Dockerfile，把它重命名为 Dockerfile 即可继续。

生成的 Dockerfile 类似这样（为了讲解加上了行号）：

# syntax=docker/dockerfile:1
ARG NODE_VERSION=22
FROM node:${NODE_VERSION}-alpine
ENV NODE_ENV production
WORKDIR /usr/src/app
RUN --mount=type=bind,source=package.json,target=package.json \
    --mount=type=bind,source=package-lock.json,target=package-lock.json \
    --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev
USER node
COPY . .
EXPOSE 8080
CMD node app.js
指令作用
# syntax=docker/dockerfile:1告诉 BuildKit 使用最新的 Dockerfile 1.x 语法（可以用上 --mount 等新特性）
ARG + FROM定义构建参数 NODE_VERSION，拉取 node:22-alpine 作为基础镜像
ENV NODE_ENV ...让 Node 以生产模式运行（性能更好、日志更少）
WORKDIR设置后续指令的工作目录：后面的 RUN、COPY、CMD 都在 /usr/src/app 里执行
RUN --mount=...把依赖清单绑定挂载进来（不进入镜像层），并用缓存挂载保留 npm 缓存，然后 npm ci --omit=dev 只安装生产依赖
USER node之后以非 root 用户 node 运行 —— 重要的安全实践
COPY . .把构建上下文（第一个点）里的源代码复制到镜像的 WORKDIR（第二个点）
EXPOSE 8080记录应用使用的端口（文档作用，不会真的打开端口）
CMD容器启动时执行的命令

BuildKit 内置了构建检查（build checks），可以像代码 lint 一样检查 Dockerfile。试试看： 

$ docker build --check .

第二个警告尤其重要。CMD 有两种写法：

shell 形式（不推荐）
CMD node app.js
# 实际执行：/bin/sh -c "node app.js"
# PID 1 是 sh，不是 node
# docker stop 的 SIGTERM 到不了 node
exec 形式（推荐）
CMD ["node", "app.js"]
# 直接执行 node，没有 shell 包装
# PID 1 就是 node
# 能直接收到 SIGTERM，优雅退出

回想第 7 章的信号知识就明白了。修正后的 Dockerfile：

# syntax=docker/dockerfile:1
ARG NODE_VERSION=22
FROM node:${NODE_VERSION}-alpine
ENV NODE_ENV=production
WORKDIR /usr/src/app
RUN --mount=type=bind,source=package.json,target=package.json \
    --mount=type=bind,source=package-lock.json,target=package-lock.json \
    --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev
USER node
COPY . .
EXPOSE 8080
CMD ["node", "app.js"]

构建上下文与 .dockerignore

那个末尾的点到底是什么意思？构建时，Buildx 客户端会把构建上下文（这个目录下的文件）发送给 BuildKit 构建器，Dockerfile 里的 COPY 只能复制上下文里的文件：

node_modules
.git
.env
*.log
Dockerfile
compose.yaml
⚠ 一定要有 .dockerignore

没有它，COPY . . 会把 .git 历史、本地的 node_modules（可能是给 macOS 编译的，放进 Linux 镜像会出错）、 甚至包含密码的 .env 文件统统复制进镜像。镜像一旦推送到公共仓库，里面的密钥就泄露了。

再仔细看看：指令与层

docker build 从上到下逐行解析 Dockerfile。以 # 开头的行是注释（第一行的 # syntax= 是一个特殊的解析器指令）。 其余每行都是一条指令，格式为 指令 参数。指令名不区分大小写，但习惯上写成大写，便于阅读。

★ 记住这条规律

添加内容（文件、程序）的指令创建新层：FROM、RUN、COPY、ADD，以及会创建目录的 WORKDIR。
不添加内容的指令只创建元数据：EXPOSE、ENV、CMD、ENTRYPOINT、USER、LABEL、ARG。 

$ docker history ddd-book:ch8.node
IMAGE          CREATED BY                                   SIZE      COMMENT
24dd...a06b    CMD ["node" "app.js"]                        0B        buildkit.dockerfile.v0
<missing>      EXPOSE map[8080/tcp:{}]                      0B        buildkit.dockerfile.v0
<missing>      COPY . . # buildkit                          98kB      buildkit.dockerfile.v0
<missing>      USER node                                    0B        buildkit.dockerfile.v0
<missing>      RUN /bin/sh -c npm ci --omit=dev # buildkit  13.6MB    buildkit.dockerfile.v0
<missing>      WORKDIR /usr/src/app                         16.4kB    buildkit.dockerfile.v0
<missing>      ENV NODE_ENV=production                      0B        buildkit.dockerfile.v0
<Snip>                                                          <<---- 以下是基础镜像的历史
<missing>      ADD alpine-minirootfs-3.22.0-aarch64.tar.gz  8.84MB

SIZE 非零的行创建了层，0B 的行只添加了元数据。buildkit.dockerfile.v0 结尾的行来自你的 Dockerfile，下面的来自基础镜像。

💡 选好基础镜像

通常建议以 Docker 官方镜像、认证发布者镜像或 Docker Hardened Images 作为基础镜像， 它们质量高、会及时修复已知漏洞。第 16 章会进一步介绍 Hardened Images。

走向生产：多阶段构建

说到容器镜像，大就是坏：

  • 大意味着慢（推送、拉取、启动都慢）；
  • 大意味着可能存在更多漏洞；
  • 大意味着更大的攻击面。

所以生产镜像应该只包含运行应用必需的东西。多阶段构建（multi-stage build）就是为此而生：一个 Dockerfile 里有多条 FROM， 每条 FROM 开始一个新的构建阶段。你可以在一个装满编译器和工具的大镜像里完成繁重的编译工作， 然后只把编译好的产物复制到一个精简的生产镜像里。构建器甚至能并行执行互不依赖的阶段。

来看一个 Go 应用的例子（在仓库的 multi-stage 目录里）。不懂 Go 没关系，只需知道它会把客户端和服务端编译成两个不依赖任何运行时的可执行文件：

FROM golang:1.25-alpine AS base                # 阶段 0：准备构建环境
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .

FROM base AS build-client                      # 阶段 1：编译客户端
RUN go build -o /bin/client ./cmd/client

FROM base AS build-server                      # 阶段 2：编译服务端
RUN go build -o /bin/server ./cmd/server

FROM scratch AS prod                           # 阶段 3：生产镜像
COPY --from=build-client /bin/client /bin/
COPY --from=build-server /bin/server /bin/
ENTRYPOINT [ "/bin/server" ]
  • base 阶段拉取 350MB+ 的 Go 镜像，复制依赖清单（go.mod、go.sum）、下载依赖、复制源码，产出一个“构建工具齐全、但应用成分很少”的中间镜像；
  • build-client 和 build-server 都 FROM base，复用上一阶段的成果，各自编译一个可执行文件。它们互不依赖，所以可以并行；
  • prod 阶段从 scratch（一个完全空的镜像）开始，用 COPY --from 从前面的阶段只拿编译好的两个文件。
$ cd ../multi-stage
$ docker build -t multi:full .
[+] Building 14.6s (15/15) FINISHED
 <Snip>
 => [build-client 1/1] RUN go build -o /bin/client ./cmd/client     5.1s   <<---- 并行
 => [build-server 1/1] RUN go build -o /bin/server ./cmd/server     5.1s   <<---- 并行

$ docker images multi
REPOSITORY   TAG    IMAGE ID       CREATED         SIZE
multi        full   a7a01440f2b5   5 seconds ago   26.7MB

$ docker history multi:full
IMAGE          CREATED BY                          SIZE
a7a01440f2b5   ENTRYPOINT ["/bin/server"]          0B
<missing>      COPY /bin/server /bin/ # buildkit   8.64MB
<missing>      COPY /bin/client /bin/ # buildkit   8.53MB

最终镜像只有 26.7MB、两个层，比构建用的 350MB+ 基础镜像小了十几倍。

构建目标：一个 Dockerfile，多个镜像

把最后的 prod 阶段拆成两个，就能从同一个 Dockerfile 分别构建客户端镜像和服务端镜像（仓库里的 Dockerfile-final）：

FROM scratch AS prod-client
COPY --from=build-client /bin/client /bin/
ENTRYPOINT [ "/bin/client" ]

FROM scratch AS prod-server
COPY --from=build-server /bin/server /bin/
ENTRYPOINT [ "/bin/server" ]

$ docker build -t multi:client --target prod-client -f Dockerfile-final .
$ docker build -t multi:server --target prod-server -f Dockerfile-final .
$ docker images multi
REPOSITORY   TAG      IMAGE ID       SIZE
multi        full     a7a01440f2b5   26.7MB
multi        server   a75778df1b9c   11.7MB
multi        client   02b621e9415f   11.9MB

-f 指定 Dockerfile 文件名，--target 指定构建到哪个阶段为止。客户端和服务端镜像各约为完整镜像的一半，合情合理。

Buildx、BuildKit、驱动与 Build Cloud

Docker 的构建系统本身也是客户端 / 服务端架构：

  • 客户端：Buildx —— 以 CLI 插件形式实现，支持 BuildKit 的所有新特性。自 Docker Engine 23.0 / Docker Desktop 4.19 起是默认构建客户端，所以你每次运行 docker build 其实都在用 Buildx。
  • 服务端：BuildKit —— 真正执行构建的引擎。每个 BuildKit 实例叫一个构建器（builder），可以在本机、在你的数据中心、或在 Docker Build Cloud 里。

运行 docker build 时，Buildx 解析命令，把构建请求（Dockerfile、命令行参数、缓存选项、导出选项、构建上下文）发给选定的构建器。 构建器执行构建并导出镜像，Buildx 负责监控并报告进度。 

$ docker buildx ls

builder *                  docker-container
 \_ builder0               desktop-linux            linux/arm64, linux/amd64, linux/riscv64,
                                                    linux/ppc64le, linux/s390x, linux/386, ...
cloud-nigelpoulton-ddd     cloud
 \_ linux-arm64            cloud://nigel...arm64    linux/arm64*
 \_ linux-amd64            cloud://nigel...amd64    linux/amd64*, linux/amd64/v2, ...
desktop-linux              docker
 \_ desktop-linux          desktop-linux            linux/arm64, linux/amd64, ...

带星号 * 的是默认构建器。docker-container 驱动支持的平台更多（靠 QEMU 模拟），Build Cloud 只支持 AMD 和 ARM，但在原生硬件上跑，复杂构建会快得多。

✨ 最新变化：Bake 与构建历史
  • Docker Bake（docker buildx bake）用一个 HCL/JSON/Compose 文件声明多个构建目标，一条命令并行构建。 Compose v5 已经移除了内置构建器，docker compose build 现在直接委托给 Bake，和 docker build 用的是同一套引擎。
  • docker buildx history ls / inspect 可以回看之前每次构建的耗时、缓存命中、日志和错误。

多架构构建

一条 docker build 命令就能为多个平台构建镜像，包括和你本机不同的架构：AMD 机器能构建 ARM 镜像，ARM 机器（比如 M 系列 Mac）也能构建 AMD 镜像。

先创建一个使用 docker-container 驱动的构建器，并设为默认：

$ docker buildx create --driver=docker-container --name=container
$ docker buildx use container

进入仓库的 web-app 目录，同时构建 AMD 和 ARM 两个版本，并直接推送到 Docker Hub（请换成你的 Docker ID；不想推送就把 --push 换成 --load）：

$ docker buildx build --builder=container \
    --platform=linux/amd64,linux/arm64 \
    -t nigelpoulton/ddd-book:ch8.1 --push .
[+] Building 79.3s (26/26) FINISHED
 => [linux/arm64 2/5] RUN apk add --update nodejs npm curl        19.0s
 => [linux/amd64 2/5] RUN apk add --update nodejs npm curl        17.4s
 => [linux/amd64 3/5] COPY . /src                                  0.0s
 <Snip>
 => => pushing manifest for docker.io/nigelpoulton/ddd-book:ch8.1@sha256:8fc61...

每条指令都执行了两次（AMD 一次、ARM 一次），最后推送的是一个 manifest list，两个架构的镜像出现在 Docker Hub 同一个库、同一个标签下（回忆第 6 章图 6-10）。

如果你有 Docker Build Cloud 订阅，可以创建云端构建器，然后用 --builder 指定它：

$ docker buildx create --driver cloud nigelpoulton/ddd
$ docker buildx build --builder=cloud-nigelpoulton-ddd \
    --platform=linux/amd64,linux/arm64 \
    -t nigelpoulton/ddd-book:ch8.1 --push .
 => [internal] connected to docker build cloud service
💡 containerd 镜像存储让事情更简单

在使用 containerd 镜像存储的 Docker（Engine 29 全新安装、较新的 Docker Desktop）上，默认的 docker 驱动就能构建多平台镜像， 并且能用 --load 把多平台镜像直接载入本地，不一定非要额外创建 docker-container 构建器。

最佳实践

1. 充分利用构建缓存

BuildKit 用缓存来加速构建。在一台干净的主机上构建一个镜像，然后立刻再构建一次，你会发现第二次瞬间完成 —— 因为第一次构建的层都被缓存了。 本地构建器的缓存只对本机可用；Build Cloud 的缓存可以全团队共享。

构建器从上到下逐行检查 Dockerfile。对每一行，它会看缓存里是否已经有“在同样的父层之上执行同样的指令”得到的层：

几个要点：

  • 任何一条指令缓存未命中，缓存就失效了，后续指令都会完整执行。所以要把最可能导致缓存失效的指令放在 Dockerfile 末尾。
  • COPY 和 ADD 会对复制的每个文件计算校验和。即使指令文字没变，只要文件内容变了，缓存也会失效 —— 否则你就会得到旧版本的文件。
  • 想强制忽略缓存，用 docker build --no-cache。
  • RUN --mount=type=cache（docker init 生成的那种）可以让 npm、pip、apt、go 的下载缓存跨构建保留，即使该层需要重建也不用从头下载。

2. 只安装必需的软件包

我们常开玩笑说“构建应用时把整个互联网都装上了”。前面那个 Node.js 应用只依赖 Express 和 Pug 两个包，但它们又依赖其他包……最终会下载 110 多个包！ 很多包管理器提供了只装必需品的方法，比如 apt 的 --no-install-recommends，只安装 depends 字段里的包，不装推荐和建议的包： 

RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*        # 同一层里清理，不留垃圾

命令速查

命令作用
docker init分析项目并生成 Dockerfile、.dockerignore、compose.yaml
docker build -t 名:标签 .用当前目录作为上下文构建镜像；-f 指定 Dockerfile，--target 指定阶段
docker build --check .只运行构建检查，不真正构建
docker tag 旧名 新名给镜像加一个新名字
docker login / docker push登录仓库 / 推送镜像
docker history 镜像查看每条指令产生的层与大小
docker buildx ls / create / use列出 / 创建 / 切换构建器
docker buildx build --platform a,b --push多架构构建并推送
docker buildx history ls查看构建历史

本章小结

  • 容器化 = 把应用构建成镜像并作为容器运行。流程：写代码 → Dockerfile → build → push → run。
  • docker init 能生成遵循最佳实践的起点；docker build --check 能帮你发现问题。
  • 添加内容的指令产生新层，其余指令只产生元数据。
  • 构建上下文会被发送给构建器，用 .dockerignore 排除无关和敏感文件。
  • 多阶段构建把“构建环境”和“运行环境”分开，生产镜像只保留运行必需的产物。
  • Buildx 是构建客户端，BuildKit 是构建引擎；构建器可以在本地、容器里或云端，支持多架构构建。
  • 把最常变化的指令放在最后，最大化利用构建缓存。

✎ 动手练习

  1. 把本章 node-app 的 Dockerfile 改成“先 COPY package*.json 再 RUN npm ci 最后 COPY . .”的写法（不用 bind mount），修改 app.js 后重新构建，观察哪些步骤显示 CACHED。
  2. 为一个你熟悉的语言（Python/Go/Java）写一个多阶段 Dockerfile，比较单阶段和多阶段镜像的大小。
  3. 故意在 Dockerfile 里写 ENV API_KEY=secret123，构建后用 docker history --no-trunc 和 docker inspect 找出这个“秘密”。然后改用 --mount=type=secret 重做一遍。
  4. 如果你有 Docker Hub 账号，构建一个 linux/amd64,linux/arm64 双架构镜像并推送，在 Docker Hub 网页上查看它的 OS/ARCH 列表。

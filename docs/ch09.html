第 9 章

Compose 多容器应用

真实的应用很少只有一个容器：Web 前端、API、数据库、缓存……如果每个都手敲一长串 docker run，很快就会失控。 Docker Compose 让你用一个 YAML 文件描述整套应用，然后一条命令部署、一条命令销毁。

本章目标

  • 理解 Compose 解决的问题，以及它从 Fig 到 Compose v5 的演进
  • 读懂 Compose 文件的三大顶层键：services、networks、volumes
  • 用 docker compose up / down / ps / logs / stop / restart 管理整套应用
  • 理解 Compose 如何给资源命名，以及为什么 down 不删除卷
  • 掌握环境变量、健康检查依赖、watch、profiles 等现代用法

一句话概括

现代云原生应用由许多协同工作的小服务组成，这叫微服务应用。一个微服务应用可能包含：

Web 前端

用户看到的界面

订单 · 商品目录

业务逻辑服务

数据存储

数据库、缓存

日志 · 认证 · 授权

基础设施服务

与其拼凑复杂的脚本和冗长的 docker 命令，Compose 让你把整个应用描述在一个叫 Compose 文件的 YAML 文件里， 然后用 docker compose 命令部署和管理整个应用。Compose 文件因此成了应用的重要组成部分，应该放进 Git 等版本控制系统。

Compose 的历史

Docker 刚诞生时，一家叫 Orchard Labs 的公司做了一个叫 Fig 的工具：用一个简单的 YAML 文件定义复杂的多容器应用， 再用 fig 命令管理整个应用生命周期。Fig 在幕后读取 YAML 文件，调用相应的 Docker 命令。

Fig 实在太好用了，Docker 公司收购了 Orchard Labs，把 Fig 改名为 Docker Compose，命令也从 fig 变成了 docker-compose。 后来 Compose 用 Go 重写并并入了 docker CLI，成为 docker compose 子命令。

另外还有一个 Compose 规范，把 Compose 作为多容器应用的开放标准，由社区主导，独立于 Docker 的实现。 Docker Compose 是这个规范的参考实现。阅读规范是学习细节的好方法。

✨ 最新变化：Compose v5 与过时的写法
  • Compose v5（2025 年底发布，Docker Desktop 4.92 自带 v5.5.1）跳过了 v3、v4 这两个版本号，避免和老的 Compose 文件格式 “version 2.x / 3.x” 混淆。 v5 可以作为 SDK 嵌入第三方软件，并且移除了内置构建器，构建统一交给 Docker Bake。
  • 带横杠的 docker-compose（v1，Python 版）早已停止维护。原书清理步骤里的 docker-compose down 应写作 docker compose down。
  • Compose 文件顶部的 version: "3.8" 这一行已经过时，现在写了只会得到一个警告，直接删掉即可。

安装 Compose

所有现代 Docker 版本都预装了 Compose，不需要单独安装。验证一下：

示例应用

我们要部署的应用有两个服务、一个网络和一个卷：

web-fe 服务运行一个 Web 服务器，每收到一次网页请求，就让 redis 服务里的计数器加 1。 两个服务都连到 counter-net 网络并通过它通信。redis 服务挂载了 counter-vol 卷来保存数据。

Compose 文件

Compose 用 YAML 文件定义应用。默认文件名是 compose.yaml 或 compose.yml，也可以用 -f 指定其他文件。下面是本例的 Compose 文件：

networks:                    # ← 顶层键：定义网络
  counter-net:

volumes:                     # ← 顶层键：定义卷
  counter-vol:

services:                    # ← 顶层键（必填）：定义微服务
  web-fe:
    build: .
    deploy:
      replicas: 1
    command: python app/app.py
    ports:
      - target: 8080
        published: 5001
    networks:
      - counter-net

  redis:
    image: redis:alpine
    deploy:
      replicas: 1
    networks:
      counter-net:
    volumes:
      - type: volume
        source: counter-vol
        target: /data

文件有三个顶层键，每个下面是一段配置。还有更多顶层键（如 secrets、configs、models），但本例只用到这三个：

web-fe 服务

配置含义
web-fe:服务名。这个服务创建的所有容器名字里都会包含 “web-fe”
build: .用当前目录的 Dockerfile 为这个服务构建镜像
deploy.replicas: 1部署 1 个容器。也可以部署多个相同的副本，但本例映射了固定的主机端口，同一台主机上只能有一个容器绑定它
command: python app/app.py每个容器启动时执行的命令（会覆盖镜像里的 CMD；镜像里必须有 Python 和 app.py，Dockerfile 负责保证这点）
ports:把容器的 8080 端口（target）映射到主机的 5001 端口（published），等价于短写法 "5001:8080"
networks:把这个服务的容器连到 counter-net 网络。网络必须已存在，或在顶层 networks 键中定义

redis 服务

配置含义
image: redis:alpine从 Docker Hub 拉取 redis:alpine 镜像来启动容器
networks:同样连到 counter-net 网络
volumes:把 counter-vol 卷挂载到容器的 /data 目录 —— 这正是 Redis 存放数据的地方，所以删掉容器数据也不会丢
✨ 更正原书

原书正文里的 Compose 文件把卷挂到了 target: /app，但文字说明又说挂到 /data。Redis 的数据目录是 /data，作者 GitHub 仓库中的最新文件也已改为 /data，本教程以此为准。

服务之间如何找到对方？

两个服务都连在 counter-net 网络上，因此可以通过服务名互相解析。看看 app/app.py 的开头：

import time
import redis
from flask import Flask, render_template

app = Flask(__name__)
cache = redis.Redis(host='redis', port=6379)   # "redis" 就是 Compose 里的服务名

代码里直接写 host='redis'，Docker 内置的 DNS 会把它解析成 redis 容器的 IP（第 13 章会讲原理）。

docker compose up 是部署 Compose 应用最常用的方式：它读取当前目录下的 Compose 文件，执行部署所需的所有 Docker 操作 —— 构建和拉取镜像、创建网络和卷、启动所有容器。--detach（或 -d）表示在后台运行。

Compose 如何给资源命名

注意所有资源的名字都是项目名 + 资源名组合出来的：

资源类型Compose 文件里的名字实际名字
镜像web-fe（build）multi-container-web-fe
容器web-femulti-container-web-fe-1
容器redismulti-container-redis-1
网络counter-netmulti-container_counter-net
卷counter-volmulti-container_counter-vol

容器名末尾的数字是为多副本准备的：如果 web-fe 有 3 个副本，它们会叫 -1、-2、-3。 加上项目名前缀，同一台机器上就可以同时跑多个项目而互不冲突。想自定义项目名，用 -p（docker compose -p myapp up）或在文件顶部写 name: myapp。

现在用浏览器访问 localhost:5001，多刷新几次，看计数器增加 —— 这个数字保存在 redis 服务的卷里。

用 Compose 管理应用

记下你刷新了多少次，然后关闭应用：

$ docker compose down
[+] Running 3/3
 ✔ Container multi-container-redis-1      Removed        0.2s
 ✔ Container multi-container-web-fe-1     Removed        0.2s
 ✔ Network multi-container_counter-net    Removed        0.2s

$ docker volume ls
DRIVER    VOLUME NAME
local     multi-container_counter-vol      <<---- 卷还在！

Docker 删除了两个容器和网络，但没有删除卷。因为 Docker 知道卷里存的是重要数据，停止、重启应用时你多半想保留它们。 本例中 redis 把计数值存在卷里，所以重新部署后你会看到同样的数字。Docker 也保留了构建和拉取的镜像。 

$ docker compose up --detach
[+] Running 3/3
 ✔ Network multi-container_counter-net    Created        0.2s
 ✔ Container multi-container-redis-1      Started        0.2s
 ✔ Container multi-container-web-fe-1     Started        0.2s

这次启动快多了，因为镜像和卷都已存在。刷新浏览器，计数器会接着之前的数字继续。再看看其他几个管理命令：

现代 Compose 必会功能

环境变量与 .env 文件

Compose 会自动读取同目录下的 .env 文件，你可以在 Compose 文件里用 ${变量} 引用它，也可以把变量注入容器：

.env
REDIS_TAG=8-alpine
WEB_PORT=5001
compose.yaml
services:
  redis:
    image: redis:${REDIS_TAG:-alpine}
  web-fe:
    ports:
      - "${WEB_PORT}:8080"
    environment:
      REDIS_HOST: redis
    env_file: [ app.env ]

${REDIS_TAG:-alpine} 表示“变量没设置时用 alpine”。用 docker compose config 可以看到变量替换后的最终配置，排错非常有用。

⚠ .env 不要提交到 Git

.env 里常常有密码，记得把它加进 .gitignore 和 .dockerignore。敏感数据更好的做法是用 Compose 的 secrets（第 16 章）。

健康检查与启动顺序

depends_on 控制启动顺序。但简单写法只保证“redis 容器已启动”，不保证“redis 已经可以接受连接”。 结合 healthcheck 和 condition: service_healthy 才能真正等到依赖就绪： 

services:
  web-fe:
    build: .
    depends_on:
      redis:
        condition: service_healthy     # 等 redis 健康了再启动我
        restart: true                  # redis 重启时，我也跟着重启
  redis:
    image: redis:alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

docker compose watch：边改代码边看效果

开发时每改一行代码都要重新构建镜像太慢了。Compose 的 develop.watch 可以监视本地文件，自动同步到容器或触发重建：

services:
  web-fe:
    build: .
    develop:
      watch:
        - action: sync               # 改了 app/ 下的代码 → 直接同步进容器
          path: ./app
          target: /app/app
        - action: rebuild            # 改了依赖清单 → 重新构建镜像
          path: requirements.txt

$ docker compose watch             # 或 docker compose up --watch

profiles：可选服务

有些服务（比如调试工具、数据库管理界面）只在需要时才启动，可以给它们加 profile：

services:
  redis-insight:
    image: redis/redisinsight
    profiles: [ debug ]            # 默认 up 不会启动它

$ docker compose --profile debug up -d

功能写法用途
重启策略restart: unless-stopped容器崩溃或主机重启后自动拉起（第 7 章）

清理

停止并删除整个应用。--volumes 会删除应用的所有卷，--rmi all 会删除它的所有镜像：

$ docker compose down --volumes --rmi all
[+] Running 6/6
 ✔ Container multi-container-web-fe-1     Removed
 ✔ Container multi-container-redis-1      Removed
 ✔ Volume multi-container_counter-vol     Removed
 ✔ Image multi-container-web-fe:latest    Removed
 ✔ Image redis:alpine                     Removed
 ✔ Network multi-container_counter-net    Removed

命令速查

命令作用
docker compose up -d部署应用：构建/拉取镜像，创建网络、卷、容器；-f 指定文件，--build 强制重新构建
docker compose ps [-a]列出应用的容器、状态、命令和端口
docker compose logs -f [服务]查看 / 跟踪日志
docker compose top列出每个容器内的进程
docker compose exec 服务 sh在某个服务的容器里执行命令
docker compose stop / restart停止但不删除 / 重启（不会应用 Compose 文件的改动）
docker compose down [-v] [--rmi all]停止并删除容器和网络；可选删除卷和镜像
docker compose ls列出本机所有 Compose 项目
docker compose config显示合并、变量替换后的最终配置
docker compose watch监视文件变化，自动同步或重建

本章小结

  • Compose 让你在一个声明式 YAML 文件里定义多容器应用，然后用一条命令部署和管理它。
  • Compose 文件定义应用需要的服务、网络、卷、机密等；它也是非常好的应用文档，应该和代码一起放进版本控制。
  • Compose 用“项目名 + 资源名”给资源命名；down 默认保留卷和镜像，数据不会因为重新部署而丢失。
  • 同一网络上的服务可以直接用服务名互相访问。
  • 现代 Compose 还提供 .env 变量、健康检查依赖、watch 热更新、profiles 等功能。

✎ 动手练习

  1. 部署本章的计数器应用，刷新几次，然后 docker compose down 再 up，确认计数没丢；再用 down -v 然后 up，确认计数归零。
  2. 给 redis 服务加上本章的 healthcheck，给 web-fe 加上 condition: service_healthy，用 docker compose ps 观察 redis 的 STATUS 从 (health: starting) 变成 (healthy)。
  3. 把 web-fe 的端口改成从 .env 文件读取，运行 docker compose config 确认替换结果。
  4. 配置 develop.watch，运行 docker compose watch，修改 app/templates/index.html 的文字，刷新浏览器看效果。

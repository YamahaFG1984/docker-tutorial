第 20 章

部署到服务器

第 18 章在本地把应用跑了起来，第 19 章让 CI 自动构建出签过名的镜像。最后一公里：把它放到一台真正的服务器上，用自己的域名、带 HTTPS 对外提供服务， 并且能一条命令更新、一条命令回滚。本章以一台云主机为例，从零走完这条路，顺带学会用 docker context 在本机直接管理远程服务器。

本章目标

  • 理解单机生产部署的整体结构：DNS、防火墙、反向代理、应用、数据库
  • 安全地准备一台 Docker 服务器，避开“Docker 绕过防火墙”这个大坑
  • 用 docker context 通过 SSH 在本机操作远程 Docker 引擎
  • 用 Caddy 做反向代理，自动申请和续期 HTTPS 证书
  • 按镜像标签部署，实现可预期的更新与秒级回滚
  • 让 CI 在构建完成后自动部署，并做好日志、备份等日常运维

目标架构

★ 三条原则
  • 只有反向代理对外。应用、数据库、缓存都不发布端口，只在内部网络里通信。
  • 服务器上不构建镜像。镜像由 CI 构建、扫描、签名后推到仓库，服务器只负责拉取和运行。这样线上跑的一定是经过验证的那个镜像。
  • 按不可变的标签部署。用 sha-3f2a9c1 或版本号，而不是 latest，回滚时才知道该回到哪里。
ⓘ 什么时候不适合单机部署

单台服务器简单、便宜、够大多数小型项目使用。当你需要多台机器之间的高可用、自动扩缩容时，再考虑 Swarm（第 12 章）或 Kubernetes，或者直接使用 Cloud Run、ECS 这类托管平台。本章的很多做法（反向代理、健康检查、按标签部署、备份）在那些平台上同样适用。

准备服务器

1. 安装 Docker 并创建部署用户

在云厂商那里开一台 Ubuntu 服务器，用 SSH 密钥登录，然后按第 3 章的方法从官方 apt 源安装 Docker Engine。接着创建一个专门用来部署的用户：

$ sudo adduser --disabled-password --gecos "" deploy
$ sudo usermod -aG docker deploy
$ sudo mkdir -p /home/deploy/.ssh
$ sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/      # 复用你的公钥，也可以单独放一个
$ sudo chown -R deploy:deploy /home/deploy/.ssh
⚠ 记住第 3 章的警告

docker 组的成员等同于 root。deploy 用户的 SSH 私钥要像 root 密码一样保管；给 CI 用的密钥最好单独生成一把，方便随时吊销。

2. 配置防火墙 —— 以及一个大坑

先在云厂商的安全组里只放行 22、80、443 三个端口。如果还想在服务器上用 ufw：

$ sudo ufw allow OpenSSH
$ sudo ufw allow 80/tcp
$ sudo ufw allow 443/tcp
$ sudo ufw allow 443/udp        # HTTP/3
$ sudo ufw enable
⚠ Docker 发布的端口会绕过 ufw

Docker 通过自己的 iptables（或 nftables）规则把发布的端口转发给容器，这些流量走的是 FORWARD 路径，不会经过 ufw 的 INPUT 规则。 结果是：你以为 ufw 挡住了 5432，其实 -p 5432:5432 发布的数据库对全世界开放 —— 这是真实发生过无数次的数据泄露原因。

对策：不需要对外的服务干脆不发布端口；确实要在服务器本机访问，就绑定到回环地址 127.0.0.1:5432:5432；再加上云厂商的安全组作为第二道防线（它在服务器之外，Docker 改不了）。

3. 配置 Docker 守护进程

给整台服务器设置日志轮转（第 13 章），并开启 live-restore（第 5 章），这样升级 Docker 时容器不会停：

{
  "log-driver": "local",
  "log-opts": { "max-size": "10m", "max-file": "5" },
  "live-restore": true
}

$ sudo systemctl restart docker

4. 配置域名

在域名服务商那里添加一条 A 记录：todo.example.com → 服务器公网 IP（有 IPv6 的话再加 AAAA 记录）。可以用 dig +short todo.example.com 确认是否已经生效。HTTPS 证书的自动申请依赖这一步。

docker context：在本机管理远程服务器

回忆第 2 章：docker 命令只是一个客户端，它把命令变成 API 请求发给引擎。这个引擎不一定在本机 —— docker context 让你把客户端指向一台远程服务器，通过 SSH 隧道把 API 请求发过去。 

# 先确认能用密钥免密登录
$ ssh deploy@todo.example.com docker version

# 创建并查看上下文
$ docker context create prod --docker "host=ssh://deploy@todo.example.com"
$ docker context ls
NAME        DESCRIPTION                               DOCKER ENDPOINT
default *   Current DOCKER_HOST based configuration   unix:///var/run/docker.sock
prod                                                  ssh://deploy@todo.example.com

# 用法一：单条命令临时指定
$ docker --context prod ps

# 用法二：切换默认上下文（记得切回来！）
$ docker context use prod
$ docker ps                     # 现在操作的是服务器
$ docker context use default
⚠ 使用远程上下文时要清楚“东西在哪一边”
  • 在本机：Compose 文件、.env / env_file、docker login 保存的凭据、docker build 的构建上下文（会通过 SSH 上传）。
  • 在服务器：容器、镜像、命名卷，以及绑定挂载的路径 —— ./Caddyfile:/etc/caddy/Caddyfile 找的是服务器上的 ./Caddyfile，而不是你电脑上的！这是远程上下文最常见的坑。
  • 最危险的是忘了自己在哪个上下文：以为在清理本机，结果 docker system prune -a 打在了生产服务器上。推荐总是用 --context prod 显式指定，而不是 context use。

生产环境的 Compose 文件

为了避开绑定挂载的问题，我们把 Caddy 的配置直接内联写进 Compose 文件（Compose 的 configs 支持 content 字段）。 这样整个部署只需要本机的两个文件：compose.prod.yaml 和 .env.prod。 

name: todo

services:
  caddy:
    image: caddy:2.11
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"                   # HTTP/3
    configs:
      - source: caddyfile
        target: /etc/caddy/Caddyfile
    volumes:
      - caddy_data:/data                # 证书！必须持久化
      - caddy_config:/config
    depends_on:
      api:
        condition: service_healthy

  api:
    image: ghcr.io/you/todo:${TAG:?请设置 TAG}   # 按不可变标签部署
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      REDIS_URL: redis://cache:6379
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 20s
    depends_on:
      db:
        condition: service_healthy
    deploy:
      resources:
        limits: { memory: 512m }

  db:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      retries: 10

  cache:
    image: redis:8-alpine
    restart: unless-stopped

configs:
  caddyfile:
    content: |
      todo.example.com {
        encode zstd gzip
        reverse_proxy api:3000
      }

volumes:
  pgdata:
  caddy_data:
  caddy_config:
deploy/.env.prod（不提交到 Git）
TAG=sha-3f2a9c1
POSTGRES_USER=todo
POSTGRES_PASSWORD=一个很长的随机密码
POSTGRES_DB=todo
和第 18 章开发配置的区别
  • image: 代替 build:
  • 只有 caddy 发布端口
  • 每个服务都有 restart
  • 加了健康检查和内存上限
  • 没有调试端口、没有 watch

Caddy 帮你做了什么

💡 还需要一个健康检查接口

api 的健康检查访问 /health，所以应用里要有这样一个接口，最好顺便检查一下数据库连接。 另外，wget 在 alpine 基础镜像里自带；如果你用的是 distroless 这类没有 shell 和工具的镜像，就需要在应用里内置一个健康检查子命令（第 21 章 Go 部分有例子）。

第一次部署

如果镜像是私有的，先让远程引擎能拉取它。docker login 的凭据保存在本机，拉取时会随请求一起发给服务器：

$ cd deploy
$ echo "$GHCR_TOKEN" | docker login ghcr.io -u you --password-stdin

$ docker --context prod compose -f compose.prod.yaml --env-file .env.prod pull
$ docker --context prod compose -f compose.prod.yaml --env-file .env.prod up -d --wait
[+] Running 8/8
 ✔ Network todo_default        Created
 ✔ Volume "todo_pgdata"        Created
 ✔ Volume "todo_caddy_data"    Created
 ✔ Container todo-db-1         Healthy
 ✔ Container todo-cache-1      Started
 ✔ Container todo-api-1        Healthy
 ✔ Container todo-caddy-1      Started

--wait 会一直等到所有服务都进入 running / healthy 状态才返回；如果某个服务的健康检查一直不过，命令会以失败退出 —— 这对后面的自动化部署非常重要。 打开 https://todo.example.com，浏览器地址栏已经有小锁了。

ⓘ 另一种做法：在服务器上放一个部署目录

不想用远程上下文也完全可以：把 compose.prod.yaml、.env.prod（和 Caddyfile 等文件）用 scp 或 Git 放到服务器的 /srv/todo， 然后 ssh deploy@服务器 "cd /srv/todo && docker compose pull && docker compose up -d --wait"。这种方式绑定挂载的路径不会出错，缺点是配置文件要同步两份。

更新与回滚

因为 Compose 文件里写的是 ${TAG}，发布新版本就是“换一个标签，再 up 一次”。Compose 只会重建镜像变化了的服务，数据库、缓存和 Caddy 不受影响：

# 发布新版本
$ TAG=sha-8b17e0d docker --context prod compose -f compose.prod.yaml --env-file .env.prod up -d --wait

# 新版本有问题？立即回滚到上一个标签
$ TAG=sha-3f2a9c1 docker --context prod compose -f compose.prod.yaml --env-file .env.prod up -d --wait

命令行里设置的 TAG 优先级高于 --env-file 里的值。更规范的做法是把当前线上的标签写回 .env.prod 并提交到一个私有的部署仓库，这样随时能看出“线上跑的是哪个版本、什么时候改的”。

⚠ 数据库迁移不能随便回滚

应用镜像可以秒级回滚，但如果新版本执行了破坏性的数据库迁移（比如删了一列），旧版本的代码就可能跑不起来。 稳妥的做法是让迁移向后兼容：先加新列、新旧代码都能工作，确认稳定后再在下一个版本删掉旧列。迁移可以用一次性任务执行： docker --context prod compose … run --rm api npm run migrate。

会有停机吗？

docker compose up 替换容器时是“先停旧的、再起新的”，中间会有几秒钟不可用，对大多数小项目来说可以接受。 如果需要零停机，可以在单台服务器上初始化一个单节点 Swarm，用 docker stack deploy 配合 update_config: order: start-first（先启动新副本、健康后再停旧副本，见第 12 章）， 或者直接迁移到 Kubernetes / 托管平台。

让 CI 自动部署

在第 19 章的工作流后面加一个 deploy 作业：镜像构建、扫描、签名都通过之后，CI 通过 SSH 上下文把新标签部署到服务器。

  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production                # 可在仓库设置里为它加人工审批
    steps:
      - uses: actions/checkout@v7

      - name: 配置 SSH
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.DEPLOY_SSH_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          echo "${{ secrets.DEPLOY_KNOWN_HOSTS }}" > ~/.ssh/known_hosts

      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: 部署
        working-directory: deploy
        env:
          TAG: sha-${{ github.sha }}
          POSTGRES_USER: ${{ secrets.POSTGRES_USER }}
          POSTGRES_PASSWORD: ${{ secrets.POSTGRES_PASSWORD }}
          POSTGRES_DB: ${{ secrets.POSTGRES_DB }}
        run: |
          docker context create prod --docker "host=ssh://deploy@todo.example.com"
          docker --context prod compose -f compose.prod.yaml pull
          docker --context prod compose -f compose.prod.yaml up -d --wait
  • DEPLOY_SSH_KEY：专门给 CI 生成的一把私钥（公钥加到服务器 deploy 用户的 authorized_keys）；
  • DEPLOY_KNOWN_HOSTS：在本机运行 ssh-keyscan todo.example.com 得到的结果，用来防止中间人攻击，不要用 StrictHostKeyChecking no 偷懒；
  • 数据库密码等从 GitHub Secrets 以环境变量传入，Compose 会用它们替换 ${…}；
  • 注意 metadata-action 的 type=sha 默认生成短 SHA（7 位）。这里用完整 SHA 的话，要在第 19 章的标签规则里写成 type=sha,format=long，两边保持一致。

日常运维

查看状态和日志

$ docker --context prod compose -p todo ps
$ docker --context prod compose -p todo logs -f --tail 100 api
$ docker --context prod stats --no-stream

只是查看状态的话，不需要 Compose 文件，用 -p todo 指定项目名即可。

备份数据库

卷里的数据是整套系统里唯一不能重新生成的东西。至少要有定时的逻辑备份，并且备份要存到服务器之外：

# 在服务器上：每天凌晨 3 点导出一次（crontab -e）
0 3 * * * docker exec todo-db-1 pg_dump -U todo todo | gzip > /backup/todo-$(date +\%F).sql.gz

# 恢复
$ gunzip -c todo-2026-09-22.sql.gz | docker exec -i todo-db-1 psql -U todo todo
⚠ 没有恢复演练过的备份，等于没有备份

把 /backup 同步到对象存储（S3、OSS 等）或另一台机器；定期在测试环境里真的恢复一次，确认备份文件是完整可用的。

保持更新

  • 操作系统：开启 Ubuntu 的 unattended-upgrades 自动安装安全更新；
  • Docker：定期 sudo apt-get upgrade（有 live-restore，容器不会中断）；
  • 镜像：基础镜像的漏洞靠重新构建修复。让 Renovate / Dependabot 定期提交升级 PR，经过 CI 后自动部署；Postgres、Redis、Caddy 这些第三方镜像也要定期升级小版本；
  • 清理：旧镜像会慢慢占满磁盘，定期 docker image prune -a --filter "until=720h" 清掉一个月前的未使用镜像（回滚需要的最近几个版本会保留）。

最基本的监控

  • 用一个外部的在线监测服务（UptimeRobot、Better Stack 等）每分钟访问一次 https://todo.example.com/health，挂了立刻发通知；
  • restart: unless-stopped 负责进程崩溃后自动拉起，健康检查负责发现“进程还在但已经不工作”；
  • 想要更完整的指标和日志，可以再部署 Prometheus + Grafana、Loki 等，或者使用云厂商的监控服务。

另一种反向代理：Traefik

Traefik 是另一个流行的选择。它通过监听 Docker API 自动发现容器，路由规则写在各个服务的 labels 上，适合服务很多、经常增减的场景： 

services:
  traefik:
    image: traefik:v3.7
    command:
      - --providers.docker=true
      - --providers.docker.exposedbydefault=false
      - --entrypoints.web.address=:80
      - --entrypoints.web.http.redirections.entrypoint.to=websecure
      - --entrypoints.websecure.address=:443
      - --certificatesresolvers.le.acme.email=you@example.com
      - --certificatesresolvers.le.acme.storage=/letsencrypt/acme.json
      - --certificatesresolvers.le.acme.httpchallenge.entrypoint=web
    ports: ["80:80", "443:443"]
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - letsencrypt:/letsencrypt

  api:
    image: ghcr.io/you/todo:${TAG}
    labels:
      - traefik.enable=true
      - traefik.http.routers.api.rule=Host(`todo.example.com`)
      - traefik.http.routers.api.entrypoints=websecure
      - traefik.http.routers.api.tls.certresolver=le
      - traefik.http.services.api.loadbalancer.server.port=3000

本章小结

  • 单机生产部署的典型结构：DNS → 防火墙 → 反向代理（唯一对外）→ 应用 → 数据库/缓存（只在内部网络）。
  • Docker 发布的端口会绕过 ufw：不需要对外的服务就不要发布端口，并用云安全组做第二道防线。
  • docker context 通过 SSH 让本机 CLI 操作远程引擎；注意绑定挂载路径指向服务器，危险操作时显式写 --context。
  • Caddy 一行配置完成反向代理和自动 HTTPS，证书卷必须持久化；Traefik 适合服务多、需要自动发现的场景。
  • 按不可变标签部署，更新和回滚都是“换标签 + up -d --wait”；数据库迁移要向后兼容。
  • CI 在构建、扫描、签名通过后自动部署；日常运维重点是日志、备份、更新和监控。

✎ 动手练习

  1. 租一台最便宜的云服务器（或用本机的 Multipass 虚拟机代替），创建 deploy 用户，并在本机用 docker context create 连上它。
  2. 在服务器上用 -p 6379:6379 启动一个 redis，开启 ufw 且不放行 6379，然后从另一台机器 nc -zv 服务器IP 6379，亲眼验证“Docker 绕过 ufw”。验证完立刻删掉这个容器。
  3. 用本章的 compose.prod.yaml 部署第 18 章的 todo 应用；没有域名的话，把 Caddyfile 的站点地址改成 :80，先用 HTTP 验证。
  4. 部署两个不同的标签，练习一次回滚，并用 docker --context prod compose -p todo ps 确认版本。
  5. 写一个备份 cron 任务，然后把备份恢复到一个新的 Postgres 容器里，确认数据完整。

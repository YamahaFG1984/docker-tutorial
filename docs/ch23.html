第 23 章

从 Compose 走向 Kubernetes

你已经会用 Compose 管理一台机器上的应用，用 Swarm 管理一个小集群。Kubernetes 是容器编排的行业标准， 它的核心思想你其实已经学过了：期望状态、调和、服务、滚动更新（第 12 章）。本章做一件具体的事： 把第 9、12 章的计数器应用从 Compose 翻译成 Kubernetes，在本地集群上跑起来，并讲清楚每个概念对应什么、有哪些坑。

本章目标

  • 判断什么时候需要 Kubernetes，什么时候 Compose 就够了
  • 建立 Compose 与 Kubernetes 的概念对照表
  • 理解 Kubernetes 的架构，以及它和 Docker 共用的那部分（containerd、runc、OCI 镜像）
  • 用 kind 创建本地集群，编写并部署 Deployment、Service、PVC
  • 体验自我修复、扩缩容、滚动更新与回滚
  • 了解对外暴露服务的方式，以及 Ingress NGINX 退役后的 Gateway API
  • 知道 Kompose 自动转换能帮到哪里、又会在哪里坑你
ⓘ 关于本章示例

本章基于 2026 年 9 月的版本：Kubernetes 1.37、kind v0.33、Gateway API v1.6。文中的 Kubernetes 清单都已用 kubeconform 按 Kubernetes 1.37 的 API 规范严格校验通过；Kompose 的输出是实际运行 Kompose 1.38 得到的。但它们没有在真实集群上运行过 —— 请在自己的 kind 集群上动手验证，这也是本章的练习。

什么时候需要 Kubernetes

先说一句可能出乎意料的话：很多项目并不需要 Kubernetes。它强大，但也复杂，需要专门的知识和运维投入。

当你遇到下面这些需求时，Kubernetes 就值得认真考虑了：

  • 几十个服务、多个团队各自发布，需要统一的部署方式和权限隔离；
  • 流量波动大，需要按 CPU、请求量自动扩缩容；
  • 需要成熟的生态：服务网格、GitOps、策略引擎、各种 Operator；
  • 公司已经有 Kubernetes 平台团队，或者使用云厂商的托管 Kubernetes（EKS、GKE、AKS 等）。

概念对照：Compose → Kubernetes

好消息是，你在 Compose 和 Swarm 里学到的几乎每个概念，在 Kubernetes 里都有对应物。

还有几处不是一一对应的地方，迁移时最容易出错：

ComposeKubernetes注意
networks没有直接对应集群内所有 Pod 默认处在一个扁平网络里、互相可达。要隔离，用 NetworkPolicy（需要网络插件支持）
depends_on没有对应Kubernetes 不保证启动顺序。应用要能自己重试连接依赖；再配合就绪探针，依赖没准备好的 Pod 不会接收流量
entrypoint / commandcommand / args名字错位了！Compose 的 command 覆盖镜像的 CMD，对应 Kubernetes 的 args；Kubernetes 的 command 覆盖的是 ENTRYPOINT（下文有真实的坑）
build没有对应Kubernetes 只运行镜像，不构建。镜像要先由 CI 构建并推到仓库（第 19 章）
restart控制器 + restartPolicyPod 里的容器崩溃会被 kubelet 重启；整个 Pod 没了，由 Deployment 创建新的

Kubernetes 的架构

  • API Server：一切操作的唯一入口。kubectl 之于 API Server，就像 docker CLI 之于 Docker API（第 2 章）。
  • etcd：保存集群的期望状态 —— Swarm 的集群存储也基于 etcd 的 Raft 实现（第 16 章）。
  • Scheduler：为新 Pod 挑选合适的节点。
  • Controllers：一组调和循环，不停地让观察状态追上期望状态（第 12 章图 12-4 的思想）。
  • kubelet：每个节点上的代理，负责按要求启动和监控 Pod，它通过 CRI 接口调用containerd，containerd 再通过 shim 调用 runc。
★ 你的 Docker 镜像可以原封不动地在 Kubernetes 上运行

第 1 章说过，Kubernetes 早就不再通过 Docker 运行容器，而是直接使用 containerd。但这完全不影响你： Docker 构建的镜像符合 OCI 标准（第 2 章），containerd 拉取、runc 运行，和在 Docker 里是同一套机制。 你在前面 22 章学到的镜像、分层、Dockerfile、多阶段构建、瘦身、签名，在 Kubernetes 里全部适用。

搭建本地集群

学习 Kubernetes 不需要云服务器，在自己电脑上就能跑一个完整的集群：

工具原理适合

⚠ 磁盘和内存

kind 的节点镜像解压后约 1 GB，集群运行时至少需要 2 GB 内存。在资源紧张的机器上创建前先 df -h 看看剩余空间。用完后 kind delete cluster --name counter 会删除整个集群。

翻译成 Kubernetes，会变成下面这些对象：

把清单放在一个 k8s/ 目录里，文件名前的数字只是为了让它们按顺序应用。先是命名空间：

apiVersion: v1
kind: Namespace
metadata:
  name: counter

然后是 redis：一个 PVC（相当于 Compose 的命名卷）、一个 Deployment、一个 Service：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: redis-data
  namespace: counter
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: counter
spec:
  replicas: 1
  strategy:
    type: Recreate                 # 卷只能挂到一个 Pod 上：先停旧的再起新的
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:8-alpine
          ports:
            - containerPort: 6379
          volumeMounts:
            - name: data
              mountPath: /data
          readinessProbe:
            exec:
              command: ["redis-cli", "ping"]
            periodSeconds: 5
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits: { memory: 256Mi }
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: redis-data
---
apiVersion: v1
kind: Service
metadata:
  name: redis                      # 这个名字就是 DNS 名：应用里连接 redis:6379
  namespace: counter
spec:
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379

最后是 web-fe：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-fe
  namespace: counter
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0            # 更新时不减少可用副本
      maxSurge: 1                  # 每次多起 1 个新副本
  selector:
    matchLabels:
      app: web-fe
  template:
    metadata:
      labels:
        app: web-fe
    spec:
      containers:
        - name: web-fe
          image: nigelpoulton/ddd-book:swarm-app
          ports:
            - containerPort: 8080
          readinessProbe:          # 就绪了才接收流量
            tcpSocket:             # 这个示例应用没有 /health，访问 / 会让计数器加 1
              port: 8080
            periodSeconds: 5
          livenessProbe:           # 卡死了就重启
            tcpSocket:
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 10
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits: { memory: 256Mi }
---

metadata:
  name: web-fe
  namespace: counter
spec:
  selector:
    app: web-fe
  ports:

逐项解读

写法含义
selector.matchLabels 与 template.metadata.labelsDeployment 靠标签认领“自己的” Pod，两者必须一致。Service 也是靠标签选择 Pod 的
strategy: Recreate（redis）ReadWriteOnce 的卷同一时间只能挂到一个节点上，所以更新时先停旧 Pod 再起新 Pod
maxUnavailable: 0、maxSurge: 1（web-fe）滚动更新时先多起一个新 Pod，就绪后再停一个旧的，始终保持 3 个可用 —— 第 12 章 Swarm update_config 的对应物
readinessProbe探测通过前，Service 不会把流量转给这个 Pod。它部分替代了 Compose 的 depends_on
livenessProbe探测失败就重启容器，处理“进程还在但已经卡死”的情况
resources.requests / limitsrequests 是调度依据（节点要有这么多空闲资源才会被选中），limits 是上限（第 16 章的 cgroups）
Service 名 redis集群 DNS 会解析 redis（同命名空间）或 redis.counter.svc.cluster.local（完整名），所以应用代码一行都不用改
⚠ 一个真实的迁移坑：command 覆盖了 ENTRYPOINT

第 12 章的 Compose 文件里写着 command: python app.py。直接翻译成 Kubernetes 的 command: ["python", "app.py"]，Pod 会一直 CrashLoopBackOff。 查一下镜像配置就明白了：它的 ENTRYPOINT 是 ["python", "app/app.py"]，工作目录是 /app。

  • 在 Compose 里，command 只替换 CMD，于是变成 python app/app.py python app.py，后面两个多余参数被程序忽略，碰巧能跑；
  • 在 Kubernetes 里，command 替换的是 ENTRYPOINT，于是执行 python app.py，而 /app/app.py 并不存在。

本章的清单干脆不写 command，直接用镜像自带的 ENTRYPOINT。迁移时可以用 docker buildx imagetools inspect 镜像 --format '{{json .Image}}' 在不拉取镜像的情况下查看它的 ENTRYPOINT 和 CMD。

ⓘ 关于探针，以及 M 系列 Mac
  • 这个示例应用没有专门的健康检查接口，而访问 / 会让计数器加 1，所以两个探针都用 TCP 端口检查。真实项目应该提供一个没有副作用的 /health（第 20 章），就绪探针用 httpGet 请求它，这样还能顺便检查数据库连接。
  • nigelpoulton/ddd-book:swarm-app 只有 amd64 版本。在 Apple 芯片的 Mac 上可能需要借助模拟运行；也可以用第 9 章的源码自己构建一个 arm64 镜像，再用 kind load docker-image 镜像名 --name counter 直接载入集群。

💡 出问题时怎么查

和第 17 章的思路一样，只是命令换了：

$ kubectl get pods -n counter                  # 看状态（相当于 docker ps）
$ kubectl describe pod -n counter 名字         # 看事件：拉取失败、调度失败、探针失败……
$ kubectl logs -n counter deploy/web-fe        # 看日志（相当于 docker logs）
$ kubectl exec -it -n counter deploy/web-fe -- sh    # 进容器（相当于 docker exec）

最常见的几种状态：ImagePullBackOff（镜像名写错或没有权限）、CrashLoopBackOff（容器反复退出，看 logs）、Pending（没有节点能满足资源请求，或 PVC 绑定不上，看 describe）。

自我修复、扩缩容、更新与回滚

这些操作你在第 12 章用 Swarm 做过一遍，现在换成 Kubernetes：

# 自我修复：删掉一个 Pod，Deployment 立刻补一个新的
$ kubectl delete pod -n counter web-fe-7c9b6d5f4-4tq2m
$ kubectl get pods -n counter          # 马上出现一个新名字的 Pod

# 扩缩容
$ kubectl scale deployment/web-fe -n counter --replicas=5

# 滚动更新到新版本镜像
$ kubectl set image deployment/web-fe -n counter web-fe=nigelpoulton/ddd-book:swarm-appv2
$ kubectl rollout status deployment/web-fe -n counter
deployment "web-fe" successfully rolled out

# 有问题？一条命令回滚到上一个版本
$ kubectl rollout undo deployment/web-fe -n counter
$ kubectl rollout history deployment/web-fe -n counter
★ 同样的教训：声明式地管理

kubectl scale、kubectl set image 这些命令式操作，和第 12 章 Swarm 的 docker service scale 有同样的问题： 集群状态和 Git 里的 YAML 会出现“配置漂移”。正式环境中应该修改 YAML 文件、提交到 Git、再 kubectl apply； 更进一步，用 Argo CD 或 Flux 这类 GitOps 工具，让集群自动与 Git 仓库保持一致。

配置与机密

Compose 里的 environment 和 secrets，在 Kubernetes 里对应 ConfigMap 和 Secret：

$ kubectl create configmap web-config -n counter --from-literal=LOG_LEVEL=info
$ kubectl create secret generic db-cred -n counter --from-literal=password='S3cr3t!'

          envFrom:
            - configMapRef:
                name: web-config              # 所有键都变成环境变量
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-cred
                  key: password
⚠ Secret 默认只是 base64 编码，不是加密

任何有权限读取 Secret 的人都能直接解码出明文，而且绝对不能把 Secret 的 YAML 提交到 Git。 生产环境通常会开启 etcd 静态加密、用 RBAC 限制读取权限，并借助 External Secrets Operator、Sealed Secrets 或云厂商的密钥服务来管理机密。

对外暴露服务

Service 有几种类型，决定了它能从哪里被访问：

✨ 最新变化：Ingress NGINX 已退役，改用 Gateway API

过去几年，对外暴露 HTTP 服务最常见的做法是 Ingress 资源配合 ingress-nginx 控制器，大量教程至今还这么写。 但由于反复出现的安全问题，Kubernetes 项目宣布退役 ingress-nginx：它已于 2026 年 3 月 24 日正式结束维护，仓库已归档，不会再有安全修复。

官方指定的继任者是 Gateway API，它用 GatewayClass、Gateway、HTTPRoute 等角色清晰的资源，取代了过去依赖各家控制器私有注解的做法。 Envoy Gateway、NGINX Gateway Fabric、Istio、Cilium、Traefik、kgateway 等都实现了它。已有的 Ingress 配置可以用官方工具 ingress2gateway 1.0 转换。 注意：退役的是 ingress-nginx 这个控制器，Ingress API 本身仍然存在，其他实现也仍可使用。

用 Gateway API 暴露 web-fe，需要先在集群里安装一个 Gateway 实现（以 Envoy Gateway 为例，按其官方文档用 Helm 安装后会提供名为 eg 的 GatewayClass），然后：

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: web
  namespace: counter
spec:
  gatewayClassName: eg             # 由你安装的 Gateway 实现提供，这里以 Envoy Gateway 为例
  listeners:
    - name: http
      protocol: HTTP
      port: 80
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web-fe
  namespace: counter
spec:
  parentRefs:
    - name: web
  hostnames: ["counter.example.com"]
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: web-fe
          port: 80

Kompose：自动转换能做到什么程度

Kompose 是 Kubernetes 官方的转换工具，能把 Compose 文件直接转换成 Kubernetes 清单。对前面的 Compose 文件实际运行一次（Kompose 1.38）：

$ kompose convert -f compose.yaml -o out/
WARN Service "redis" won't be created because 'ports' is not specified
INFO Kubernetes file "out/web-fe-service.yaml" created
INFO Kubernetes file "out/redis-deployment.yaml" created
INFO Kubernetes file "out/counter-vol-persistentvolumeclaim.yaml" created
INFO Kubernetes file "out/web-fe-deployment.yaml" created

生成的 4 个文件都能通过 Kubernetes 的格式校验，但仔细看第一行警告：

⚠ 格式合法，但跑不起来

Kompose 没有给 redis 生成 Service，因为 Compose 文件里 redis 没有写 ports —— 在 Compose 里，同一网络上的服务本来就不需要 ports 也能互相访问；但在 Kubernetes 里，没有 Service 就没有 redis 这个 DNS 名， web-fe 会一直报“连接不上 redis”。修复方法：在 Compose 文件的 redis 下加上 expose: ["6379"] 或 ports 再转换，或者手动补一个 Service。

把 Kompose 的输出和本章手写的清单对比一下：

Kompose 生成本章手写
redis 的 Service缺失（应用连不上数据库）有
web-fe 的 Service 端口5001 → 8080（照搬主机端口，名字叫 "5001"）80 → 8080
命名空间没有（部署到 default）counter
健康探针没有就绪 + 存活探针
资源请求和上限没有有
滚动更新策略默认值maxUnavailable: 0
redis 更新策略Recreate ✓（识别出了卷）Recreate
标签io.kompose.service + 一堆注解简洁的 app

结论：Kompose 适合用来快速得到一个起点、了解对应关系，但生成的清单一定要人工审查和补全。对于正式项目，建议手写清单（或者用 Helm / Kustomize 管理），而不是依赖一次性转换。

本章小结

  • Kubernetes 很强大但也复杂，需求简单时 Compose、Swarm 或托管平台可能是更好的选择。
  • Compose 的概念大多能对应到 Kubernetes：服务 → Deployment + Service，卷 → PVC，环境变量 → ConfigMap，机密 → Secret，健康检查 → 探针。
  • 没有直接对应的要特别注意：depends_on（要靠重试和就绪探针）、networks（默认扁平网络）、build（先由 CI 构建），以及名字错位的 command/args。
  • Kubernetes 的节点用 containerd + runc 运行容器，你的 Docker 镜像原封不动就能运行。
  • kind 让你在本地用 Docker 容器跑一个完整的 Kubernetes 集群。
  • 对外暴露 HTTP 服务应该使用 Gateway API；ingress-nginx 已于 2026 年 3 月退役。
  • Kompose 能快速给出起点，但会漏掉东西（本例中漏掉了 redis 的 Service），一定要人工审查。

✎ 动手练习

  1. 用 kind 创建集群，部署本章的清单，用 port-forward 访问计数器应用。
  2. 刷新几次页面后执行 kubectl delete pod -n counter -l app=redis，等新的 redis Pod 起来后再刷新，确认计数没有丢失（PVC 的作用）。再删除命名空间重建一次，观察计数是否归零。
  3. 故意在 web-fe 的容器定义里加上 command: ["python", "app.py"] 重新 apply，用 kubectl get pods 和 kubectl logs 观察 CrashLoopBackOff，然后改成 args 看看会怎样。
  4. 用 kubectl set image 更新到 swarm-appv2，同时在另一个终端运行 kubectl get pods -n counter -w 观察滚动更新过程，然后 rollout undo。
  5. 对第 9 章的 Compose 文件运行 kompose convert，找出生成的清单里还缺什么，并补全它。

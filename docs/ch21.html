第 21 章

按语言写 Dockerfile

第 8 章讲了 Dockerfile 的通用原理，但真正动手时，每种语言都有自己的“坑”：Node 的信号处理、Python 的依赖编译、Go 的静态链接、Java 的内存设置…… 本章给出 Node.js、Python、Go、Java 四个生产级模板，逐行解释为什么这么写，以及各自最容易踩的坑。你可以直接拿去用。

本章目标

  • 掌握所有语言通用的 Dockerfile 骨架和检查清单
  • 根据语言和需求选择基础镜像：完整版、slim、alpine、distroless、scratch
  • 写出 Node.js、Python（uv）、Go、Java（Spring Boot）的生产级 Dockerfile
  • 避开各语言特有的坑：信号、musl、CGO、JVM 内存等
ⓘ 版本说明

本章模板使用 2026 年 9 月的版本：Node.js 24（当前 Active LTS）、Python 3.14、Go 1.27、Java 25（Eclipse Temurin，LTS）。前面章节里的 node:22 等示例依然可用，新项目建议选当前的 LTS 版本。

选择基础镜像

⚠ alpine 不总是最好的选择

alpine 使用 musl libc，而绝大多数预编译的二进制（Python wheel、Node 原生模块、各种 SDK）是按 glibc 编译的。 在 alpine 上它们可能没有现成的包，只能从源码编译 —— 构建变慢、需要装编译器，偶尔还有细微的行为差异（DNS 解析、线程栈大小）。 经验法则：Go 这类静态二进制随便选；Python、带原生模块的 Node 项目优先 slim。 另外别忘了第 16 章的 Docker Hardened Images，它提供各语言的加固版基础镜像，可以直接替换。

Node.js

# syntax=docker/dockerfile:1
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev                      # 只装生产依赖

FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci   # 包括 TypeScript 等开发依赖
COPY . .
RUN npm run build                          # 例如 tsc 输出到 dist/

FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=deps  --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
USER node
EXPOSE 3000
CMD ["node", "dist/index.js"]

Node.js 的坑

坑说明与对策
CMD ["npm", "start"]npm 会多套一层进程，而且不能可靠地把 SIGTERM 转发给 node，docker stop 常常要等 10 秒被强杀。直接用 node 启动。
PID 1 不处理信号Node 作为 PID 1 时，如果代码没监听 SIGTERM，信号会被忽略（第 7 章）。在代码里 process.on('SIGTERM', …) 优雅关闭 HTTP 服务器和数据库连接；或者运行时加 --init。
原生模块bcrypt、sharp 这类带 C++ 扩展的包在 alpine 上可能需要编译。遇到问题就换 node:24-slim。
本地 node_modules 混进镜像.dockerignore 里一定要有 node_modules，否则 macOS 编译的模块会被复制进 Linux 镜像。
内存上限新版本 Node 会参考容器的内存限制设置堆大小，但想要可预期的行为，可以显式指定：ENV NODE_OPTIONS="--max-old-space-size=384"（约为容器内存上限的 75%）。
pnpm / yarn用 corepack enable 启用，锁文件换成 pnpm-lock.yaml，安装命令换成 pnpm install --frozen-lockfile，思路完全相同。
const server = app.listen(3000, '0.0.0.0')   // 监听 0.0.0.0，原因见第 17 章

process.on('SIGTERM', () => {
  console.log('收到 SIGTERM，正在关闭……')
  server.close(async () => {
    await db.end()                            // 关闭数据库连接池
    process.exit(0)
  })
})

Python

Python 这几年的依赖管理工具换了一代：uv（Astral 出品，用 Rust 编写）速度极快，并且原生支持锁文件 uv.lock，已经成为新项目的主流选择。 下面的模板用 uv 在构建阶段创建虚拟环境，再把整个虚拟环境复制到运行阶段： 

# syntax=docker/dockerfile:1
FROM python:3.14-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.12 /uv /uvx /bin/
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_NO_DEV=1 \
    UV_PYTHON_DOWNLOADS=0
WORKDIR /app

# 1. 只根据锁文件安装依赖（源码变化不会让这一层失效）
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project

# 2. 复制源码，安装项目本身
COPY . .
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked

FROM python:3.14-slim AS runtime
ENV PYTHONUNBUFFERED=1 \
    PATH="/app/.venv/bin:$PATH"
RUN groupadd --system app && useradd --system --gid app --no-create-home app
WORKDIR /app
COPY --from=build --chown=app:app /app /app
USER app
EXPOSE 8000
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0", "--port", "8000"]
设置作用
COPY --from=ghcr.io/astral-sh/uv:0.12直接从 uv 的官方镜像里复制可执行文件，不用 pip 安装 uv；固定到小版本
UV_COMPILE_BYTECODE=1安装时预编译 .pyc，容器启动更快
UV_LINK_MODE=copy缓存挂载和目标目录不在同一文件系统，用复制代替硬链接，避免警告
UV_NO_DEV=1不安装开发依赖（pytest、ruff 等）
UV_PYTHON_DOWNLOADS=0使用镜像自带的 Python，不让 uv 另外下载一个
PYTHONUNBUFFERED=1输出不缓冲，docker logs 能实时看到日志
PATH=/app/.venv/bin:…让 uvicorn、python 直接使用虚拟环境里的版本
💡 还在用 pip + requirements.txt？

思路一样，只是换成：

FROM python:3.14-slim AS build
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
# 运行阶段：COPY --from=build /opt/venv /opt/venv，并设置同样的 PATH

Python 的坑

坑说明与对策
用 alpine 导致构建极慢numpy、pandas、cryptography 等在 alpine 上经常没有可用的 wheel，要现场编译几分钟甚至几十分钟。优先 slim。
需要编译的依赖在 build 阶段装 build-essential、libpq-dev 等，运行阶段只装运行时库（如 libpq5）。编译器不进最终镜像。
虚拟环境路径变了就失效虚拟环境里写死了绝对路径，所以构建阶段和运行阶段要用同一个路径（本例都是 /app/.venv）和同一个 Python 版本。
开发服务器上生产flask run、manage.py runserver 只用于开发。生产用 gunicorn、uvicorn、granian 等。
日志看不到忘了 PYTHONUNBUFFERED=1，输出卡在缓冲区里，容器崩溃时最后几行日志就丢了。

Go

Go 是最适合容器的语言之一：可以编译成不依赖任何系统库的静态二进制，最终镜像可以小到只有几 MB。 而且 Go 的交叉编译能力，让多架构构建完全不需要 QEMU 模拟： 

# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:1.27-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .
ARG TARGETOS TARGETARCH
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /out/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
设置作用
--platform=$BUILDPLATFORM构建阶段使用构建机自己的架构，而不是目标架构，避免 QEMU 模拟
ARG TARGETOS TARGETARCHBuildKit 自动提供的参数，表示当前要产出的目标平台
CGO_ENABLED=0不链接 C 库，生成纯静态二进制，才能在 distroless/static 或 scratch 里运行
-trimpath -ldflags="-s -w"去掉本机路径和调试符号，二进制更小、构建更可重复
两个缓存挂载/go/pkg/mod 缓存下载的模块，/root/.cache/go-build 缓存编译结果
distroless/static:nonroot只含 CA 证书、时区数据和一个非 root 用户，约 2 MB

Go 的坑

坑说明与对策
用 scratch 后 HTTPS 请求失败scratch 里没有 CA 证书，报 x509: certificate signed by unknown authority。用 distroless/static（自带证书），或从构建阶段复制 /etc/ssl/certs/ca-certificates.crt。
时区不对scratch 里没有时区数据。用 distroless，或者编译时加 -tags timetzdata 把时区数据嵌进二进制。
用了 CGO 的库比如某些 SQLite 驱动。要么换纯 Go 实现，要么保留 CGO_ENABLED=1 并改用 distroless/base（含 glibc）作为运行镜像，交叉编译也会变复杂。
没有 shell，健康检查怎么写distroless 里没有 wget/curl。在程序里实现一个子命令，例如 /server healthcheck 去请求本地的 /health，然后 HEALTHCHECK CMD ["/server", "healthcheck"]。

Java（Spring Boot）

Java 镜像的关键在于三点：用 JDK 构建、用 JRE 运行；让 JVM 正确感知容器的内存限制；利用分层让依赖（通常几十 MB）不必每次都重新推送。

# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN --mount=type=cache,target=/root/.m2 \
    ./mvnw -B dependency:go-offline          # 先下载依赖，独立成层
COPY src src
RUN --mount=type=cache,target=/root/.m2 \
    ./mvnw -B package -DskipTests            # 测试交给 CI 的 test 目标
# 把 Spring Boot 的可执行 jar 按层拆开
RUN java -Djarmode=tools -jar target/*.jar extract --layers --destination /extracted

FROM eclipse-temurin:25-jre AS runtime
RUN groupadd --system app && useradd --system --gid app app
WORKDIR /app
COPY --from=build /extracted/dependencies/          ./
COPY --from=build /extracted/spring-boot-loader/    ./
COPY --from=build /extracted/snapshot-dependencies/ ./
COPY --from=build /extracted/application/           ./
USER app
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "application.jar"]

Java 的坑

坑说明与对策
JVM 内存设置现代 JVM 能感知容器限制，但默认最大堆只有容器内存的 25%，很浪费。用 -XX:MaxRAMPercentage=75 按比例设置，而不要写死 -Xmx —— 否则改了容器内存限制还得记着改它。剩下的内存留给元空间、线程栈、直接内存等。
OOM 后半死不活-XX:+ExitOnOutOfMemoryError 让 JVM 在内存溢出时直接退出，交给重启策略拉起，而不是带病运行。
用 JDK 运行JDK 比 JRE 大好几百 MB，还带着编译器等不必要的工具。运行阶段用 -jre；更进一步可以用 jlink 裁剪出只含所需模块的运行时，或用 gcr.io/distroless/java25-debian13。
启动慢可以考虑 CDS / AOT 缓存（新版本 JDK 持续在改进），或者用 GraalVM Native Image 编译成原生二进制（启动毫秒级，但构建慢、有兼容性限制）。
Gradle 项目思路相同：先复制 build.gradle、settings.gradle、gradle/ 下载依赖，缓存挂载 /root/.gradle，再复制源码执行 ./gradlew bootJar。

附：前端静态站点

React、Vue、Vite 这类前端项目，构建结果只是一堆静态文件，运行时根本不需要 Node：

# syntax=docker/dockerfile:1
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build                          # 输出到 dist/

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

单页应用还需要让 nginx 把找不到的路径都回退到 index.html（try_files $uri /index.html;）。也可以直接用第 20 章的 Caddy 托管静态文件。

💡 别忘了 docker init

第 8 章的 docker init 支持 Node、Python、Go、Java、Rust、PHP、ASP.NET 等，会生成一个遵循最佳实践的起点。可以先用它生成，再对照本章的模板和清单做调整。

本章小结

  • 所有语言的生产 Dockerfile 都遵循同一个骨架：固定基础镜像 → 依赖层 → 源码与构建 → 精简的运行阶段。
  • 基础镜像按需选择：slim 兼容性最好，alpine 小但要注意 musl，distroless / scratch 最小最安全，适合静态二进制。
  • Node.js：用 node 直接启动并处理 SIGTERM，生产依赖和编译产物分阶段准备。
  • Python：用 uv 和锁文件，虚拟环境整体复制到运行阶段，优先 slim，别忘了 PYTHONUNBUFFERED。
  • Go：CGO_ENABLED=0 静态编译，利用 $BUILDPLATFORM 交叉编译避开 QEMU，运行在 distroless 上。
  • Java：JDK 构建、JRE 运行，MaxRAMPercentage 设置堆大小，Spring Boot 分层让依赖层可以复用。

✎ 动手练习

  1. 挑一种你熟悉的语言，把自己的一个项目按本章模板容器化，然后对照“通用检查清单”逐项检查。
  2. 用同一个 Python 项目分别构建 3.14、3.14-slim、3.14-alpine 三个版本，比较构建时间和镜像大小。
  3. 用本章的 Go 模板执行 docker buildx build --platform linux/amd64,linux/arm64 .，观察编译步骤是否需要 QEMU（看日志里的平台标记），并与第 8 章不加 $BUILDPLATFORM 的写法对比耗时。
  4. 给 Java 容器设置 --memory 1g，进入容器执行 java -XX:+PrintFlagsFinal -version | grep MaxHeapSize，对比设置 MaxRAMPercentage=75 前后的值。
  5. 把 Node 模板的 CMD 改成 ["npm", "start"]，用 time docker stop 对比停止耗时和退出码。

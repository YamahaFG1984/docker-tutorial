第 12 章

Docker Swarm

Compose 管理的是一台机器上的应用。如果要把应用跑在多台机器组成的集群上，并且能自动扩缩容、自我修复、滚动更新呢？ 这就需要编排器（orchestrator）。Docker 自带的编排器叫 Swarm：简单、内置、零额外安装，是学习 Kubernetes 前的最佳热身。

本章目标

  • 理解 swarm（集群）与 Swarm（编排器）、管理节点与工作节点
  • 搭建一个高可用的多节点 swarm
  • 理解期望状态、观察状态与调和（reconciliation）
  • 用 docker stack deploy 部署、扩容、滚动更新应用
  • 理解为什么应该声明式而不是命令式地管理应用
✨ Swarm 在 2026 年

Kubernetes 早已是容器编排的事实标准，Swarm 的使用者在减少，原书作者也因此把 Swarm 压缩成了这一章。 不过 Swarm 仍是 Docker Engine 29 的内置功能、仍在维护（Mirantis 等公司持续投入），对于不需要 Kubernetes 那么复杂的小团队和小型业务依然是很好的选择。 另外，第 14 章的 overlay 网络和第 16 章的 Docker 机密都依赖 Swarm 模式。

Swarm 入门

2010 年代中期发生过一场“编排之战”：Docker Swarm、HashiCorp Nomad、Mesosphere DC/OS 和 Kubernetes 争夺容器编排平台的王座。 如今 Kubernetes 胜出并拥有最大、最活跃的生态，但 Swarm 仍有一批拥趸，在某些场景下比 Kubernetes 更合适 —— 比如需求简单、不想承担 Kubernetes 陡峭学习曲线和运维开销的小企业。

Docker Swarm 是两样东西：

  1. 一个安全的 Docker 节点集群（小写 s 的 swarm）；
  2. 一个智能的应用编排器（大写 S 的 Swarm）。
  • 管理节点（manager）运行控制平面服务，负责保护集群安全并提供编排智能；
  • 工作节点（worker）运行用户应用；
  • 两种节点都可以是物理机、虚拟机、云主机……唯一的要求是装了 Docker，并且能通过可靠的网络互相通信。

默认情况下管理节点也会运行用户应用。实验环境这样没问题，但在繁忙的生产环境中，最好让管理节点专心做控制平面的工作。

搭建 swarm

你需要两台或更多装了 Docker 的机器。推荐用 Play with Docker 快速创建几个节点， 也可以用 Multipass、VirtualBox 创建本地虚拟机。不建议用 Docker Desktop，因为它只有一个 Docker 节点。

生产环境应考虑：

  • 3 个管理节点，分布在不同可用区，保证高可用；
  • 足够多的工作节点来满足应用需求；
  • 节点之间能通过名字互相解析，并开放以下端口：
端口用途
2377/tcp管理平面通信（节点加入、集群管理）
7946/tcp + 7946/udp控制平面通信（基于 SWIM 的 gossip 协议）
4789/udpoverlay 网络的 VXLAN 数据平面（第 14 章）

初始化 swarm

登录到你想作为第一个管理节点的机器上运行（如果节点有多个 IP，会提示你用 --advertise-addr 指定主 IP）：

$ docker swarm init
Swarm initialized: current node (b8slc7l29tgdetxgy8acy1k1q) is now a manager.

To add a worker to this swarm, run the following command:
    docker swarm join --token SWMTKN-1-2hl6...-...3lqg 172.31.40.192:2377

恭喜，你有了一个单节点 swarm。

添加工作节点（可选）

管理节点也能跑应用，所以工作节点是可选的。如果资源够，把上面输出里的整条 docker swarm join 命令（含令牌）复制到要作为工作节点的机器上运行：

wrk-1 $ docker swarm join --token SWMTKN-1-2hl6...-...3lqg 172.31.40.192:2377
This node joined a swarm as a worker.

添加管理节点实现高可用

在管理节点上获取“加入为管理节点”的命令，然后到其他机器上运行它：

$ docker swarm join-token manager
To add a manager to this swarm, run the following command:
    docker swarm join --token SWMTKN-1-2f4s47lja0z1ddkgv...6ytm3qnq9bu8uei9stiu 172.31.40.192:2377

$ docker node ls

y43jr1d754pbjv3arlhpn9pqw     node2      Ready    Active         Reachable        29.8.0

管理节点的 MANAGER STATUS 是 Leader 或 Reachable，工作节点这一列为空；星号 * 表示你执行命令的那个节点。 Swarm 采用主备（active/passive）多管理节点模型：一个 Leader 掌控集群，其他管理节点做后备。

★ 为什么管理节点要用奇数个？

管理节点之间用 Raft 共识算法保持一致，任何决策都需要超过半数的管理节点同意。 3 个管理节点可以容忍 1 个故障，5 个可以容忍 2 个；而 4 个和 3 个一样只能容忍 1 个 —— 多一个节点却没多一点容错，所以用奇数。 另外请注意，这是集群的高可用，不是应用的高可用：如果挂掉的管理节点上恰好运行着某个数据库的唯一副本，那个数据库照样不可用。

部署 Swarm 应用

这一节把应用部署到 swarm 上，体验 Swarm 的编排能力：跨节点调度、扩缩容、从故障中自我修复、滚动更新。

示例应用

ⓘ 术语

本章中，服务（service）指 Docker 的 service 对象，它管理一个或多个相同的容器；“容器”和“副本（replica）”两个词混用。

在一个管理节点上克隆仓库，进入 swarm-new 目录：

$ git clone https://github.com/nigelpoulton/ddd-book.git
$ cd ddd-book/swarm-new

networks:
  counter-net:
    driver: overlay             # overlay 网络：横跨整个 swarm
    driver_opts:
      encrypted: 'yes'          # 加密应用流量
volumes:
  counter-vol:
services:
  web-fe:
    image: nigelpoulton/ddd-book:swarm-app
    command: python app.py
    deploy:
      replicas: 4               # 部署 4 个副本
      update_config:            # 如何进行更新：
        parallelism: 2          #   每次更新 2 个副本
        delay: 10s              #   每批之间等 10 秒
        failure_action: rollback  # 失败就回滚
      restart_policy:           # 副本失败时：
        condition: on-failure   #   只在失败时重启
        delay: 5s               #   重启间隔 5 秒
        max_attempts: 3         #   最多尝试 3 次
        window: 120s            #   2 分钟后判定是否重启成功
    networks:
      - counter-net
    ports:
      - "5001:8080"             # 在主机 5001 端口发布
  redis:
    image: "redis:alpine"
    networks:
      counter-net:
    volumes:
      - type: volume
        source: counter-vol
        target: /data           # 注：作者仓库此处写的是 /app，Redis 的数据目录实际是 /data

和第 9 章的 Compose 文件相比，主要区别在于：网络用了 overlay 驱动（多主机网络，第 14 章），以及 deploy 块里多了 update_config 和 restart_policy —— 这些是 Swarm 专用的编排配置，单机 Compose 大多会忽略它们。

ⓘ 加密网络的代价

加密 overlay 网络能保护应用流量的私密性，但会带来一定的性能损失，具体取决于流量类型和流向，通常在 10% 左右，最好自己测试。

期望状态

Swarm 最核心的概念是期望状态（desired state）：你希望应用是什么样子，由 Compose 文件定义。 本例的期望状态可以概括为：web-fe 服务 4 个副本、redis 服务 1 个副本，以及所有网络、卷和端口映射。

部署应用

在管理节点的 swarm-new 目录下运行，把应用部署为一个叫 ddd 的 stack：

$ docker stack deploy -c compose.yaml ddd

Creating service ddd_web-fe
Creating service ddd_redis

观察状态和期望状态一致：你要 4 个 web-fe 副本和 1 个 redis 副本，得到的正是这些。Swarm 还把 4 个 web-fe 副本均匀分配到了各个节点上。 用浏览器访问任意一个 swarm 节点的 IP 加 5001 端口，都能看到应用。

管理应用：命令式 vs 声明式

管理 Swarm 应用有两种方式：

  • 命令式（imperative）：直接运行 CLI 命令修改，比如用 docker service scale 增减副本数；
  • 声明式（declarative）：所有修改都通过 Compose 文件进行，改完文件再运行一次 docker stack deploy。这是推荐的方式。

下面这个故事说明了为什么：

每次 docker stack deploy 都会把 Compose 文件作为新的期望状态推给 Swarm。Swarm 比较它和观察状态，发现你要更新 catalog 服务，于是安排更新； 但同时它也发现 reporting 应该只有 1 个副本（文件里就是这么写的），于是把 10 个缩回 1 个。所以：所有修改都应该通过 Compose 文件声明式地进行，并且把 Compose 文件放进版本控制。

扩容并滚动更新

我们把两个修改作为一次任务完成：web-fe 副本从 4 增加到 10；web-fe 升级到新镜像 swarm-appv2。编辑 Compose 文件：

services:
  web-fe:
    image: nigelpoulton/ddd-book:swarm-appv2     # 改成 swarm-appv2
    command: python app.py
    deploy:
      replicas: 10                               # 从 4 改成 10

$ docker stack deploy -c compose.yaml ddd
Updating service ddd_web-fe (id: rsm3x02o9fwcftt3a87fqcabq)
Updating service ddd_redis (id: otr7927s9m1s5mkz326243kv3)

$ docker stack ps ddd
NAME              IMAGE                               NODE   DESIRED STATE   CURRENT STATE
ddd_web-fe.1      nigelpoulton/ddd-book:swarm-app     wrk1   Running         Running 8 mins ago
ddd_web-fe.2      nigelpoulton/ddd-book:swarm-appv2   mgr1   Running         Running 13 secs ago
 \_ ddd_web-fe.2  nigelpoulton/ddd-book:swarm-app     mgr1   Shutdown        Shutdown 26 secs ago
ddd_web-fe.3      nigelpoulton/ddd-book:swarm-app     mgr2   Running         Running 8 mins ago
<Snip>

从输出能看到：web-fe.1 还在跑旧镜像；web-fe.2 的旧副本 26 秒前被关闭，由一个跑新镜像的新副本替代；web-fe.3 还没轮到。 Swarm 会立即添加 6 个新副本，而对原有的 4 个副本则遵守 update_config：每次更新 2 个，每批之间等 10 秒。

回顾一下这次调和：Swarm 上记录的期望状态原本是“4 个运行 swarm-app 的 web-fe 副本”。你修改 Compose 文件后运行 docker stack deploy，推送了新的期望状态。 Swarm 比较后发现集群里有 4 个跑旧镜像的副本，但应该有 10 个跑新镜像的副本，于是按照 update_config 的规则，用 10 个新副本替换了旧的 4 个。 刷新浏览器，就能看到新版应用。

清理

$ docker stack rm ddd              # 不会要求确认！
Removing service ddd_redis
Removing service ddd_web-fe
Removing network ddd_counter-net

服务和网络被删除了，但卷没有 —— Swarm 把卷的生命周期和容器、服务解耦了。到运行 redis 副本的那个节点上删除卷：

$ docker volume rm ddd_counter-vol

要解散 swarm，在所有节点上运行 docker swarm leave，最后处理 Leader 节点，可能需要加 --force。

命令速查

命令作用
docker swarm init初始化新 swarm，当前节点成为第一个管理节点
docker swarm join-token worker|manager显示加入为工作 / 管理节点的命令和令牌
docker swarm join --token …把当前节点加入 swarm
docker node ls列出所有节点及其角色、状态
docker stack deploy -c 文件 名称部署或更新 Swarm 应用
docker stack ls列出所有 stack 及其服务数
docker stack ps 名称每个副本在哪个节点、用哪个镜像、期望状态与当前状态
docker stack services 名称每个服务的模式、副本数、端口
docker service logs 服务查看服务所有副本的日志
docker stack rm 名称删除 Swarm 应用（不确认）
docker swarm leave [--force]离开 swarm

本章小结

  • Docker Swarm 把多个 Docker 节点组成一个安全、高可用的集群，并提供类似 Kubernetes 的应用编排能力。
  • 管理节点运行控制平面（用 Raft 保持一致，建议 3 或 5 个），工作节点运行应用。
  • Swarm 的核心是期望状态与调和：不断让观察状态追上期望状态，从而实现自我修复。
  • 用 docker stack deploy 部署和更新应用；应该声明式地通过 Compose 文件修改，避免配置漂移。
  • update_config 控制滚动更新节奏，restart_policy 控制失败副本的重启行为。
  • 学会 Swarm，是开始学习 Kubernetes 的好起点。

✎ 动手练习

  1. 在 Play with Docker 上创建 3 个节点，搭一个 1 管理 + 2 工作的 swarm，部署本章的 stack。
  2. 在某个工作节点上用 docker rm -f 强行删掉一个 web-fe 容器，然后在管理节点上 docker stack ps ddd，观察 Swarm 如何自动补上副本。
  3. 先用 docker service scale ddd_web-fe=6 命令式扩容，再不改文件直接 docker stack deploy，亲手验证“配置漂移”被覆盖回去的现象。
  4. 把 update_config.parallelism 改成 1、delay 改成 20s，再做一次版本更新，边更新边 watch docker stack ps ddd。

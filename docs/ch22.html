第 22 章

镜像瘦身实战

第 6、8、16、21 章从不同角度讲过“镜像要小”，但到底能小多少？每一步的收益有多大？镜像小了，漏洞真的会变少吗？ 这一章不讲道理，只做实验：拿同一个应用，一步一步地优化，每一步都真实构建、测量体积、扫描漏洞。 结果是从 1268 MB、3454 个已知漏洞，降到 72 MB、0 个漏洞。

本章目标

  • 用真实数据理解每个瘦身手段的收益：换基础镜像、.dockerignore、多阶段构建、换发行版、删多余组件
  • 学会找出镜像里“胖”在哪里
  • 理解“在后面的层里删除文件，镜像不会变小”
  • 正确解读漏洞扫描的数字：总数不等于风险
  • 知道瘦身的优先级：先做收益最大、成本最低的

实验设置

ⓘ 这些数字是真的测出来的

本章所有数字都来自 2026 年 9 月 22 日在一台 x86_64 Linux 机器上的实测：Docker Engine 29.3.1，BuildKit 构建， 漏洞扫描使用 Trivy 0.74.0（当天更新的漏洞库）。你自己重做时数字会有出入 —— 基础镜像每周都在更新，漏洞库每天都在变 —— 但每一步的相对变化是稳定的。

示例应用是一个很小的 FastAPI 服务，依赖只有 fastapi 和 uvicorn（锁文件里一共 13 个包）：

from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

为了模拟真实项目，项目目录里还有两样“杂物”：开发时建的本地虚拟环境 .venv/（60 MB），和测试用的数据文件 tests/fixtures/big-dump.sql（30 MB）。真实项目里的 .git、node_modules、日志、构建产物都属于这一类。

每个版本我们记录四个指标：

指标含义影响什么
解压后大小镜像在磁盘上展开后的大小服务器磁盘占用
压缩后大小推送、拉取时实际传输的大小部署速度、仓库存储费用、冷启动时间
漏洞总数扫描器发现的所有已知漏洞扫描报告看起来有多吓人
可修复的严重 + 高危漏洞已有修复版本的 Critical 和 High 漏洞真正需要你处理的风险

第 ① 步：直接写

这是网上最常见、也是很多人第一次写出来的 Dockerfile：

FROM python:3.14
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0"]
1268 MB解压后
524 MB压缩后（每次部署都要拉这么多）
3454已知漏洞（严重 18，高危 311）
11可修复的严重 + 高危

答案一目了然：最大的三层都是编译工具和开发库（gcc、各种 -dev 头文件包、git、svn……），合计近 1 GB。 完整版的 python:3.14 基于 Docker 官方的 buildpack-deps 镜像，它的设计目标是“什么都能编译”—— 这对需要编译 C 扩展的构建阶段很方便， 但我们的应用运行时一个都用不上。第四大的是 COPY . .，它把 94 MB 的杂物原封不动地带了进来。

💡 自己动手查：镜像胖在哪里

docker history --no-trunc 镜像 列出每一层的大小和产生它的指令，按 SIZE 一看就知道大头在哪。 想看某一层里具体有哪些文件，可以用开源工具 dive，它能逐层浏览文件树，还会估算“浪费的空间”。

第 ② 步：换成 slim

只改一个词：

FROM python:3.14-slim
250 MB解压后（−80%）
152 MB压缩后（−71%）
155已知漏洞（严重 0，高危 46）
2可修复的严重 + 高危
★ 投入产出比最高的一步

改一个词，体积减少 1 GB，漏洞从 3454 个降到 155 个。没装的软件不会有漏洞 —— 编译工具链带来的几千个漏洞，随着工具链一起消失了。 如果你只打算做一件事，就做这一步。

第 ③ 步：忽略杂物，调整顺序

v3.Dockerfile
FROM python:3.14-slim
ENV PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY myapp ./myapp
RUN useradd --system app
USER app
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0"]
.dockerignore
.venv
tests
.git
__pycache__
150 MB解压后（−100 MB）
52.5 MB压缩后（−65%）
155已知漏洞（没变）
2可修复的严重 + 高危

减掉的 100 MB 来自两处：

  • 94 MB 杂物：.dockerignore 让 .venv 和测试数据根本不进入构建上下文；只复制 myapp/ 而不是整个目录，更是双保险。
  • 约 6 MB pip 缓存：PIP_NO_CACHE_DIR=1 让 pip 不在镜像里留下下载缓存（pip 安装层从 32.0 MB 降到 26.3 MB）。

压缩后的大小降得更多（152 → 52.5 MB），因为那些杂物是随机数据、几乎无法压缩；真实项目里的 .git 目录也常常压缩效果很差。 漏洞数没有变化 —— 杂物不是软件包。另外两处改动不影响体积，但同样重要：先复制依赖清单再复制代码，改代码时依赖层能命中缓存（第 8 章）；以非 root 用户运行（第 16 章）。

第 ④ 步：多阶段构建 + uv

用第 21 章的模板：在构建阶段用 uv 按锁文件建立虚拟环境，运行阶段只复制这个虚拟环境：

# syntax=docker/dockerfile:1
FROM python:3.14-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.12 /uv /bin/
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_NO_DEV=1 UV_PYTHON_DOWNLOADS=0
WORKDIR /app
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project
COPY pyproject.toml uv.lock ./
COPY myapp ./myapp
RUN --mount=type=cache,target=/root/.cache/uv uv sync --locked --no-editable

FROM python:3.14-slim
ENV PYTHONUNBUFFERED=1 PATH="/app/.venv/bin:$PATH"
RUN useradd --system app
WORKDIR /app
COPY --from=build /app/.venv /app/.venv
USER app
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0"]
140.6 MB解压后（−10 MB）
48.9 MB压缩后
155已知漏洞（没变）
2可修复的严重 + 高危

这一步只省了 10 MB（虚拟环境 16.8 MB，对比 pip 安装层 26.3 MB），看起来不起眼。这是一个诚实的结果： 我们的依赖全都有预编译的 wheel，构建阶段本来就不需要编译器。多阶段构建的巨大收益出现在构建需要重型工具的时候： 要装 build-essential 编译 C 扩展的 Python 项目、要 JDK 的 Java 项目、要完整 Go 工具链的 Go 项目（见本章后面的 Go 对比）。 而且即使体积收益小，它也带来了锁文件保证的可重复构建，以及“构建环境和运行环境分离”这个好习惯。

第 ⑤ 步：卸载用不到的 pip

第 ④ 步还剩 2 个可修复的高危漏洞，查一下扫描报告，它们来自哪里？

Python (python-pkg)
  HIGH  msgpack     1.1.2   → 1.2.1    GHSA-6v7p-g79w-8964
  HIGH  setuptools  70.3.0  → 78.1.1   CVE-2025-47273

我们的应用根本不依赖 msgpack 和 setuptools。追查下去才发现，它们是基础镜像里预装的 pip 内部打包（vendor）的组件。 而我们的运行阶段用的是 uv 创建的虚拟环境，pip 完全用不上。那就在运行阶段卸载它： 

RUN /usr/local/bin/python -m pip uninstall -y pip    # 用系统解释器，虚拟环境里没有 pip
USER app
145.0 MB解压后（反而 +4.4 MB！）
50.6 MB压缩后（+1.7 MB）
152已知漏洞
0可修复的严重 + 高危 ✓

可修复的高危漏洞清零了，但镜像反而变大了。为什么？

★ 瘦身的铁律：不要先放进来，再删掉

在一个 RUN 里下载、另一个 RUN 里删除，前一层的文件永远留在镜像里。正确的做法有三种： 在同一个 RUN 里装完就清理（比如 apt-get install … && rm -rf /var/lib/apt/lists/*）； 用多阶段构建只复制需要的产物；或者选一个本来就没有这些东西的基础镜像。 本例中卸载 pip 对安全有意义（被遮盖的文件在运行时不可见），但如果追求体积，就应该换用不带 pip 的基础镜像。

第 ⑥⑦ 步：换成 alpine

把第 ④ 步两个阶段的基础镜像都换成 python:3.14-alpine（用户创建命令相应改为 adduser -S -H app），然后再做一次 ⑤ 的卸载 pip：

版本解压后压缩后漏洞总数可修复的严重 + 高危
⑥ alpine + 多阶段 + uv67.9 MB23.4 MB3（高危 2，中危 1）2（还是 pip 那两个）
⑦ 再卸载 pip72.3 MB25.2 MB00

alpine 版本的体积是 slim 版本的一半，更引人注目的是漏洞：Debian 系统层的 152 个漏洞，在 Alpine 上是 0 个。 最终版的 ⑦ 已经实际启动验证过，/health 正常返回。

⚠ 这次 alpine 顺利，是因为运气好

alpine 用的是 musl libc。本例能顺利运行，是因为所有依赖（包括用 Rust 编译的 pydantic-core）都提供了 musllinux 的预编译 wheel。 如果你的项目依赖某个只有 glibc wheel 的包，在 alpine 上就只能现场编译 —— 构建变慢、镜像里要装编译器，甚至运行时出现细微差异（第 21 章）。 换 alpine 之前，先在 CI 里完整跑一遍测试。

正确解读漏洞数字

看到 slim 版本有 152 个漏洞、其中 44 个高危，你可能会紧张。但把扫描结果按状态分类后，情况完全不同：

状态含义第 ⑤ 步中的数量
affected受影响，但发行版还没有、或不打算发布修复（常见理由：风险极低、只在特定配置下可利用）150
fix_deferred发行版决定推迟修复2
fixed已有修复版本，升级即可0
  • 总数不等于风险。Debian 会把大量“理论上受影响、实际上几乎无法利用”的问题也登记在案，所以 Debian 系镜像的漏洞总数天然偏高。
  • 真正该盯的是“可修复的严重 + 高危”，这也是第 19 章质量门里 ignore-unfixed: true 的原因 —— 否则你的流水线会因为一个谁也修不了的漏洞永远红着。
  • 没修复的漏洞也不是可以永远忽略的。定期重建镜像以获取最新补丁；对真正影响你的漏洞，评估是否需要换基础镜像。
  • 软件包越少，攻击面越小。这一点在 ①→② 和 ②→⑥ 两次跳变中体现得淋漓尽致。

对照：Go 应用

用一个同样只有健康检查接口的 Go 程序，对比第 21 章的单阶段和多阶段写法：

单阶段
FROM golang:1.27-alpine
WORKDIR /src
COPY . .
RUN go build -o /server .
CMD ["/server"]
多阶段 + distroless
FROM golang:1.27-alpine AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -trimpath \
    -ldflags="-s -w" -o /server .

FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /server /server
ENTRYPOINT ["/server"]

这就是多阶段构建真正发威的场景：单阶段镜像里装着整个 Go 工具链（编译器、标准库源码），而运行程序只需要一个静态二进制。 多阶段版本压缩后只有 3.4 MB。两个版本的漏洞扫描结果都是 0。实际启动后，distroless 镜像里连 id 这样的命令都没有 —— 攻击者即使攻破了程序，也找不到 shell 和常用工具。

瘦身的优先级

根据实测结果，按“收益 ÷ 成本”排序：

ⓘ 还可以更进一步
  • Docker Hardened Images（第 16 章）：Docker 维护的精简加固镜像，很多语言都有“不带包管理器和 shell”的运行时变体，相当于官方替你做完了 ⑤⑥⑦。本章没有测量它，因为需要登录它的仓库。
  • distroless：Go、Java 等有现成的 distroless 运行时镜像。它的 Python 镜像使用发行版自带的 Python 版本，不一定和你需要的版本一致，选用前要确认。
  • 不要走火入魔：镜像从 72 MB 压到 60 MB 的收益，远不如花同样的时间把测试写好。本章的前两步已经拿到了 90% 以上的收益。

几个常见误区

误区事实
“我在最后一个 RUN 里 rm -rf 了缓存，镜像就小了”只有在同一个 RUN 里产生和删除才有效，否则文件留在之前的层里（本章第 ⑤ 步实测 +4.4 MB）
“层越少越好，把所有 RUN 合成一个”层数本身几乎不影响性能。过度合并反而破坏缓存（改一点就要全部重建）。按“变化频率”分层比按“数量最少”分层更重要
“镜像越小越好，一律用 scratch”越小越难调试，兼容性要求越高。先拿到大头收益，再按需要取舍。调试可以用第 7 章的 docker debug
“漏洞数为 0 就安全了”扫描器只能发现已知漏洞，也看不到你自己代码里的问题和错误配置。它是必要条件，不是充分条件
“alpine 一定最小最好”对 Go 这类静态二进制，distroless/scratch 更小；对依赖 glibc wheel 的 Python 项目，alpine 可能让构建更慢、镜像更大

自己重做这个实验

下面是本章测量方法的要点，你可以用它来评估自己的镜像：

# 构建并查看大小
$ docker build -t myapp:v1 -f v1.Dockerfile .
$ docker image ls myapp

# 每一层的大小与来源
$ docker history myapp:v1

# 漏洞扫描：Trivy（只看可修复的严重 / 高危）或 Docker Scout
$ trivy image --severity CRITICAL,HIGH --ignore-unfixed myapp:v1
$ docker scout quickview myapp:v1
⚠ 安装扫描工具也要当心供应链

2026 年 3 月 Trivy 本身就遭遇过供应链攻击，恶意版本被发布到 GitHub 和 Docker Hub（详见第 19 章）。 安装任何安全工具都应该：从官方渠道下载固定版本，校验官方发布的 SHA256 校验和（最好再用 cosign 验证签名），不要盲目使用 latest。 本章实验使用的是 Trivy 0.74.0，下载后先校验了官方的 SHA256 再运行。

本章小结

  • 同一个应用，从 ① 到 ⑦：1268 MB → 72 MB，拉取量 524 MB → 25 MB，已知漏洞 3454 → 0。
  • 收益最大的一步是把 python:3.14 换成 python:3.14-slim：改一个词，减少 80% 的体积和 95% 以上的漏洞。
  • .dockerignore 和只复制需要的文件，能挡住大量杂物，压缩后的收益尤其明显。
  • 多阶段构建在构建需要重型工具时收益巨大（Go 示例 −97%），否则收益较小但依然值得。
  • 在后面的层里删除文件不会让镜像变小；要么在同一层清理，要么根本不放进来。
  • 漏洞总数不等于风险，重点关注“可修复的严重 + 高危”；软件包越少，攻击面越小。

✎ 动手练习

  1. 对你自己项目的镜像运行 docker history，找出最大的三层分别是什么，判断它们在运行时是否真的需要。
  2. 给你的项目加上 .dockerignore，比较前后的构建上下文大小（构建输出里 “transferring context” 那一行）和镜像大小。
  3. 写一个在两个 RUN 里分别下载和删除一个 50 MB 文件的 Dockerfile，再写一个在同一个 RUN 里完成的版本，对比两个镜像的大小，验证本章的“铁律”。
  4. 用 Trivy 或 Docker Scout 扫描你的镜像，分别统计“漏洞总数”和“可修复的严重 + 高危”，想一想哪个数字更值得放进 CI 的质量门。

第 16 章

Docker 安全

如果安全很难做，人们就不太会去做。好在 Docker 的大部分安全措施都很简单，而且预设了合理的默认值 —— 零配置就能得到“还算安全”的体验。 本章先讲 Docker 用到的 Linux 安全技术，再讲 Docker 自己的安全技术，最后给出一份可以直接照做的加固清单。

本章目标

  • 理解“纵深防御”：命名空间、cgroups、capabilities、MAC、seccomp 各自防什么
  • 理解 Swarm 自带的安全机制：加入令牌、双向 TLS、证书轮换、加密集群存储
  • 会用漏洞扫描，了解 Docker Hardened Images
  • 知道 Docker Content Trust 已退役，会用 Sigstore Cosign 签名和验证镜像
  • 用 Docker 机密（secrets）安全地传递密码等敏感数据
  • 掌握一套实用的容器加固参数

一句话概括

好的安全靠的是层层设防（纵深防御），层数越多越好。Docker 提供了很多层：

Docker 利用了常见的 Linux 安全与隔离技术：命名空间、控制组、capabilities、强制访问控制（MAC）和 seccomp，并为每一项都提供了合理的默认配置，你也可以按需定制。 Docker 还有自己的安全技术：漏洞扫描（Docker Scout）、镜像签名与验证、机密管理等。 如果你用 Docker Swarm，还会自动得到：加密的节点 ID、双向 TLS 认证、自动 CA 配置与证书轮换、安全的加入令牌、加密的集群存储、加密网络……

Linux 安全技术

内核命名空间：隔离

命名空间（namespaces）是构建容器的主要技术。和虚拟机对比一下：Hypervisor 虚拟化的是 CPU、磁盘等物理资源， 把虚拟 CPU、虚拟磁盘、虚拟网卡组合成看起来像物理机的虚拟机；命名空间虚拟化的是进程树、文件系统等操作系统结构， 把虚拟进程树、虚拟文件系统、虚拟网卡组合成看起来像普通操作系统的容器。

★ 命名空间只提供轻量隔离，不是强安全边界

和虚拟机相比，容器更高效，但虚拟机更安全。所以 Docker 还要叠加 cgroups、capabilities、seccomp 等技术来增强容器安全。

每个 Docker 容器都有自己的一组命名空间：

命名空间Docker 用它做什么
pid（进程 ID）每个容器有独立的进程树和自己的 PID 1，看不到其他容器和宿主机的进程
net（网络）每个容器有独立的网络栈：网卡、IP、端口范围、路由表。比如每个容器都有自己的 eth0
mnt（挂载 / 文件系统）每个容器有独立的根文件系统（自己的 /etc、/var、/dev），看不到宿主机和其他容器的文件系统
ipc（进程间通信）容器内的共享内存访问，并与宿主机和其他容器的共享内存隔离
user（用户）容器内的用户只在容器内有效，还可以把容器的 root 映射成宿主机上的普通用户
uts每个容器有自己的主机名

记住：容器就是一组被 Docker 组织起来、看起来像一个普通操作系统的命名空间。

💡 亲眼看看命名空间

在 Linux 主机上启动一个容器，找到它的主进程 PID（docker inspect -f '{{.State.Pid}}' 容器名），然后 sudo ls -l /proc/<PID>/ns，就能看到它所属的各个命名空间。 和 ls -l /proc/1/ns（宿主机的 init 进程）对比，编号都不一样。

控制组：限制

如果说命名空间管的是隔离，控制组（cgroups）管的就是限制。 把容器想象成酒店的房间：每个房间看起来是独立的，但它们共享供水、供电、空调、泳池、健身房、电梯、早餐…… 容器也一样，虽然彼此隔离，但共享宿主机的 CPU、内存、网络 I/O 和磁盘 I/O。 Docker 用 cgroups 限制每个容器对这些共享资源的使用，防止某个容器吃光资源、造成拒绝服务（DoS）。第 7 章的 --memory、--cpus 就是在设置 cgroups。

✨ 最新变化：cgroup v1 已弃用

现代 Linux 发行版都默认使用 cgroup v2（统一层级）。Docker Engine 29 已将 cgroup v1 支持标记为弃用（会保留到 2029 年 5 月）。如果你还在用很老的系统，请规划升级。

Capabilities：最小权限

Linux 的 root 用户权力极大，不应该用它来运行应用和容器。但简单地改用普通用户也不行 —— 大多数普通用户权限太小，几乎什么都干不了。 我们需要的是：让应用和容器恰好拥有它需要的权限，不多也不少。Capabilities 就是答案。

在底层，root 的权力其实是一长串 capabilities 的组合，比如：

Capability允许做什么
CAP_CHOWN修改文件所有者
CAP_NET_BIND_SERVICE绑定 1024 以下的端口
CAP_SETUID提升进程的权限级别
CAP_SYS_BOOT重启系统
……还有几十项

Docker 可以让容器以 root 启动，但去掉所有不需要的 capabilities。比如容器只需要绑定低端口，那就启动后丢掉所有 capabilities，再只加回 CAP_NET_BIND_SERVICE。 这是最小权限原则的完美体现。Docker 还会阻止容器重新加回被丢弃的 capabilities。 

$ docker run -d --cap-drop ALL --cap-add NET_BIND_SERVICE -p 80:80 my-web-app

Docker 默认已经去掉了很多危险的 capabilities，但生产应用最好自己配置。不过自定义需要大量工作和测试。

强制访问控制（MAC）

Docker 支持 Linux 主流的 MAC 技术 AppArmor 和 SELinux。根据发行版不同，Docker 会给所有新容器应用默认的 AppArmor 或 SELinux 配置文件。 按照 Docker 文档的说法，默认配置“提供适度的保护，同时兼顾广泛的应用兼容性”。你可以让容器不使用这些策略，也可以编写自己的策略 —— 同样很强大，但需要大量工作和测试。

seccomp：限制系统调用

应用通过系统调用（syscall）请求 Linux 内核做事。Linux 有 300 多个系统调用，Docker 用 seccomp 限制容器能向内核发起哪些调用， 默认配置禁用了其中大约 40–50 个危险的调用，在不影响兼容性的前提下提供适度安全。 你可以自定义 seccomp 配置，或者让容器不使用它。可惜系统调用表很长，自定义 seccomp 策略对很多人来说可能过于复杂。

小结：Linux 安全技术

Docker 支持大部分重要的 Linux 安全技术，并提供了“加了安全又不会太束手束脚”的默认值。其中一些技术需要内核知识，定制起来可能很复杂，但默认配置已经是很好的起点。

搭建一个安全的 swarm

你需要三台能用名字互相 ping 通的 Docker 主机，示例中叫 mgr1、mgr2、wrk1。在 mgr1 上：

$ docker swarm init
Swarm initialized: current node (7xam...662z) is now a manager.

就这一条命令，你已经配置了：加密的集群 ID、加密的集群存储、一个证书轮换周期为 90 天的 CA、一组用于加入管理节点和工作节点的安全令牌， 并给当前管理节点配置了用于双向 TLS 的客户端证书。这个 CA 只用于 Swarm 内部安全，不要把它挪作他用。 

mgr1 $ docker swarm join-token manager
To add a manager to this swarm, run the following command:
    docker swarm join --token SWMTKN-1-1dmtwu...r17stb-2axi5...8p7glz 172.31.5.251:2377

mgr2 $ docker swarm join --token SWMTKN-1-1dmtwu...r17stb-2axi5...8p7glz 172.31.5.251:2377
This node joined a swarm as a manager.

mgr1 $ docker swarm join-token worker
    docker swarm join --token SWMTKN-1-1dmtw...17stb-ehp8g...w738q 172.31.5.251:2377

wrk1 $ docker swarm join --token SWMTKN-1-1dmtw...17stb-ehp8g...w738q 172.31.5.251:2377
This node joined a swarm as a worker.

mgr1 $ docker node ls
ID                 HOSTNAME   STATUS   AVAILABILITY   MANAGER STATUS
7xamk...ge662z *   mgr1       Ready    Active         Leader
ailrd...ofzv1u     wrk1       Ready    Active
i0ue4...zcjm7f     mgr2       Ready    Active         Reachable

管理节点做了高可用，集群存储复制到了两个管理节点上；工作节点是 swarm 的一员，但不能访问集群存储。现实中请始终使用 3 或 5 个管理节点。

TLS 与双向认证

Docker 给每个管理节点和工作节点颁发一张客户端证书，用于双向认证。证书标识了节点身份、所属 swarm 以及它是管理节点还是工作节点：

$ sudo openssl x509 -in /var/lib/docker/swarm/certificates/swarm-node.crt -text
Certificate:
    Data:
        Signature Algorithm: ecdsa-with-SHA256
        Issuer: CN = swarm-ca
        Validity
            Not Before: Sep 22 08:23:00 2026 GMT
            Not After : Dec 21 09:23:00 2026 GMT                 <<---- 90 天有效期
        Subject: O = tcz3w1t7yu0s4wacovn1rtgp4,                  <<---- O  = Swarm ID
                 OU = swarm-manager,                             <<---- OU = 节点角色
                 CN = 2gxz2h1f0rnmc3atm35qcd1zw                  <<---- CN = 节点 ID

这些值可以和 docker info 的输出对上（ClusterID 对应 O，Is Manager 对应 OU，NodeID 对应 CN，CA Configuration → Expiry Duration 对应有效期）。

CA 配置与集群存储

$ docker swarm update --cert-expiry 720h      # 把证书轮换周期改成 30 天
$ docker swarm ca --rotate                    # 轮换根 CA
$ docker swarm init --external-ca …           # 新建 swarm 时使用外部 CA

Swarm 允许节点提前续期证书，避免所有节点在同一时刻更新。

集群存储保存着 swarm 的配置和状态，overlay 网络和机密等功能也依赖它 —— 这就是 overlay 网络和很多高级安全功能只能在 swarm 模式下用的原因。 集群存储基于流行的 etcd 分布式数据库（Raft），自动加密并复制到所有管理节点。日常维护 Docker 会处理，但生产集群一定要有可靠的备份和恢复方案。 还可以开启 docker swarm update --autolock=true，让管理节点重启后必须提供解锁密钥才能解密集群存储。

漏洞扫描与加固镜像

每个容器都运行着多个软件包，而这些包都可能有被攻击者利用的缺陷和漏洞。 镜像扫描会分析镜像，列出它用到的所有软件包，这份清单叫软件物料清单（SBOM）； 扫描系统再把 SBOM 和已知漏洞数据库比对，给出漏洞报告，大多数扫描器还会给漏洞评级并提供修复建议。漏洞扫描已经是软件供应链中不可或缺的一环。

$ trivy image nigelpoulton/tu-demo:latest     # 开源替代：Trivy，结果类似

漏洞扫描虽好，但它只扫描镜像，发现不了网络、节点或编排器的安全问题。而且扫描器水平参差不齐：好的会做深入的二进制级扫描，差的只看包名。 最后提醒一句：知道了漏洞，就有责任去修复或缓解它。

✨ 最新变化：Docker Hardened Images 免费了

与其扫描出一堆漏洞再去修，不如一开始就用干净的基础镜像。Docker Hardened Images（DHI）是 Docker 维护的精简、加固、持续打补丁的基础镜像， 通常只有极少甚至零已知漏洞，并附带 SBOM、来源证明和签名。自 2025 年 12 月起 DHI 对所有人免费（需要合规认证或 SLA 保障的企业版仍收费）。 用法和普通镜像一样，只是把 FROM 换成 DHI 目录里的对应镜像；Docker Desktop 还提供了 dhictl CLI 插件。 同类选择还有 Google 的 distroless、Chainguard Images 等。

签名与验证镜像

镜像签名解决的问题是：我拉到的镜像，真的是它声称的发布者发布的吗？中途有没有被篡改？这在通过互联网这样的不可信网络拉取镜像时尤为重要。

Docker Content Trust（已退役）

原书用 Docker Content Trust（DCT）演示镜像签名：用 docker trust key generate 生成密钥对，docker trust signer add 把密钥关联到仓库， docker trust sign 签名并推送，再 export DOCKER_CONTENT_TRUST=1 强制只拉取签过名的镜像。

⚠ DCT 已经退役，不要再用
  • DCT 依赖的 Notary v1 是 2015 年的 TUF 实现，上游早已停止维护，只有不到 0.05% 的 Docker Hub 拉取用到它。
  • Docker 于 2025 年宣布退役 DCT：Docker Engine 29 已从 CLI 中移除 DCT，notary.docker.io 从 2026 年 7 月起分阶段停服，将于 2026 年 12 月 8 日彻底关闭。
  • 官方迁移建议：取消 DOCKER_CONTENT_TRUST 环境变量；用摘要固定镜像（第 6 章）；改用 OCI 原生的签名工具 Sigstore Cosign 或 Notary Project 的 Notation。

现代做法：用 Cosign 签名

Sigstore / Cosign 和 Notation 都把签名作为 OCI 制品和镜像存放在同一个仓库里，不需要额外维护一套信任基础设施。 Cosign 对开发者更友好，支持基于 OIDC 身份的“无密钥（keyless）”签名和透明日志；Notation 更偏规范化，支持多签名并能对接现有 PKI。下面用 Cosign 演示最基本的基于密钥的流程： 

# 1. 生成密钥对（会提示输入私钥密码，生成 cosign.key 和 cosign.pub）
$ cosign generate-key-pair

# 2. 推送镜像，并用摘要（而不是标签）签名
$ docker push nigelpoulton/ddd-trust:signed
$ cosign sign --key cosign.key nigelpoulton/ddd-trust@sha256:b65f9a1aa4e6...

# 3. 使用者用公钥验证
$ cosign verify --key cosign.pub nigelpoulton/ddd-trust:signed
Verification for index.docker.io/nigelpoulton/ddd-trust:signed --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key

在 CI（如 GitHub Actions）里更推荐无密钥签名：cosign sign nigelpoulton/ddd-trust@sha256:…，Cosign 会用 CI 的 OIDC 身份签名，验证时检查签名者身份即可，不用保管任何私钥。

💡 附赠：给镜像附上 SBOM 和来源证明

BuildKit 可以在构建时生成证明（attestations）并随镜像一起推送： docker buildx build --sbom=true --provenance=mode=max -t 镜像 --push .。 SBOM 记录镜像里有哪些软件，来源证明（provenance）记录镜像是怎么、在哪里、用什么源码构建的 —— 这些都是现代软件供应链安全（如 SLSA）的基础。

Docker 机密

大多数应用都会用到密码、证书、SSH 密钥这类敏感数据。千万别把它们写进镜像、环境变量或 Compose 文件里！Docker 提供了机密（secrets）来安全地保管它们。

ⓘ 注意

Swarm 的机密功能依赖集群存储，因此只能在 swarm 模式下使用。单机 Compose 也支持一种基于文件的 secrets（见下文）。

  1. 你创建机密；
  2. Docker 把它存进加密的集群存储；
  3. 你创建服务（或更新服务），并授权它访问这个机密；
  4. Docker 把机密发送给服务副本时，在网络上加密传输；
  5. Docker 把机密以未加密文件的形式挂载到副本的内存文件系统里（默认在 /run/secrets/），应用直接读取即可，不需要解密密钥。

其他服务的副本无法访问这个机密。使用它的副本一结束，Docker 就销毁内存文件系统、把机密从节点上清除。

$ printf 'S3cr3t!' | docker secret create db_pw -       # 从标准输入创建，避免留在 shell 历史里
$ docker secret ls
$ docker service create --name db --secret db_pw \
    -e POSTGRES_PASSWORD_FILE=/run/secrets/db_pw postgres:17

很多官方镜像（postgres、mysql、mariadb……）都支持 *_FILE 形式的环境变量，专门用来从文件读取机密。在 Compose 文件里也可以声明机密，单机 Compose 会把本地文件以只读方式挂载进去：

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_pw
    secrets:
      - db_pw
secrets:
  db_pw:
    file: ./db_pw.txt        # 记得把它加进 .gitignore

构建阶段需要的机密（比如私有 npm 仓库的令牌）则用第 8 章讲过的 RUN --mount=type=secret，它们不会留在任何镜像层里。

实用加固清单

原书没有单独总结，但下面这些参数和做法在生产中非常常用，建议对照检查：

$ docker run -d --name hardened \
    --user 1000:1000 \
    --read-only \
    --tmpfs /tmp \
    --cap-drop ALL \
    --cap-add NET_BIND_SERVICE \
    --security-opt no-new-privileges \
    --memory 256m --cpus 0.5 --pids-limit 100 \
    -p 127.0.0.1:8080:8080 \
    my-app@sha256:<摘要>
参数作用
--user 1000:1000不以 root 运行
--read-only + --tmpfs /tmp根文件系统只读，需要写的目录单独给 tmpfs
--cap-drop ALL --cap-add …去掉所有 capabilities，只加回需要的
--security-opt no-new-privileges禁止进程再提权（例如通过 setuid 程序）
--memory / --cpus / --pids-limit资源上限，防止 DoS 和 fork 炸弹
-p 127.0.0.1:…只在本机发布端口
镜像@sha256:…用摘要固定镜像，确保运行的就是验证过的那一个
层面做法
镜像用官方 / Hardened / distroless 等精简基础镜像；多阶段构建；定期重建以获取补丁；扫描漏洞；签名并验证
构建.dockerignore；不把机密写进 ARG/ENV；用 --mount=type=secret；生成 SBOM 和来源证明
运行非 root 用户；只读根文件系统；最小 capabilities；no-new-privileges；资源限制；绝不随意使用 --privileged
主机及时升级 Docker 和内核；谨慎授予 docker 组权限；考虑 rootless 模式或 userns-remap；不要把 /var/run/docker.sock 挂进不可信的容器
网络自定义网络隔离不同应用；只发布必要端口；Swarm 中对敏感流量使用加密 overlay
⚠ 两个最常见的“后门”

--privileged 几乎关闭了本章讲的所有防护；把 /var/run/docker.sock 挂进容器，等于把宿主机的 root 权限交给了这个容器。 两者都只应该在你完全清楚后果、并且信任容器内程序的情况下使用。

清理

$ docker service rm db
$ docker secret rm db_pw
$ unset DOCKER_CONTENT_TRUST          # 如果你以前设置过
$ docker swarm leave -f               # 在所有节点上执行，最后处理管理节点

本章小结

  • Docker 支持所有主要的 Linux 安全技术：命名空间（隔离）、cgroups（限制）、capabilities（最小权限）、MAC（AppArmor/SELinux）、seccomp（系统调用过滤），并提供合理的默认值。
  • Swarm 开箱即安全：加密节点 ID、双向 TLS、自动轮换的证书、安全的加入令牌、加密的集群存储。
  • 漏洞扫描基于 SBOM 比对已知漏洞；使用 Docker Hardened Images 等加固镜像可以从源头减少漏洞。
  • Docker Content Trust 已退役，应改用 Sigstore Cosign 或 Notation 签名和验证镜像，并用摘要固定镜像。
  • Docker 机密把敏感数据加密存储、加密传输，只以内存文件的形式提供给被授权的服务。
  • 运行时加固：非 root、只读根文件系统、最小 capabilities、no-new-privileges、资源限制，远离 --privileged 和 docker.sock 挂载。

✎ 动手练习

  1. 运行 docker run --rm alpine sh -c 'cat /proc/self/status | grep Cap' 和加上 --cap-drop ALL 的版本，对比 CapEff 的值（可以用 capsh --decode= 解码）。
  2. 用 --read-only 启动一个 nginx，观察它为什么启动失败，然后用 --tmpfs 给它需要写的目录（/var/cache/nginx、/var/run）解决问题。
  3. 用 Trivy 或 Docker Scout 扫描 python:3.13 和 python:3.13-slim，比较漏洞数量。
  4. 安装 Cosign，给你推送到 Docker Hub 的一个镜像签名，然后验证它；再推一个新版本覆盖同一个标签，看看验证结果如何变化。

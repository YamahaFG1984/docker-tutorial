第 10 章

Docker 与 AI

想在自己电脑上跑大语言模型（LLM），又不想把数据发给云端？Docker 提供了 Docker Model Runner（DMR）： 像拉镜像一样拉模型，像跑容器一样跑模型，再通过 OpenAI 兼容的 API 接入你的应用和 Compose 项目。

本章目标

  • 理解 DMR 为什么在容器之外运行模型
  • 理解 DMR 的架构：推理后端、API 端点、模型存储、OCI 模型制品
  • 会用 docker model 拉取、查看、运行、删除模型
  • 用 curl 调用 DMR 的 OpenAI 兼容 API
  • 用 Compose 的 models: 语法部署一个依赖大模型的聊天应用
  • 把 Open WebUI 之类的第三方应用接到 DMR 上
✨ 本章相对原书的主要更新
  • DMR 已从 Docker Desktop 的“开发中功能”变为正式功能，并支持 Linux 上的 Docker Engine。
  • 推理后端从只有 llama.cpp，扩展到 llama.cpp、vLLM、Diffusers。
  • API 除了 OpenAI 兼容，还提供 Anthropic 兼容和 Ollama 兼容端点。
  • Compose 中声明模型的写法从 provider: type: model 改为顶层 models: 元素。

为什么要在本地跑模型

Docker 提供两种部署 AI 应用的方式：Docker Model Runner（推荐）和把模型服务放进容器。两者都是在本地运行模型，适合这些场景：

🔒

隐私

数据不出本机，适合有合规要求的企业。

💰

成本可控

没有按 token 计费的云账单。

⚡

低延迟

不走网络，适合对延迟敏感的应用。

🔧

完全掌控

自由定制提示词、上下文长度，甚至微调。

DMR 的设计思路：模型跑在容器外面

是的，你没看错：Docker Model Runner 是在容器之外执行 AI 模型的！原因是容器很难访问 GPU、NPU、TPU 这些让模型跑得飞快的 AI 加速硬件 —— 它们大多是各厂商私有的，有各自的驱动和 SDK，Docker 和整个生态很难为每一种都开发并维护支持。

没错，装了 NVIDIA Container Toolkit 之后，容器可以访问较新的 NVIDIA GPU。但它安装复杂，而且只支持 NVIDIA 的 CUDA GPU。 把模型放在容器外执行，DMR 两全其美：

  • 和 Docker 工具链及整个云原生生态无缝集成；
  • 更容易用上宿主机的 AI 加速硬件（Mac 的 Apple 芯片 GPU、NVIDIA/AMD GPU 等）。

DMR 的架构

逐块解读：

  • DMR 进程：在 Docker Desktop 上，它是独立于 Docker 引擎的宿主机进程；对 Mac 用户来说，这意味着它跑在 Docker Desktop 虚拟机之外，可以直接访问 GPU。 在 Linux 的 Docker Engine 上，它以一个专门配置、可访问 GPU 的组件形式运行。
  • 可插拔推理后端：真正加载和执行模型、提供推理的核心引擎。默认是 llama.cpp（到处都能跑，适合本地开发）； vLLM 面向高吞吐的生产场景（需要 NVIDIA GPU）；Diffusers 用于图像生成。
  • API 端点：一组模型管理端点，加上 OpenAI、Anthropic、Ollama 兼容的推理端点。容器、本机程序、其他主机都能访问。
  • 模型存储：模型从 Docker Hub 等 OCI 仓库拉取，存放在本地（~/.docker/models），通常有好几个 GB。
  • CLI：docker model 插件负责拉取、推送、运行、管理模型。

DMR vs Ollama vs LM Studio

如果你已经在用本地模型，会发现 DMR 和 Ollama、LM Studio 很像：它们都可以用 llama.cpp 作为核心推理引擎，都能提供 OpenAI 风格的端点，核心功能和性能都差不多。 DMR 的优势在于和 Docker 工具链、Compose、Docker Hub 以及整个云原生生态的无缝集成。如果你已经在用 Docker，或打算用 Docker，就值得认真考虑 DMR， 这样可以把工具和生态合并到一处。当然，引入任何新工具前，都应该对照自己的需求做测试。

启用 Docker Model Runner

平台要求启用方式
macOSApple 芯片Docker Desktop → Settings → AI → 勾选 Enable Docker Model Runner； 如需从本机程序访问，再勾选 Enable host-side TCP support（默认端口 12434）→ Apply
WindowsNVIDIA GPU（或 Qualcomm Adreno 等）
LinuxDocker Engine；可选 NVIDIA / AMD / Vulkan GPUsudo apt-get install docker-model-plugin（第 3 章已介绍官方软件源）

没有受支持的 GPU 也没关系，DMR 也能在 CPU 上运行，只是慢一些。也可以用命令行启用 Desktop 里的 DMR：

$ docker desktop enable model-runner --tcp 12434

验证是否正常运行：

$ docker model status
Docker Model Runner is running

Status:
llama.cpp: running llama.cpp latest-metal (sha256:ad58230f548...) version: a0f7016

输出说明 DMR 正在运行，使用 llama.cpp 作为推理后端，而 llama.cpp 又通过 Apple 的 Metal API 让模型用上了 MacBook 的 GPU。

$ git clone https://github.com/nigelpoulton/ddd-book.git
$ cd ddd-book/dmr

探索 Docker Model Runner

从 Docker Hub 拉取模型

Docker 在 Docker Hub 的 ai 命名空间下维护了一个模型目录。点击某个模型能看到它的模型卡片： 架构、训练截止日期、各种变体，甚至基准测试数据（这些数据来自模型发布方，你仍应针对自己的需求自行测试）。

下面拉取一个量化（quantized）版的 Gemma3 4B 模型。量化是一种在不太损失准确度和性能的前提下缩小模型体积的方法。即便量化后，模型也常常有好几个 GB，下载需要一些时间： 

$ docker model pull ai/gemma3:4B-Q4_K_M
Downloaded: 2.31 GB
Model pulled successfully

$ docker model ls
MODEL NAME            PARAMETERS  QUANTIZATION     ARCHITECTURE  MODEL ID      SIZE
ai/gemma3:4B-Q4_K_M   3.88 B      IQ2_XXS/Q4_K_M   gemma3        0b329b335467  2.31 GiB
💡 看懂模型标签

ai/gemma3:4B-Q4_K_M 里：4B 表示约 40 亿参数；Q4_K_M 是量化方式（大约每个参数 4 bit，K_M 是 llama.cpp 的一种量化变体）。 参数越多通常越聪明但越慢、越占内存；量化位数越低越小越快但精度越差。入门可以先试 ai/smollm2、ai/qwen3:0.6B-Q4_K_M 这类很小的模型。

模型也是 OCI 制品

DMR 从 Docker Hub 拉取的模型，是以一种新的 OCI 制品形式存储和分发的（遵循 Docker 的 model-spec）。看看它的 manifest：

$ docker manifest inspect ai/gemma3:4B-Q4_K_M
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",        <<--- 标准 OCI manifest
  "config": {
    "mediaType": "application/vnd.docker.ai.model.config.v0.1+json", <<--- 模型配置
    "size": 372,
    "digest": "sha256:22273fdf4e6dbaf...af0e6569be41539"
  },
  "layers": [
    {
      "mediaType": "application/vnd.docker.ai.gguf.v3",              <<--- 模型权重（GGUF 文件）
      "size": 2489757856,
      "digest": "sha256:09b370de51ad3...fc96ab2dc1adaa7"
    },
    {
      "mediaType": "application/vnd.docker.ai.license",              <<--- 许可证
      "size": 8346,
      "digest": "sha256:a4b03d96571f0...dc90e3f960823e5"
    }
  ]
}

拉取模型时，DMR 读取 manifest，拉取 config 和两个层，以 SHA 为文件名存入本地模型存储，你可以直接查看：

$ ls -lh ~/.docker/models/blobs/sha256
-rw-r--r--@ 1  2.3G 09b370de51ad3bde8c3aea...667ddbafc96ab2dc1adaa7   <<---- 模型文件 (GGUF)
-rw-r--r--@ 1  372B 22273fd2f4e6dbaf5b5dae...308eb0faf0e6569be41539   <<---- 模型配置 JSON
-rw-r--r--@ 1  8.2K a4b03d96571f0ad98b1253...328909bdc90e3f960823e5   <<---- 许可证

$ docker model inspect ai/gemma3:4B-Q4_K_M       # 更友好的查看方式

把模型打包成 OCI 制品，意味着可以直接复用企业里已有的公共和私有 OCI 仓库 —— 它们本来就存着容器镜像、签名、SBOM、OPA 策略、Helm Chart、Wasm 模块、MCP 工具…… 现在再加上 AI 模型，就不用为模型单独建一套存储了。你也可以用 docker model package 把自己的 GGUF 文件打包，再 docker model push 推到仓库。

测试模型

最简单的测试方式是命令行。可以一次性提问，也可以进入交互式 REPL：

$ docker model run ai/gemma3:4B-Q4_K_M "用一句话介绍 Docker"
Docker 是一个把应用及其依赖打包进可移植容器、让它在任何环境中一致运行的平台。

$ docker model run ai/gemma3:4B-Q4_K_M
Interactive chat mode started. Type '/bye' to exit.
> How long is a day on Mars?
A day on Mars, also known as a "sol," is about 24 hours, 39 minutes, and 35 seconds long...
> /bye

Docker Desktop 也提供了图形界面：点击左侧导航栏的 Models，选择一个模型即可开始聊天，而且会保留对话上下文。

调用 DMR 的 API

DMR 提供一组原生的模型管理端点，以及多套兼容主流厂商格式的推理端点：

类别端点方法
DMR 模型管理/modelsGET
/models/createPOST
/models/{namespace}/{name}GET、DELETE
OpenAI 兼容/engines/v1/modelsGET
/engines/v1/chat/completionsPOST
/engines/v1/completionsPOST
/engines/v1/embeddingsPOST
Anthropic 兼容/anthropic/v1/messagesPOST
Ollama 兼容/api/tags、/api/chat、/api/generateGET / POST

从哪里访问，用哪个基础地址：

先列出可用模型，确认 API 里用的模型名：

$ curl -s localhost:12434/engines/v1/models | jq
{
  "object": "list",
  "data": [
    { "id": "ai/gemma3:4B-Q4_K_M", "object": "model", "created": 1742979452, "owned_by": "docker" }
  ]
}

然后向 OpenAI 兼容的 chat/completions 端点发送问题：

$ curl -s http://localhost:12434/engines/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
      "model": "ai/gemma3:4B-Q4_K_M",
      "messages": [
        { "role": "system", "content": "Keep your responses to one sentence only." },
        { "role": "user",   "content": "How long is a day on Mars?" }
      ],
      "temperature": 0.7,
      "max_tokens": 500
    }' | jq -r '.choices[0].message.content'
A day on Mars, also known as a sol, is approximately 24.6 hours long.
  • model：要用的模型名；
  • messages：system 消息告诉模型怎么回答（这里要求只回答一句话），user 消息是你的问题；
  • temperature：创造性，通常在 0–1 之间，0 最可预测，1 最有创意；
  • max_tokens：限制回答长度。

如果 DMR 有多个推理后端，可以在路径里指定，例如 /engines/llama.cpp/v1/chat/completions。

★ 这意味着什么

因为端点和 OpenAI API 格式兼容，任何用 OpenAI SDK 写的程序，只要把 base_url 改成 DMR 的地址，就能改用本地模型，代码几乎不用动。 本章的聊天应用后端就是这么做的：AsyncOpenAI(base_url=MODEL_HOST, api_key="not-needed")。

在 Compose 中使用 DMR

现在用 Compose 部署一个以 DMR 作为推理服务的聊天应用。它有三部分：

用 2026 年的 Compose 语法，这个应用的 Compose 文件这样写：

services:
  frontend:
    build: ./frontend
    ports:
      - "3000:3000"
    depends_on:
      - backend

  backend:
    build: ./backend
    ports:
      - "8000:8000"
    models:                          # 声明这个服务要用哪个模型
      llm:
        endpoint_var: MODEL_HOST     # 把模型的 API 地址注入到这个环境变量
        model_var: LLM_MODEL_NAME    # 把模型名注入到这个环境变量

models:                              # 顶层：定义应用需要的模型
  llm:
    model: ai/gemma3:4B-Q4_K_M
    context_size: 8192               # 可选：上下文长度

Compose 的 models 有两种服务级写法：

短写法：自动生成变量名
services:
  app:
    image: my-app
    models:
      - llm
# 注入 LLM_URL、LLM_MODEL
长写法：自定义变量名
services:
  app:
    image: my-app
    models:
      llm:
        endpoint_var: AI_MODEL_URL
        model_var: AI_MODEL_NAME
✨ 与原书的写法对比

原书（以及作者仓库里的 dmr/compose.yaml）使用的是早期的 provider 写法：一个名为 dmr 的“假服务”，其他服务通过 depends_on: [dmr] 依赖它， 模型地址则写在 .env 里：

  dmr:
    provider:
      type: model
      options:
        model: ${LLM_MODEL_NAME}

新的 models: 顶层元素让模型成为 Compose 的一等公民：不再需要假服务，地址和模型名也会自动注入。 如果你用的是较老的 Compose 版本，仓库里的原文件仍然可以运行。

部署应用：

$ docker compose up --build --detach
[+] Building 3.3s (25/25) FINISHED
[+] Running 5/5
 ✔ backend                    Built
 ✔ frontend                   Built
 ✔ Network dmr_default        Created
 ✔ Container dmr-backend-1    Started
 ✔ Container dmr-frontend-1   Started

Docker 自动为项目创建了一个叫 default 的网络，构建前端和后端镜像，确保模型可用后依次启动服务。 打开 http://localhost:3000 就可以和聊天机器人对话了。它会保留对话历史、根据前文推断上下文；输入框下方的小字显示的是 DMR 正在使用的模型名。

ⓘ 连接远程 DMR

后端的 MODEL_HOST 也可以指向另一台机器上的 DMR：http://<主机>:12434/engines/v1。这时就不要用 models: 声明了，直接用 environment: 设置变量即可。

接入第三方应用：Open WebUI

理论上，任何支持 OpenAI 兼容接口的第三方应用都能接入 DMR。Open WebUI 是一个流行的开源 AI 平台， 和 DMR 组合起来，就能得到一个外观和体验都接近 ChatGPT、Claude 的本地聊天机器人。 

$ docker model pull ai/qwen3:0.6B-Q4_K_M       # 再拉一个小模型，方便在界面里切换
$ docker model ls
MODEL NAME             PARAMETERS  QUANTIZATION     ARCH    MODEL ID      SIZE
ai/gemma3:4B-Q4_K_M    3.88 B      IQ2_XXS/Q4_K_M   gemma3  0b329b335467  2.31 GiB
ai/qwen3:0.6B-Q4_K_M   751.63 M    IQ2_XXS/Q4_K_M   qwen3   18e5114fc13b  456.11 MiB

services:
  open-webui:
    image: ghcr.io/open-webui/open-webui:main
    environment:
      - WEBUI_AUTH=False
      - OPENAI_API_KEY=na              # DMR 不需要密钥，随便填
    volumes:
      - open-webui:/app/backend/data   # 保存配置和对话记录
    ports:
      - "3001:8080"
    restart: always
    models:
      llm:
        endpoint_var: OPENAI_API_BASE_URL
        model_var: DEFAULT_MODELS

models:
  llm:
    model: ai/qwen3:0.6B-Q4_K_M

volumes:
  open-webui:

$ cd ../openwebui
$ docker compose up -d

Open WebUI 镜像接近 6GB，首次拉取可能要一阵子；第一次启动时它还要在后台下载一些文件，这时访问可能会看到 500: Internal Error，等一会儿即可。 然后打开 http://localhost:3001：

  • 用左上角的模型选择器在 DMR 已下载的模型之间切换；
  • 点击左下角用户 → Settings → General，设置一个 system prompt，比如 “Give simple answers. Limit responses to two sentences.”，让回答更符合你的需要；
  • 提问“月亮离地球多远？”，接着问“那太阳呢？”—— 它能理解第二个问题是承接上一个的。对话会保存在左侧导航栏里。

把模型放进容器（不推荐）

把模型服务放在容器里运行已经不推荐了，这里只做简单介绍。前面说过，容器里只能访问装了 NVIDIA Container Toolkit 的 CUDA GPU； 如果宿主机是其他厂商的 GPU、NPU、TPU，容器里的模型只能慢吞吞地跑在 CPU 上。

作者仓库的 ai-compose 目录有一个类似的三层聊天应用，只是把 DMR 换成了一个容器化的 Ollama 服务（compose.yaml 用 CPU，gpu-compose.yaml 用 NVIDIA GPU）： 

  ollama:
    image: nigelpoulton/gsd-book:chat-model
    volumes:
      - ollama_data:/root/.ollama
    environment:
      - MODEL=${MODEL:-mistral:latest}
    deploy:
      resources:
        limits:
          memory: 8G

它同样映射 3000 端口，会和前面的聊天应用冲突。如果真想运行，先修改端口。

清理

# 在 openwebui 目录：删除 Open WebUI 应用及其镜像、网络和卷（不会停用 DMR，也不会删模型）
$ docker compose down --rmi all --volumes

# 在 dmr 目录：删除聊天应用
$ docker compose down --rmi all --volumes

# 删除模型
$ docker model rm ai/qwen3:0.6B-Q4_K_M ai/gemma3:4B-Q4_K_M

要彻底停用 DMR，在 Docker Desktop 的 Settings → AI 中取消勾选 Enable Docker Model Runner。

本章小结

  • Docker Model Runner 是用 Docker 运行本地 AI 模型的推荐方式：模型在容器之外、直接在宿主机硬件上执行，能用上更多种类的 AI 加速硬件。
  • DMR 按需加载和卸载模型，通过 OpenAI / Anthropic / Ollama 兼容端点提供服务，推理后端可插拔（llama.cpp、vLLM、Diffusers）。
  • 模型以 OCI 制品的形式存储和分发，可以复用现有的镜像仓库。
  • DMR 与 Docker CLI、Docker Hub、Compose 深度集成：用顶层 models: 声明模型，Compose 会把地址和模型名注入到服务的环境变量里。
  • 仍然可以在容器里跑 Ollama 等模型服务，但通常更慢，能用的加速硬件也更少。

✎ 动手练习

  1. 拉取 ai/smollm2，用 docker model run 问它几个问题；再用 curl 调用 /engines/v1/chat/completions，对比 temperature 为 0 和 1 时回答的差异。
  2. 用任意语言的 OpenAI SDK 写一个十几行的小程序，把 base_url 设为 http://localhost:12434/engines/v1，调用本地模型。
  3. 把作者仓库里的 dmr/compose.yaml 改写成本章的 models: 新语法并部署；进入 backend 容器执行 env | grep MODEL，看看注入了哪些变量。

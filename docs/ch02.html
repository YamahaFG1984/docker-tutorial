第 2 章

Docker 与容器标准

“Docker”这个词到底指什么？一家公司？一个命令？一个平台？本章先把这个名字拆清楚， 再认识几个塑造整个容器生态的组织和标准：OCI、CNCF 和 Moby。这些是后面所有章节的地基。

本章目标

  • 区分“Docker 公司”和“Docker 平台”
  • 理解 Docker 的客户端 / 服务端（引擎）架构
  • 知道 OCI 的三个规范分别管什么，以及为什么标准如此重要
  • 了解 CNCF 和 Moby 项目在生态中的角色
  • 对 2026 年 Docker 的产品全家桶有个整体印象

“Docker”的两层含义

当人们说“Docker”时，可能指两件事：

  1. Docker 平台：一套打包好的技术，用来创建、管理和编排容器。你敲的 docker 命令就属于它。
  2. Docker 公司（Docker, Inc.）：创造了 Docker 平台、并持续推动它发展的那家公司。

Docker 公司

Docker 公司总部位于美国加州帕洛阿尔托，由法裔美国开发者 Solomon Hykes 创立（他后来离开了公司）。

这家公司最早是一个叫 dotCloud 的 PaaS（平台即服务）提供商。dotCloud 在幕后用容器来交付服务， 并且开发了一个内部工具来部署和管理这些容器，这个工具就叫 Docker。 “Docker”是英式英语里 dock worker（码头装卸工）的简称 —— 就是在码头上把货物装上船、卸下船的人。 这个名字和 Docker 的鲸鱼驮着集装箱的 Logo 完美呼应：Docker 做的，就是把软件装进标准“集装箱”再运走。

2013 年，dotCloud 砍掉了经营困难的 PaaS 业务，更名为 Docker, Inc.，全力把 Docker 和容器推向世界。

💡 集装箱的比喻

在标准集装箱出现之前，货轮装货要一件件搬，不同形状的货物各有各的装法。标准集装箱出现后，不管里面装的是香蕉还是汽车零件， 起重机、货轮、卡车都用同样的方式搬运它。容器之于软件，就像集装箱之于货物： 不管里面是 Java、Python 还是 Go 程序，Docker 都用同样的方式构建、分发和运行它。

Docker 技术：客户端与引擎

Docker 平台让构建、分享和运行容器变得简单。从高处看，它由两大部分组成：

  • CLI（客户端）：就是你熟悉的 docker 命令行工具。它把你输入的简单命令翻译成 API 请求，发给引擎。
  • 引擎（服务端）：所有在服务器端运行和管理容器的组件的统称，核心是一个叫 dockerd 的守护进程（daemon）。

在后面的章节里你会看到，客户端和引擎内部其实都由很多小而专的组件组成，非常复杂。但客户端把这些复杂性全藏起来了： 你只需输入友好的 docker 命令，CLI 把它变成 API 请求发给守护进程，剩下的事守护进程全包了。

容器标准与组织

有几个重要的标准和治理组织深刻影响着容器生态，本章介绍其中三个：

OCI：开放容器倡议

开放容器倡议（OCI）是负责制定底层容器标准的治理委员会，隶属于 Linux 基金会。

它的诞生有一段小插曲。容器生态早期，CoreOS 公司的一些人不满 Docker 一家独大，于是创建了另一套开放标准 appc， 定义了镜像格式和容器运行时等规范，还做了一个参考实现叫 rkt（读作 rocket）。 appc 和 Docker 的做法不同，整个生态一下子面临两套相互竞争的标准。

竞争通常是好事，但竞争的标准通常是坏事 —— 它会制造混乱、拖慢用户采用。好在主要玩家们坐到了一起， 成立了中立的、轻量的 OCI 来统一治理容器标准。appc 项目随后被归档，所有底层容器规范都归入 OCI 管理。

OCI 目前维护三个规范：

规范管什么Docker 里谁实现了它
image-spec
镜像规范		镜像长什么样：由哪些层、配置和清单（manifest）组成BuildKit 构建出的镜像符合 OCI 标准
runtime-spec
运行时规范		怎样把一个镜像“解包”并作为容器运行起来Docker 使用 runc（runtime-spec 的参考实现）
distribution-spec
分发规范		镜像仓库（registry）的 API：怎么推送、拉取镜像Docker Hub 是符合 OCI 标准的仓库
★ 铁轨的比喻

当铁轨的宽度和规格被标准化之后，造火车、造车厢、造信号系统、建站台的企业家们都有了信心：他们造出来的东西一定能在标准铁轨上用。 没有人想要互相竞争的轨距标准。OCI 规范对容器生态做了同样的事，此后整个生态蓬勃发展。 正因为有了 OCI，你用 Docker 构建的镜像可以推到任何仓库（Docker Hub、GHCR、阿里云 ACR……），也可以在任何平台（Kubernetes、Podman……）上运行。

这些底层规范演进得非常慢 —— 两个最初的规范在 2017 年 7 月发布 1.0，至今仍处于 1.x 版本。 稳定压倒一切，因为无数项目都依赖它们。Docker 公司是 OCI 的创始成员，至今仍有人在 OCI 技术监督委员会任职。

🔬 深入：OCI 标准现在不只装镜像

image-spec 1.1 引入了 artifactType 和 subject 字段，让 OCI 仓库可以存储任意制品（artifact）： 镜像签名、SBOM（软件物料清单）、Helm Chart、Wasm 模块，甚至第 10 章会讲到的 AI 模型。 “一个仓库装下一切”正在成为现实。

CNCF：云原生计算基金会

云原生计算基金会（CNCF）是 Linux 基金会旗下另一个对容器生态影响深远的组织，成立于 2015 年， 目标是“推进容器技术……让云原生计算无处不在”。

和 OCI 不同，CNCF 不制定规范，而是托管项目，比如 Kubernetes、containerd、Prometheus、Cilium 等。 “托管”的意思是为项目提供空间、组织结构和支持，帮助它们成长成熟。所有 CNCF 项目都要经历三个阶段：

Moby 项目

Docker 创建 Moby 项目，作为一个由社区主导的地方，让开发者可以构建专门的工具来搭建容器平台。 平台构建者可以从 Moby 中挑选需要的工具，甚至把 Moby 工具、自研工具和其他项目的工具混搭成自己的平台。

Moby 最早由 Docker 公司发起，现在的成员还包括微软、Mirantis、NVIDIA 等。 你可以把 Moby 理解为 Docker Engine 的开源上游：Docker Engine 的源码就在 github.com/moby/moby 仓库里。

★ 一句话记住三者关系

Docker 平台 = OCI 的标准 + CNCF 的项目（如 containerd）+ Moby 的零件（如 libnetwork、BuildKit）+ Docker 公司自己的产品。

本章小结

  • “Docker”既可以指 Docker 公司，也可以指 Docker 平台。公司前身是 dotCloud，2013 年更名。
  • Docker 平台由客户端（docker CLI）和引擎（服务端）组成，客户端把命令翻译成 API 请求发给引擎。
  • OCI 维护镜像、运行时、分发三个底层规范，保证了整个生态的互通；Docker 完整实现了这三个规范。
  • CNCF 托管 Kubernetes、containerd 等项目，并通过沙箱 → 孵化 → 毕业三阶段帮助它们成熟。
  • Moby 是构建容器平台的开源零件库，也是 Docker Engine 的开源上游。

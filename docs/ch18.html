第 18 章

用容器搭开发环境

新同事入职第一天，花一整天装 Node、Postgres、Redis，还装错了版本 —— 这种场景你一定不陌生。 本章从零搭一个真实的开发环境：一条 docker compose up 拉起应用、数据库和缓存，改代码立刻生效，还能断点调试； 最后再用 Dev Containers 把编辑器也搬进容器。

本章目标

  • 理解“开发环境容器化”解决什么问题，以及它和生产镜像的区别
  • 用一个 Dockerfile 的不同阶段（target）分别产出开发镜像和生产镜像
  • 用 Compose 编排应用 + Postgres + Redis，并处理好数据库初始化和启动顺序
  • 掌握两种热更新方式：绑定挂载和 docker compose watch，避开 node_modules 陷阱
  • 用 compose.override.yaml 区分开发与生产配置
  • 在容器里断点调试，并用 Dev Containers 获得“开箱即用”的编辑器环境

为什么要容器化开发环境

传统方式：每人手工装一遍
  • README 里写着十几步安装说明，总有一步过时
  • A 电脑上 Postgres 16，B 电脑上 Postgres 14
  • 两个项目要不同版本的 Node，来回切换
  • “在我电脑上是好的”
容器方式：环境即代码
  • git clone + docker compose up，几分钟就能开工
  • 版本写在 Compose 文件里，所有人完全一致
  • 每个项目各自的依赖互不干扰，电脑上什么都不用装
  • 开发环境和生产环境用同一套镜像基础

本章的示例项目是一个小型 Node.js API（记录待办事项），依赖 Postgres 存数据、Redis 做缓存。整体结构如下：

一个 Dockerfile，两个目标

开发镜像和生产镜像的需求正好相反：开发时要所有依赖（包括 nodemon 等开发工具）和调试能力，生产时要最小、最安全。用多阶段构建（第 8 章）的 target 就能在一个文件里兼顾：

# syntax=docker/dockerfile:1
FROM node:22-alpine AS base
WORKDIR /app
COPY package*.json ./

# ---------- 开发目标：装全部依赖，用 nodemon 监听代码变化 ----------
FROM base AS dev
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
EXPOSE 3000 9229
CMD ["npx", "nodemon", "--inspect=0.0.0.0:9229", "src/index.js"]

# ---------- 生产目标：只装生产依赖，非 root 运行 ----------
FROM base AS prod
ENV NODE_ENV=production
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev
COPY src ./src
USER node
EXPOSE 3000
CMD ["node", "src/index.js"]

数据库初始化脚本

官方 Postgres、MySQL、MariaDB 镜像有一个非常实用的约定：第一次启动、数据目录为空时，会自动执行 /docker-entrypoint-initdb.d/ 目录下的 .sql 和 .sh 文件。把建表和测试数据放进去即可：

CREATE TABLE todos (
  id    SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  done  BOOLEAN NOT NULL DEFAULT false
);
INSERT INTO todos (title) VALUES ('学会 Docker'), ('用容器搭开发环境');
⚠ 初始化脚本只执行一次

数据保存在卷里，所以第二次启动时数据目录不为空，脚本不会再执行。改了 init.sql 想重新初始化？运行 docker compose down -v 删掉卷再 up（开发数据会被清空）。

Compose 文件

我们把配置拆成两个文件：compose.yaml 放开发和生产通用的部分；compose.override.yaml 放只在开发时需要的东西。Compose 会自动读取并合并这两个文件，不需要任何额外参数。

name: todo

services:
  api:
    build:
      context: .
      target: prod                          # 默认构建生产目标
    environment:
      DATABASE_URL: postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      REDIS_URL: redis://cache:6379
    ports:
      - "${API_PORT:-3000}:3000"
    depends_on:
      db:
        condition: service_healthy           # 等数据库真正就绪
      cache:
        condition: service_started

  db:
    image: postgres:17
    env_file: .env                           # POSTGRES_USER / PASSWORD / DB
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10

  cache:
    image: redis:8-alpine

volumes:
  pgdata:
ⓘ 为什么写 $${POSTGRES_USER}？

Compose 会在读取文件时替换 ${…}。写成 $$ 表示“保留一个字面上的 $”，让这个变量留到容器里由 shell 展开 —— 健康检查运行在 db 容器里，那里正好有这些环境变量。

services:
  api:
    build:
      target: dev                            # 覆盖：开发时构建 dev 目标
    environment:
      NODE_ENV: development
    ports:
      - "9229:9229"                          # Node 调试端口
    develop:
      watch:
        - action: sync                       # 改 src/ → 同步进容器，nodemon 自动重启
          path: ./src
          target: /app/src
        - action: rebuild                    # 改依赖清单 → 重新构建镜像
          path: package.json

  db:
    ports:
      - "127.0.0.1:5432:5432"                # 方便用本机的数据库客户端连接

  adminer:                                   # 网页版数据库管理工具，按需启动
    image: adminer
    ports:
      - "127.0.0.1:8081:8080"
    profiles: [tools]

热更新：改代码立刻生效

开发环境最重要的体验就是“保存文件 → 马上看到效果”。有两种做法：

本章的 override 文件用的是 watch。启动方式：

$ docker compose up --watch          # 前台运行，同时显示日志和同步事件
# 或者在另一个终端：
$ docker compose watch

修改 src/index.js 并保存，Compose 把文件同步进容器，nodemon 检测到变化后自动重启 Node 进程。修改 package.json 则会触发整个镜像重新构建。

如果用绑定挂载：小心 node_modules 陷阱

很多教程直接把整个项目目录挂进去：- .:/app。这会带来一个经典问题：

services:
  api:
    build:
      target: dev
    volumes:
      - .:/app                               # 本机项目目录 → 容器
      - node_modules:/app/node_modules       # 依赖留在容器里的命名卷中
volumes:
  node_modules:
💡 文件变化检测不到？

在 Windows（WSL 之外的目录）或某些网络文件系统上，绑定挂载的文件变化事件可能传不进容器，nodemon、Vite 等察觉不到修改。 解决办法：把项目放在 WSL 2 的 Linux 文件系统里；改用 compose watch；或者让工具使用轮询（如 nodemon --legacy-watch、CHOKIDAR_USEPOLLING=true）。

ⓘ exec 和 run 的区别

exec 在已经运行的容器里执行命令；run 基于服务配置新建一个临时容器执行命令，加 --rm 用完即删。跑测试、数据库迁移这类一次性任务用 run --rm，不会影响正在运行的开发服务器。

在容器里断点调试

dev 目标用 --inspect=0.0.0.0:9229 启动了 Node 调试器，override 文件又把 9229 端口映射到了本机。 注意这里同样要监听 0.0.0.0，原因见第 17 章图 17-4。在 VS Code 里添加一个“附加”配置： 

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "附加到容器中的 Node",
      "type": "node",
      "request": "attach",
      "address": "localhost",
      "port": 9229,
      "localRoot": "${workspaceFolder}",
      "remoteRoot": "/app",
      "restart": true
    }
  ]
}

按 F5 启动这个配置，就能在本机的源码上打断点、单步执行，而程序实际运行在容器里。Python（debugpy，端口 5678）、Java（JDWP，端口 5005）、Go（Delve，端口 2345）都是同样的思路：容器里开调试端口，映射出来，IDE 附加上去。

Dev Containers：把编辑器也搬进容器

到目前为止，运行时在容器里，但你的编辑器、语言服务器、代码检查工具、Git 钩子还装在本机。 Dev Containers 更进一步：整个开发环境都在容器里，编辑器只是一个“远程窗口”。 它由一个开放规范（containers.dev）定义，VS Code、JetBrains、GitHub Codespaces 等都支持。

在项目里新建 .devcontainer/devcontainer.json，直接复用前面的 Compose 文件：

{
  "name": "todo",
  "dockerComposeFile": ["../compose.yaml", "../compose.override.yaml", "compose.devcontainer.yaml"],
  "service": "api",
  "workspaceFolder": "/workspace",
  "features": {
    "ghcr.io/devcontainers/features/github-cli:1": {}
  },
  "forwardPorts": [3000, 8081],
  "postCreateCommand": "npm ci",
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "ms-azuretools.vscode-containers"]
    }
  }
}

services:
  api:
    volumes:
      - ..:/workspace:cached          # 把项目挂进容器，编辑器直接在里面改
    command: sleep infinity           # 让容器保持运行，由你在终端里启动应用

然后在 VS Code 里执行命令 Dev Containers: Reopen in Container（需要安装 Dev Containers 扩展）。第一次会构建容器、安装扩展、执行 postCreateCommand，之后编辑器左下角会显示你已经“在容器里”了：打开的终端是容器里的 shell，扩展运行在容器里，npm 和 node 也来自容器。

只用 Compose（本章前半部分）Dev Containers
运行时、数据库容器里容器里
编辑器扩展、语言服务器、代码检查本机容器里
本机需要装什么Docker（加上你喜欢的编辑器插件依赖）只要 Docker + 编辑器
团队一致性运行时一致连工具链、扩展、格式化配置都一致
适合大多数项目，简单直接工具链复杂的项目、开源项目、云端开发（Codespaces）

更多建议

  • 固定版本：postgres:17、redis:8-alpine，不要用 latest，让所有人和生产环境保持一致。
  • 数据库端口只绑定到 127.0.0.1：避免开发数据库暴露在咖啡馆的 Wi-Fi 上。
  • 把常用命令写进 Makefile 或 package.json 的 scripts，比如 make dev、make reset-db，新人更容易上手。
  • Mac / Windows 性能：依赖目录放在命名卷里；优先 compose watch；Docker Desktop 设置里给足 CPU 和内存。
  • 定期验证生产镜像：开发时一直用 dev 目标，偶尔用 docker compose -f compose.yaml up --build 跑一下 prod 目标，别等到上线才发现问题。第 19 章会让 CI 自动做这件事。

本章小结

  • 容器化开发环境让“克隆仓库 + 一条命令”就能开工，所有人的依赖版本完全一致。
  • 用多阶段构建的 target，一个 Dockerfile 同时产出开发镜像和生产镜像。
  • 官方数据库镜像会在首次启动时执行 /docker-entrypoint-initdb.d/ 下的脚本；配合 healthcheck 解决启动顺序。
  • compose.override.yaml 会被自动合并，适合放开发专用配置。
  • 热更新有两种方式：绑定挂载（注意 node_modules 陷阱）和 docker compose watch（同步、重启、重建）。
  • 容器里开调试端口并监听 0.0.0.0，映射出来后 IDE 就能附加调试。
  • Dev Containers 把整个工具链都放进容器，并且能无缝迁移到 GitHub Codespaces。

✎ 动手练习

  1. 按本章内容搭建 todo 项目（src/index.js 可以自己用 Express + pg 写一个 GET /todos），确认 curl localhost:3000/todos 能返回初始化数据。
  2. 启动 docker compose up --watch，修改接口返回内容，观察日志里的同步事件和 nodemon 重启。
  3. 改用绑定挂载 - .:/app 但不加 node_modules 卷，重现“模块找不到”的错误；再加上卷解决它。
  4. 在 VS Code 里配置 launch.json，在路由处理函数里打一个断点并命中它。
  5. 给项目加上 .devcontainer，用 “Reopen in Container” 打开，确认终端里的 node --version 来自容器。

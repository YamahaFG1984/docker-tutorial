第 5 章

Docker 引擎

当你敲下 docker run 时，幕后到底发生了什么？本章打开引擎盖，看看 Docker 引擎由哪些零件组成、它们如何协作把一个容器“造”出来。 不懂这些也能用 Docker，但想真正掌握它，这一章绕不过去。

本章目标

  • 说出 Docker 引擎的主要组件：dockerd、containerd、shim、runc
  • 理解 Docker 为什么从一个“大单体”拆成许多小组件
  • 完整追踪一次 docker run 从 CLI 到内核的全过程
  • 理解 shim 的作用和“无守护进程容器”的含义
  • 知道这些组件在 Linux 上对应哪些可执行文件

一句话概括

Docker 引擎是 Docker 服务端所有组件的统称，负责运行和管理容器。如果你用过 VMware，Docker 引擎的地位类似于 ESXi。

Docker 引擎是模块化的，由许多来自 OCI、CNCF、Moby 的小而专的组件拼成。它很像一台汽车发动机：

汽车发动机
由进气歧管、节气门、气缸、活塞、火花塞、排气歧管等专门零件组成，协同工作让汽车跑起来。
Docker 引擎
由 API、镜像构建器、高层运行时、低层运行时、shim 等专门工具组成，协同工作来创建和运行容器。
ⓘ 大小写约定

runc 和 containerd 在官方文档中总是全小写，本教程也遵循这个约定，即使它们出现在句首。

引擎的演化史

Docker 刚发布时，引擎只有两个主要组件：

  • Docker 守护进程（daemon）：一个巨大的单体程序，API、镜像构建、容器执行、卷、网络……所有代码都在里面。
  • LXC：负责和 Linux 内核打交道，创建容器所需的命名空间和 cgroups。

替换 LXC

依赖 LXC 给 Docker 带来了两个问题：第一，LXC 只能用于 Linux，而 Docker 想跨平台；第二，Docker 发展太快，没法保证 LXC 按 Docker 需要的方向演进。

于是 Docker 开发了自己的工具 libcontainer 来替代 LXC —— 一个平台无关的库，让 Docker 直接调用宿主机内核里的容器基础能力。这件事很早就完成了。

拆分单体守护进程

随着时间推移，把几乎所有功能都塞进一个守护进程的做法越来越成问题：

  1. 它变得越来越慢；
  2. 这不是生态想要的 —— 其他平台想复用 Docker 的某部分能力，却只能整个拿走；
  3. 单体软件很难创新。

Docker 于是启动了一个长期的拆分计划：把每个功能都重构成独立的小工具，让其他平台也能复用它们。 最典型的成果就是把高层和低层运行时功能拆成了 containerd 和 runc —— 如今它们被 Docker、Kubernetes、Firecracker、AWS Fargate 等无数项目使用。 后来，Docker 连镜像管理也交给了 containerd。

OCI 的影响

就在 Docker 重构引擎的同时，OCI 正在制定两个容器标准：镜像规范和运行时规范。 两者都在 2017 年 7 月发布了 1.0 版本，后来又增加了第三个分发规范（管理镜像仓库如何分发镜像）。

自 2016 年以来的所有 Docker 版本都实现了 OCI 规范：用 runc（runtime-spec 的参考实现）创建符合 OCI 的容器； 用 BuildKit 构建符合 OCI 的镜像；Docker Hub 是符合 OCI 的镜像仓库。

runc：低层运行时

runc（读作 “run see”）是 OCI 运行时规范的参考实现。Docker 公司深度参与了这个规范的制定，并贡献了 runc 的最初代码。

runc 本质上是 libcontainer 的一个轻量命令行包装。你可以单独下载它来管理 OCI 容器，但它非常底层，几乎没有 Docker 引擎那些丰富的功能。 好在 Docker 把 runc 作为自己的低层运行时，这样你既得到了符合 OCI 标准的容器，又享受到了 Docker 的易用体验。

行话里，我们说 runc 工作在 OCI 层，称它为低层运行时（low-level runtime）：它负责和内核打交道，真正地把容器“造”出来和拆掉。

containerd：高层运行时

containerd（读作 “container dee”）是 Docker 从守护进程中剥离出来的另一个工具。 我们称它为高层运行时（high-level runtime），因为它管理的是生命周期事件：启动、停止、删除容器。 但真正干活需要一个低层运行时，大多数情况下就是 runc。

containerd · 包工头

接活、安排、盯进度：决定什么时候启动哪个容器、把镜像准备好、监控状态。

runc · 施工队

按图纸干活：调用内核创建命名空间和 cgroups，把容器进程启动起来，然后撤场。

containerd 最初的定位是一个只管容器生命周期的小工具，后来逐渐增加了镜像、网络、卷管理等能力 —— 一个原因是 Kubernetes 等项目希望 containerd 能自己拉取和推送镜像。好在这些功能是模块化的，其他项目可以只取需要的部分。

containerd 由 Docker 公司开发并捐赠给了 CNCF，目前是 CNCF 的毕业项目，稳定且可用于生产。

✨ 最新变化：containerd 2.x 与 containerd 镜像存储

containerd 在 2024 年底发布了 2.0，Docker Desktop 4.92 自带的已经是 containerd 2.3。 更重要的是，从 Docker Engine 29 开始，全新安装默认使用 containerd 镜像存储： 镜像的拉取、存储、解包都由 containerd 的 “snapshotter” 负责，而不再是 dockerd 自己的“图驱动（graph driver）”。 这意味着 Docker 和 Kubernetes 在镜像管理上走向了同一套实现，也让多平台镜像、镜像证明等功能开箱即用。

一次 docker run 的完整旅程

现在把所有零件串起来。运行下面的命令启动一个 NGINX 容器：

$ docker run -d --name ctr1 nginx
$ docker ps
CONTAINER ID   IMAGE   COMMAND                  CREATED         STATUS         PORTS    NAMES
9cfb0c9aacb2   nginx   "/docker-entrypoint.…"   9 seconds ago   Up 9 seconds   80/tcp   ctr1

逐步解读：

  1. CLI → dockerd：Docker 客户端把命令转换成 API 请求，发给守护进程。守护进程可以在本地套接字上提供 API （Linux 上是 /var/run/docker.sock，Windows 上是 \\.\pipe\docker_engine），也可以通过网络提供。
  2. dockerd → containerd：守护进程收到请求，理解为“要创建一个新容器”，于是通过 gRPC 调用 containerd 的 CRUD 风格 API。 记住：守护进程里已经没有任何创建容器的代码了。
  3. containerd 准备材料：containerd 其实也不会创建容器。它把所需的 Docker 镜像转换成一个 OCI bundle（根文件系统 + config.json）， 然后通过 shim 让 runc 用这个 bundle 创建容器。
  4. runc 干活：runc 调用操作系统内核，把创建容器所需的一切（命名空间、cgroups 等）组装起来。
  5. 容器诞生，runc 撤场：容器作为 runc 的子进程启动，一旦容器启动成功，runc 立刻退出。
★ “无守护进程容器”

把容器的创建和管理从 Docker 守护进程中解耦出来、交给 containerd 和 runc 之后，就可以停止、重启甚至升级 Docker 守护进程，而不影响正在运行的容器。 我们称之为无守护进程容器（daemonless containers）。要在 Linux 上启用这个行为，需要在 /etc/docker/daemon.json 里设置 "live-restore": true。

别忘了清理刚才的容器：

$ docker rm ctr1 -f

shim 到底是干什么的？

shim（垫片）是软件工程里常见的一种模式。Docker 引擎在 containerd 和 OCI 层之间使用 shim，带来三个好处：

🔄

无守护进程容器

dockerd 和 containerd 重启时，容器由 shim“托管”着，不会跟着一起挂掉。

⚡

更高效

每个容器一个 runc 进程，但 runc 启动完就退出；只留下一个很轻的 shim 常驻。

🔌

可插拔的 OCI 层

换一个 shim，就能把 runc 换成其他低层运行时，比如 gVisor、Kata Containers，或第 11 章的 Wasm 运行时。

具体来说：containerd 为每个新容器 fork 出一个 shim 和一个 runc 进程。runc 在容器启动后立即退出，shim 就成了容器的父进程。 shim 负责汇报容器状态，并执行一些底层任务，比如保持容器的 STDIN 和 STDOUT 流一直打开。

在 Linux 上长什么样

在 Linux 系统上，上面讨论的组件对应以下几个独立的可执行文件：

可执行文件组件什么时候能看到
/usr/bin/dockerdDocker 守护进程Docker 运行时一直在
/usr/bin/containerdcontainerd一直在
/usr/bin/containerd-shim-runc-v2shim每个运行中的容器对应一个
/usr/bin/runcrunc只在创建容器的一瞬间存在

在 Linux Docker 主机上启动一个容器，然后用 ps 就能看到它们：

$ docker run -d --name demo nginx
$ ps -ef --forest | grep -E "dockerd|containerd|nginx" | grep -v grep
root   1021     1  /usr/bin/containerd
root   1180     1  /usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock
root   5530     1  /usr/bin/containerd-shim-runc-v2 -namespace moby -id 3f1c... -address /run/containerd/containerd.sock
root   5553  5530   \_ nginx: master process nginx -g daemon off;
101    5601  5553       \_ nginx: worker process

注意 nginx 的父进程（PPID 5530）是 shim，而不是 dockerd 或 containerd。 如果你用的是 Mac 上的 Docker Desktop，就看不到这些进程，因为引擎跑在那台 Linux 虚拟机里。

我们还需要守护进程吗？

到今天，Docker 已经把守护进程里的大部分功能剥离出去了。但 dockerd 仍然负责提供 Docker API， 以及构建（调用 BuildKit）、网络（libnetwork）、卷等高层功能 —— 它是 Docker 用户体验的“门面”。

💡 回头看看 hello-world

第 3 章运行 docker run hello-world 时，输出里有 4 个步骤：客户端联系守护进程 → 守护进程从 Docker Hub 拉取镜像 → 守护进程创建容器并运行 → 守护进程把输出流回客户端。现在你知道第 3 步背后其实是 containerd、shim 和 runc 在接力了。

本章小结

组件角色一句话
dockerd守护进程提供 Docker API，是用户体验的门面
containerd高层运行时管理容器生命周期和镜像；CNCF 毕业项目，Kubernetes 也在用
shim垫片容器的“保姆”，让守护进程可以重启；让低层运行时可以替换
runc低层运行时OCI 运行时规范的参考实现，调用内核创建容器后立即退出

✎ 动手练习

  1. 在一台 Linux Docker 主机上（Multipass 虚拟机也行）启动 3 个容器，用 ps -ef --forest 数一数有几个 containerd-shim-runc-v2 进程。
  2. 在 /etc/docker/daemon.json 里加上 {"live-restore": true}，重启 Docker（sudo systemctl restart docker）， 观察之前运行的容器是否还活着。再把这个配置去掉试一次，对比结果。
  3. 运行 docker info，找到 Default Runtime 和 Runtimes 两行，看看你的引擎支持哪些低层运行时。

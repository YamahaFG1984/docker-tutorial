第 6 章

镜像

镜像是 Docker 世界里的“安装包”。本章深入镜像：它是什么、从哪里来、怎么命名、内部如何分层、 为什么标签不可靠而摘要可靠、一个标签如何同时服务 ARM 和 x86 电脑，以及怎样扫描漏洞和删除镜像。 自己构建镜像的方法留到第 8 章。

本章目标

  • 理解镜像是“只读的构建期对象”，容器是“可写的运行期对象”
  • 看懂完整的镜像名：仓库地址/用户名/仓库名:标签
  • 理解镜像分层、层共享和联合文件系统
  • 理解标签（tag）和摘要（digest）的区别，知道什么时候该用摘要
  • 理解多架构镜像背后的 manifest list
  • 会用 pull、images、inspect、history、rmi、scout

一句话概括

先说明一下：镜像、Docker 镜像、容器镜像、OCI 镜像指的都是同一个东西，本教程会混用。

镜像是一个只读的包，里面包含运行一个应用所需的一切：应用代码、依赖、最小化的操作系统组件，以及元数据。 一个镜像可以启动多个容器。

🖥

运维视角

镜像像虚拟机模板。虚拟机模板是一台“停止的虚拟机”，镜像就是一个“停止的容器”。

💻

开发视角

镜像像类（class）。一个类可以创建多个对象，一个镜像可以启动多个容器。

获取镜像最简单的方式是从镜像仓库（registry）拉取，最常用的仓库是 Docker Hub。 镜像由多个独立的层（layer）堆叠而成，Docker 把它们呈现为一个统一的整体。 镜像通常很小：官方 NGINX 镜像约 80 MB（压缩后），官方 Redis 约 40 MB。不过 Windows 镜像可能非常大。

镜像与容器的关系

镜像是构建期（build-time）的产物，容器是运行期（run-time）的产物。 docker run 是从镜像启动容器最常用的方式。

容器一旦运行起来，就和它的镜像绑定了：在删除所有使用该镜像的容器之前，你无法删除这个镜像。

镜像为什么这么小

容器被设计成只运行一个应用或微服务，所以镜像里只应该有应用代码和依赖，不该有构建工具、排障工具这些“可有可无”的东西。

  • 没有多余的东西。官方 Alpine Linux 镜像只有 3 MB 左右 —— 它不带六种 shell、三个包管理器和一堆“十年用一次”的工具。 越来越多的镜像甚至连 shell 和包管理器都不带：应用运行时用不到的，镜像里就不放。这种镜像叫精简镜像（slim image）。
  • 没有内核。容器使用宿主机的内核，所以镜像里的操作系统部分通常只是一些文件系统对象。人们常说镜像里只有“刚刚够用的操作系统”（just enough OS）。

拉取镜像

Docker 主机上存放镜像的地方叫本地仓库或镜像缓存。全新安装时它是空的。 如果你用 Docker Desktop，它位于那台 Linux 虚拟机里。 

$ docker pull redis
Using default tag: latest                      <<---- 默认使用 latest 标签
latest: Pulling from library/redis             <<---- 默认从 Docker Hub 拉取
08df40659127: Download complete                <<---- 拉取一个层
4f4fb700ef54: Already exists                   <<---- 这个层本地已经有了
4fe7fa4aab04: Download complete
57dea0f129a5: Download complete
<Snip>
Digest: sha256:76d5908f5e19fcdd73daf956a38826f790336ee4707d9028f32b24ad9ac72c08
Status: Downloaded newer image for redis:latest
docker.io/library/redis:latest                 <<---- docker.io 就是 Docker Hub

从这段输出能读出两个重要信息：

  1. Docker 很“有主见”。你没指定标签，它就假设你要 latest；你没指定仓库地址，它就假设从 Docker Hub 拉取。这两个默认值都可以覆盖。
  2. 层可以共享。这个镜像有 8 层，但 Docker 只拉了 7 层，因为其中一层本地已经有了（被别的镜像用过）。Docker 足够聪明，只拉取它还没有的层。
ⓘ Docker Hub 拉取频率限制

Docker Hub 对匿名拉取有频率限制（按 IP 计算，每小时次数很有限），登录后额度会高很多。如果你看到 toomanyrequests: You have reached your pull rate limit，先运行 docker login。 具体额度以 Docker Hub 官方文档为准。

镜像仓库

镜像集中存放在叫镜像仓库（registry）的地方。它的职责是安全地存储镜像，并让不同环境都能方便地访问。 它在“构建 → 分享 → 运行”流水线中处于核心位置：

现代镜像仓库大多实现了 OCI 分发规范（所以也叫 OCI 仓库），同时兼容 Docker Registry v2 API， 因此都能用 Docker CLI 以同样的方式操作。有些还提供镜像扫描、与构建流水线集成等高级功能。

仓库的组织结构是：一个镜像仓库（registry）包含多个镜像库（repository），一个镜像库包含多个镜像（用标签区分）。

官方镜像库与非官方镜像库

Docker Hub 有官方镜像库（Docker Official Images）的概念：由 Docker 和软件厂商共同审核和维护， 应该是最新的、高质量的、安全的、文档齐全的。它们很好认：位于 Docker Hub 命名空间的顶层，并带有绿色的 Docker Official Image 徽章。例如：

  • nginx：hub.docker.com/_/nginx
  • redis：hub.docker.com/_/redis
  • alpine、busybox、mongo、postgres、python、node……

其他镜像则位于某个用户或组织的二级命名空间下，比如 nigelpoulton/tu-demo。 另外还有带 Verified Publisher（认证发布者）徽章的商业厂商镜像。

⚠ 永远不要盲目信任来自互联网的软件

非官方镜像库里有很多好镜像，但你应该默认假设非官方镜像不安全。即使是官方镜像，使用前也应保持谨慎（比如先做漏洞扫描，见本章后文）。

镜像命名与标签

大多数时候你都是通过名字来使用镜像，而名字本身包含了很多信息。一个完全限定的镜像名长这样：

拉取官方镜像最简单，只需要 镜像库名:标签：

$ docker pull redis:8.2           # 官方 redis 库里标签为 8.2 的镜像
$ docker pull busybox:glibc       # 官方 busybox 库里标签为 glibc 的镜像
$ docker pull alpine              # 官方 alpine 库里标签为 latest 的镜像

两个要点：

  • 不写标签就默认 latest。如果这个库没有 latest 标签，命令会失败。
  • latest 并不保证是最新的镜像！它只是一个普通的标签名，由维护者自己决定指向哪个镜像。

拉取非官方镜像，要在前面加上 Docker Hub 用户名或组织名；拉取其他仓库的镜像，要再在前面加上仓库的域名：

$ docker pull nigelpoulton/tu-demo:v2                 # Docker Hub 上的个人镜像
$ docker pull ghcr.io/regclient/regsync:latest        # GitHub Container Registry 上的镜像
latest: Pulling from regclient/regsync
f140ae7f526a: Download complete
<Snip>
ghcr.io/regclient/regsync:latest

从 GHCR 拉取的体验和 Docker Hub 一模一样，因为 GHCR 同样实现了 OCI 分发规范。

一个镜像，多个标签

一个镜像可以有任意多个标签。下面的输出看起来像三个镜像，但仔细看 IMAGE ID，其实只有两个：

$ docker images
REPOSITORY             TAG      IMAGE ID       CREATED          SIZE
nigelpoulton/tu-demo   latest   b4210d0aa52f   2 days ago       115MB
nigelpoulton/tu-demo   v1       b4210d0aa52f   2 days ago       115MB
nigelpoulton/tu-demo   v2       6ba12825d092   12 minutes ago   115MB

这里 latest 和 v1 指向同一个镜像，而它比 v2 还旧 —— 这正是“latest 不一定最新”的活生生的例子。

镜像与层

镜像是一组松散关联的只读层，每一层包含一个或多个文件。Docker 负责把它们堆叠起来，呈现为一个统一的镜像。

查看层信息有三种方式：拉取时的输出、docker inspect、docker history。

$ docker pull node:latest
latest: Pulling from library/node
952132ac251a: Pull complete
82659f8f1b76: Pull complete
c19118ca682d: Pull complete
8296858250fe: Pull complete
24e0251a0e2c: Pull complete
Digest: sha256:f4691c96e6bbaa99d...28ae95a60369c506dd6e6f6ab

docker history 显示的是镜像的构建历史，而不是严格的层列表：有些 Dockerfile 指令（如 ENV、EXPOSE、CMD、ENTRYPOINT） 只添加元数据，不创建层（第 8 章详细讲）。

基础层与层的堆叠

所有镜像都从一个基础层（base layer）开始，每添加新内容就增加一层。举个简化的例子：公司规定所有应用都必须基于官方 Ubuntu 24.04 镜像构建， 那么 Ubuntu 就是基础层；安装公司认可的 Python 版本会增加第二层；应用源代码是第三层。

镜像是所有层按构建顺序叠加的结果。如果上层有一个文件和下层的文件同名同路径，上层的文件会遮住下层的。 这就是“修改”镜像的方式：不改动旧层，而是添加一个包含改动的新层。

在底层，Docker 用存储驱动（storage driver）把这些层堆叠起来，呈现为一个统一的文件系统。 传统上几乎所有 Docker 主机都用 overlay2 驱动（还有 zfs、btrfs、vfs 等选择）。 无论用哪个驱动，开发者和用户的体验都是一样的。

✨ 最新变化：snapshotter 取代 graph driver

在 Docker Engine 29 的全新安装中，层的管理交给了 containerd 的 snapshotter（默认是 overlayfs snapshotter）， 原理和 overlay2 一样，都是基于 Linux 的 OverlayFS 联合文件系统。区别在于镜像数据现在由 containerd 管理， 因此能原生保存多平台镜像和镜像证明（SBOM、来源证明）。你可以用 docker info 查看自己用的是哪种。

层共享

多个镜像可以共享同一个层，这节省了磁盘空间，也加快了拉取速度。前面拉取 redis 时出现的 Already exists 就是这个原因。

镜像仓库那边也一样：仓库里存了很多相似的镜像，但任何一个层都只存一份。

用摘要拉取镜像

到目前为止，我们都用名字（标签）来操作镜像。这是最常见的方式，但有个问题：标签是随意的、可变的。 你可以把错误的镜像打上某个标签，也可以把新镜像打上和旧镜像一样的标签。最典型的就是 latest：一年前拉取的 alpine:latest 和今天拉取的肯定不是同一个。

⚠ 一个真实的灾难场景

你的生产环境有很多容器在用 golftrack:1.5，突然收到警告：这个镜像有严重漏洞。你构建了修复版，然后…… 把它推送到了同一个库、用了同一个标签 1.5。旧镜像被覆盖了，现在你没有好办法知道哪些生产容器用的是有漏洞的旧版、哪些是修好的新版 —— 它们的标签一模一样！

镜像摘要（digest）来救场了。Docker 使用内容寻址存储（content addressable storage）模型： 每个镜像都有一个根据其内容计算出来的加密哈希值，叫做摘要。因为它是内容的哈希：

  • 两个不同的镜像不可能有相同的摘要；
  • 镜像只要有任何改动，摘要必然改变。
# 查看本地镜像的摘要
$ docker images --digests alpine
REPOSITORY   TAG      DIGEST                    IMAGE ID       CREATED       SIZE
alpine       latest   sha256:c5b1261d...8e1ad6b c5b1261d6d3e   2 weeks ago   11.8MB

# 拉取之前，先查看仓库里某个镜像的摘要
$ docker buildx imagetools inspect nigelpoulton/k8sbook:latest
Name:      docker.io/nigelpoulton/k8sbook:latest
MediaType: application/vnd.docker.distribution.manifest.list.v2+json
Digest:    sha256:13dd59a0c74e9a147800039b1ff4d61201375c008b96a29c5bd17244bce2e14b

# 用摘要拉取：保证拿到的永远是这一个镜像
$ docker pull nigelpoulton/k8sbook@sha256:13dd59a0c74e9a147800039b1ff4d61201375c008b96a29c5bd17244bce2e14b
💡 生产环境的最佳实践

在生产环境的部署文件和 Dockerfile 的 FROM 里，可以同时写标签和摘要：FROM node:22-alpine@sha256:…。 标签给人看（一眼知道是什么版本），摘要给机器用（保证一字不差）。Dependabot、Renovate 等工具可以帮你自动更新摘要。

镜像哈希与层哈希

你已经知道镜像只是一堆独立层的松散集合。实际上，镜像本身只是一个清单文件（manifest），包含一些元数据和层的列表； 真正的应用和依赖都在层里，而层完全独立，根本不知道自己属于哪个镜像。所以：

  • 镜像摘要是镜像 manifest 文件的哈希；
  • 层摘要是层内容的哈希。
🔬 深入：为什么不同命令显示的哈希对不上？

Docker 在每次推送和拉取前后都会比对哈希，以确保数据在网络传输中没被篡改。但推送和拉取时层会被压缩（节省带宽和仓库空间）， 压缩后的哈希自然和压缩前不同。所以每个层实际上有两个哈希：内容哈希（未压缩，即 config 里的 diff_id） 和分发哈希（压缩后，即 manifest 里的 digest）。这就是为什么 CLI 和仓库网页上显示的哈希有时对不上 —— 你看到的可能一个是内容哈希，一个是分发哈希。

多架构镜像

Docker 最大的优点之一是简单。但随着它支持 Windows、Linux，以及 ARM、x64、PowerPC、s390x 等各种 CPU 架构， 同一个镜像突然有了多个版本，用户要费劲地挑出适合自己机器的那个。这破坏了 Docker 的流畅体验。

多架构镜像解决了这个问题：Docker 和仓库 API 把多个架构的镜像藏在同一个标签后面。 你在任何架构上执行 docker pull alpine，都会自动拿到正确的版本。背后靠的是两个结构：

  • manifest list（OCI 里叫 image index）：一个标签支持哪些架构的列表；
  • manifest：每个架构各自的清单，列出该架构版本的 config 和层。
$ docker buildx imagetools inspect alpine
Name:      docker.io/library/alpine:latest
MediaType: application/vnd.oci.image.index.v1+json         <<---- manifest list / image index
Digest:    sha256:c5b1261d6d3e43071626931fc004f70149baeba2c8ec672bd4f27761f8e1ad6b
Manifests:
  Name:      docker.io/library/alpine:latest@sha256:6457d53f...628977d0
  MediaType: application/vnd.oci.image.manifest.v1+json    <<---- 某个架构的 manifest
  Platform:  linux/amd64
  Name:      docker.io/library/alpine:latest@sha256:a0264d60...93467a46
  MediaType: application/vnd.oci.image.manifest.v1+json
  Platform:  linux/arm64/v8
  <Snip>

看看效果：在 ARM Mac 和 x86 Windows 上执行完全相同的命令，Docker 各自拉取了正确的镜像：

# ARM 架构的 Mac
$ docker run --rm golang go version
go version go1.25.1 linux/arm64

# x86 的 Windows（Windows 容器模式）
> docker run --rm golang go version
go version go1.25.1 windows/amd64

你也可以用 --platform 显式要求某个架构，比如在 ARM Mac 上拉取 x86 镜像：docker pull --platform linux/amd64 alpine （运行时会通过 QEMU/Rosetta 模拟，速度较慢）。如何构建多架构镜像，第 8 章会讲。

💡 看看本地存了哪些架构

在使用 containerd 镜像存储的 Docker 上，可以运行 docker image ls --tree，以树状结构列出每个多平台镜像下本地实际存在的各个架构版本。

用 Docker Scout 扫描漏洞

有很多工具可以扫描镜像中的已知漏洞。Docker Scout 内置于 Docker 的各个层面：CLI、Docker Desktop、Docker Hub 和 scout.docker.com 门户。它会先为镜像生成一份软件物料清单（SBOM），再拿它去比对已知漏洞数据库。 

$ docker scout quickview nigelpoulton/tu-demo:latest
    ✓ SBOM of image already cached, 66 packages indexed

  Target             │  nigelpoulton/tu-demo:latest  │    0C     1H     1M     0L
    digest           │  b4210d0aa52f                 │
  Base image         │  python:3-alpine              │    0C     1H     1M     0L
  Updated base image │  python:3.13-alpine           │    0C     0H     0M     0L

输出表示：0 个严重（Critical）、1 个高危（High）、1 个中危（Medium）、0 个低危（Low）漏洞，并且建议你换一个更新的基础镜像。想看详情和修复建议，用 docker scout cves：

$ docker scout cves nigelpoulton/tu-demo:latest
    ✓ Detected 1 vulnerable package with 2 vulnerabilities
## Packages and Vulnerabilities
   0C     1H     1M     0L  expat 2.5.0-r2
pkg:apk/alpine/expat@2.5.0-r2?os_name=alpine&os_version=3.19
    ✗ HIGH CVE-2023-52425
      https://scout.docker.com/v/CVE-2023-52425
      Affected range : <2.6.0-r0
      Fixed version  : 2.6.0-r0
<Snip>

从报告中可以读出：哪个软件包有漏洞（expat 2.5.0-r2）、漏洞编号（CVE-2023-52425）、详情链接，以及修复版本（2.6.0-r0）。

✨ 最新变化：Scout 的定位调整

Docker Scout 仍在持续开发（例如新增了 JSON 输出格式），CLI 命令 docker scout 照常可用，个人账户有免费额度。 但在 2026 年 9 月的 Docker Desktop 4.92 中，Desktop 里独立的 Scout 视图以及 docker pull/docker build 后的 Scout 提示已被移除。 开源的替代工具还有 Trivy、Grype 等。第 16 章会再讨论漏洞扫描。

删除镜像

用 docker rmi（remove image）删除镜像。删除会从本地仓库移除镜像，并删除本地文件系统上对应的层数据。 但被多个镜像共享的层要等所有引用它的镜像都删掉后才会被删除。可以用名字、短 ID 或 SHA 删除，也可以一次删多个： 

$ docker rmi redis:latest af111729d35a sha256:c5b1261d...f8e1ad6b
Untagged: redis:latest
Deleted: sha256:76d5908f5e19fcdd73daf956a38826f790336ee4707d9028f32b24ad9ac72c08
Untagged: nigelpoulton/tu-demo:v2
Deleted: sha256:af111729d35a09fd24c25607ec045184bb8d76e37714dfc2d9e55d13b3ebbc67
<Snip>

如果镜像正被某个容器使用，或者被多个标签引用，Docker 会阻止删除。可以加 -f 强制删除，但要谨慎： 强制删除一个正在被容器使用的镜像，只会去掉它的标签，镜像本身会作为悬空镜像（dangling image）留在系统里（在列表中显示为 <none>:<none>）。

批量清理的几个常用命令：

$ docker images -q                 # 只输出所有镜像的 ID
44dd6f223004
3f5ef9003cef

$ docker rmi $(docker images -q) -f   # 把 ID 列表交给 rmi：删除所有镜像（慎用！）

$ docker image prune               # 删除所有悬空镜像
$ docker image prune -a            # 删除所有没有被容器使用的镜像
$ docker system df                 # 查看镜像、容器、卷、构建缓存各占多少磁盘
ⓘ Windows 用户

$(...) 这种命令替换写法只能在 PowerShell 里用，老式的 cmd 不支持。

命令作用
docker pull <镜像>从仓库下载镜像，默认 Docker Hub、默认 latest 标签
docker images列出本地镜像；--digests 显示摘要，-q 只显示 ID
docker inspect <镜像>查看镜像的详细元数据（层、环境变量、启动命令……）
docker history <镜像>查看镜像的构建历史
docker manifest inspect <镜像>查看仓库里镜像的 manifest list
docker buildx imagetools inspect <镜像>查看仓库里镜像的摘要和各架构 manifest
docker scout quickview / cves漏洞概览 / 漏洞详情与修复建议
docker rmi <镜像>删除镜像；正被容器使用的镜像不能删
docker image prune [-a]清理悬空镜像 / 所有未使用的镜像

本章小结

  • 镜像包含运行应用所需的一切：刚刚够用的 OS、代码、依赖和元数据。一个镜像可以启动多个容器。
  • 镜像由多个只读层堆叠而成，每个镜像都有一个 manifest，列出组成它的层以及堆叠方式。层可以在镜像之间共享。
  • 镜像名（标签）是可变的，latest 不一定最新；摘要是内容的哈希，不可变，可以保证你拉到的就是你想要的那个镜像。
  • Docker Hub 有经过审核的官方镜像，但任何来自互联网的软件都要保持警惕。
  • 多架构镜像通过 manifest list 让同一个标签服务不同的 CPU 架构。
  • Docker Scout 等工具可以扫描镜像中的已知漏洞并给出修复建议。

✎ 动手练习

  1. 拉取 python:3.13-slim 和 python:3.13-alpine，比较它们的大小。再拉取 python:3.13，看看完整版有多大。
  2. 对 nginx:latest 运行 docker history 和 docker inspect，数一数它有几层，找出启动命令（Cmd）是什么。
  3. 运行 docker buildx imagetools inspect nginx，列出 nginx 支持的所有平台。
  4. 给 alpine 打一个新标签：docker tag alpine my-alpine:v1，然后用 docker images 验证两个标签的 IMAGE ID 相同。

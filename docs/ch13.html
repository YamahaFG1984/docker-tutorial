第 13 章

Docker 网络

“永远是网络的锅！”—— 基础设施一出问题，大家总是先怪网络。这是因为网络处在一切的中心。 本章带你理解 Docker 网络的理论基础（CNM、libnetwork、驱动），然后动手玩转单机 bridge 网络、端口映射、接入现有 VLAN、服务发现和 ingress 负载均衡。

本章目标

  • 理解 CNM 的三个构件：沙箱、端点、网络
  • 理解 libnetwork 与驱动的分工（控制平面 vs 数据平面）
  • 掌握 bridge 网络、veth、docker0，以及自定义网络的 DNS 解析
  • 理解端口映射的原理和局限
  • 了解 MACVLAN 如何让容器直接出现在物理网络上
  • 理解 Docker 内置 DNS 的服务发现流程，以及 Swarm 的 ingress 路由网格
ⓘ 建议的实验环境

本章涉及的都是 Linux 容器。建议用 Multipass 或 Play with Docker 跟着做，因为要用到一些 Linux 命令； Docker Desktop 把一切都跑在虚拟机里，你看不到宿主机上的网桥等设备。涉及 Swarm 的部分需要一个 swarm 集群（第 12 章）。

一句话概括

Docker 运行的微服务应用由许多协同工作的容器组成。这些容器之间需要通信，有些还要连接外部服务（物理服务器、虚拟机等）。Docker 对两类需求都有方案。

Docker 网络基于 libnetwork，它是一个开源架构 CNM（Container Network Model，容器网络模型）的参考实现。 Docker 自带了满足最常见需求的一切：单机网络、多主机的容器间网络、接入现有 VLAN 等；这个模型又是可插拔的，生态可以通过驱动扩展。 此外，libnetwork 还提供原生的服务发现和基础的负载均衡。

Docker 网络理论

从最高层看，Docker 网络由三部分组成：

  • CNM 是设计规范，描述 Docker 网络的基本构件；
  • libnetwork 是 CNM 的真实实现，作为 Moby 项目的一部分开源，被 Docker 和其他平台使用；
  • 驱动（driver）通过实现具体的网络拓扑（比如 VXLAN overlay 网络）来扩展这个模型。

CNM：容器网络模型

一切从设计开始。CNM 定义了三个构件（推荐阅读 设计文档）：

沙箱 Sandbox

容器内一个隔离的网络栈：网卡、端口、路由表、DNS 配置……一个完整网络栈该有的都有。

端点 Endpoint

虚拟网卡，看起来和普通网卡一模一样。它把沙箱连接到网络上。

网络 Network

虚拟交换机（通常是 802.1d 网桥的软件实现），把需要通信的端点组织在一起并与其他网络隔离。

  • 容器 A 只有一个端点，只连接网络 A；容器 B 有两个端点，同时连接网络 A 和网络 B。
  • 容器 A 和 B 都在网络 A 上，所以能互相通信；但容器 B 里的两个端点位于不同网络，彼此不能直接通信。
  • 端点就像真实网卡一样只能连接一个网络，所以容器 B 要连两个网络就需要两个端点。
  • 即使两个容器在同一台主机上，它们的网络栈也是完全隔离的，只能通过网络通信。

libnetwork 与驱动

在 libnetwork 出现之前，Docker 把所有网络代码都写在守护进程里，导致守护进程臃肿、其他项目难以复用。 于是 Docker 把网络代码剥离出来，按 CNM 设计重构成了外部库 libnetwork。今天 Docker 的所有核心网络功能都在 libnetwork 里实现。

libnetwork 实现的是控制平面（管理 API、服务发现、基于 ingress 的负载均衡），而数据平面交给驱动：驱动负责创建网络、保证隔离和连通性。 Docker 内置了一些驱动，称为原生驱动或本地驱动：

驱动作用典型场景
bridge单机网络（Linux 网桥）单机开发、Compose 应用（默认）
host容器直接使用宿主机网络栈，不隔离追求极致网络性能
none只有回环接口，完全断网离线批处理、安全隔离
overlay跨多台主机的网络（VXLAN）Swarm 集群（第 14 章）
macvlan / ipvlan让容器直接出现在物理网络 / VLAN 上对接传统网络和遗留系统

每个网络都归某个驱动所有，由这个驱动创建和管理网络的一切。比如你创建一个叫 prod-fe-cuda 的 overlay 网络，Docker 就会调用 overlay 驱动来创建它。 为了满足复杂多变的环境，一台 Docker 主机或一个 Swarm 集群里可以同时有多个由不同驱动管理的网络。

单机 bridge 网络

最简单的 Docker 网络是单机 bridge 网络，名字说明了两件事：

  • 单机：网络只存在于一台 Docker 主机上；
  • bridge：它是 802.1d 网桥（二层交换机）的实现。

Docker 用内置的 bridge 驱动创建单机 bridge 网络（Windows 容器用 nat 驱动，效果基本相同）。 每台 Docker 主机都有一个默认的 bridge 网络，名字就叫 bridge，新容器如果不用 --network 指定，就会连到它上面。 

$ docker network ls
NETWORK ID     NAME     DRIVER    SCOPE
c7464dce29ce   bridge   bridge    local       <<---- 所有 Docker 主机上都有的默认网络
c65ab18d0580   host     host      local
42a783df0fbe   none     null      local

$ docker network inspect bridge
[
    {
        "Name": "bridge",
        "Scope": "local",
        "Driver": "bridge",
        "IPAM": {
            "Config": [ { "Subnet": "172.17.0.0/16", "Gateway": "172.17.0.1" } ]
        },
        <Snip>
    }
]

所有 bridge 网络都基于 Linux 内核中已经存在了 20 多年的 Linux bridge 技术，性能高、非常稳定，而且可以用标准的 Linux 工具查看。 默认的 bridge 网络对应宿主机内核里一个叫 docker0 的网桥： 

$ docker network inspect bridge | grep bridge.name
            "com.docker.network.bridge.name": "docker0",

$ ip link show docker0
3: docker0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc...
    link/ether 02:42:af:f9:eb:4f brd ff:ff:ff:ff:ff:ff

$ ip link show type bridge           # 列出所有网桥（旧工具 brctl show 的现代替代）
3: docker0: <...>

动手：创建自己的 bridge 网络

$ docker network create -d bridge localnet
f918f1bb0602373bf949615d99cb2bbbef14ede935fbb2ff8e83c74f10e4b986

$ ip link show type bridge
3: docker0: <...>
7: br-f918f1bb0602: <...>           <<---- 内核里多了一个新网桥

新网桥的名字 br-f918f1bb0602 里的数字，正是 localnet 网络 ID 的前 12 位。现在创建一个容器连到 localnet 上：

$ docker run -d --name c1 --network localnet alpine sleep 1d

$ docker network inspect localnet --format '{{json .Containers}}' | jq
{
  "09c5f4926c87...": {
    "Name": "c1",
    "EndpointID": "27770ac30577...",
    "MacAddress": "02:42:ac:15:00:02",
    "IPv4Address": "172.21.0.2/16",
    "IPv6Address": ""
  }
}

$ ip link show master br-f918f1bb0602     # 看看哪些接口插在这个网桥上
9: veth833aaf9@if8: <...> master br-f918f1bb0602

每个 veth 就像一根两端各有一个接口的网线：一端在容器里（容器看到的 eth0），另一端插在内核中对应的网桥上。

用名字互相访问：内置 DNS

如果再往 localnet 上加容器，它们都能用名字互相通信，因为 Docker 会自动把容器名注册到内置的 DNS 服务里。 唯一的例外是默认的 bridge 网络，它不支持 DNS 解析 —— 这是推荐总是创建自定义网络的重要原因。 

$ docker run -it --name c2 --network localnet alpine sh
/ # ping c1
PING c1 (172.21.0.2): 56 data bytes
64 bytes from 172.21.0.2: seq=0 ttl=64 time=1.564 ms
64 bytes from 172.21.0.2: seq=1 ttl=64 time=0.338 ms
^C
/ # exit
★ 最佳实践：总是使用自定义网络

自定义 bridge 网络提供按名字解析的 DNS、更好的隔离（不同网络之间默认不通），还能在容器运行时动态连接或断开（docker network connect / disconnect）。 Compose 会自动为每个项目创建自定义网络，这就是第 9 章里 web-fe 能直接用 redis 找到数据库的原因。

通过端口映射实现外部访问

到目前为止，bridge 网络上的容器只能和同一网络上的容器通信。要让外部访问，可以把容器端口映射到 Docker 主机的端口上。 这种方式有点笨拙、限制很多，但对偶尔的测试和开发很有用。 

$ docker run -d --name web --network localnet --publish 5005:80 nginx

$ docker port web
80/tcp -> 0.0.0.0:5005
80/tcp -> [::]:5005

映射存在于 Docker 主机的所有接口上。用浏览器访问主机 IP 的 5005 端口能看到 Welcome to nginx!。再从另一个网络上的容器试试：

$ docker run -it --name client --network bridge alpine sh
/ # apk add curl
/ # curl 192.168.64.69:5005
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
...

虽然能用，但这种方式笨拙且不可扩展：比如主机的 5005 端口被占用后，其他容器和主机进程都不能再用它。 这也是单机 bridge 网络只适合本地开发和很小的应用的原因之一。

✨ 最新变化：更安全的默认网络行为
  • 只绑定到本机：-p 5005:80 默认绑定所有接口（0.0.0.0），意味着局域网甚至公网都能访问。开发时更安全的写法是 -p 127.0.0.1:5005:80。
  • Docker Engine 28 起加强了 bridge 网络的隔离：未发布（没有 -p）的容器端口，不再能被同一局域网里的其他主机通过路由直接访问。
  • Docker Engine 29 实验性地支持用 nftables 代替 iptables 管理防火墙规则。
  • Docker Desktop 较新的版本也支持了 --network host（以前只有 Linux 上才有真正的 host 网络）。

接入现有网络与 VLAN

让容器化应用连接外部系统和物理网络非常重要。常见的场景是部分容器化的应用：跑在容器里的部分需要和没跑在容器里的部分通信。

内置的 MACVLAN 驱动（Windows 上叫 transparent）就是为此设计的。它给每个容器分配外部物理网络上的独立 IP 和 MAC 地址， 让每个容器看起来就像一台物理服务器或虚拟机。

好处是性能好，不需要端口映射和额外的网桥。坏处是宿主机网卡必须运行在混杂模式（promiscuous mode）， 很多企业网络和公有云都不允许。所以 MACVLAN 可能适用于你的数据中心（如果网络团队同意），但在公有云上多半行不通。

假设物理网络上已有 VLAN 100，创建一个连接它的 MACVLAN 网络需要提供：子网、网关、可分配给容器的 IP 范围、使用宿主机的哪个接口或子接口：

$ docker network create -d macvlan \
    --subnet=10.0.0.0/24 \
    --ip-range=10.0.0.0/25 \
    --gateway=10.0.0.1 \
    -o parent=eth0.100 \
    macvlan100

$ docker run -d --name mactainer1 --network macvlan100 alpine sleep 1d
  • -o parent=eth0.100：MACVLAN 驱动会创建标准的 Linux 子接口，并用 VLAN ID 标记（.100 表示 VLAN 100）。请改成你系统上的接口名，比如 enp0s1.100。
  • --ip-range：告诉网络可以给容器分配哪一段地址。必须把这段地址预留给 Docker，因为 MACVLAN 驱动没有检查 IP 是否已被占用的管理功能。

底层的 VLAN 100 看不到任何 MACVLAN 魔法，它只看到带着自己 MAC 和 IP 的容器，所以 mactainer1 能和 VLAN 100 上的所有其他系统通信。 MACVLAN 驱动还支持 VLAN trunk：可以创建多个 MACVLAN 网络分别连接不同的 VLAN。

💡 不能开混杂模式？试试 ipvlan

ipvlan 驱动与 macvlan 类似，但所有容器共享宿主机网卡的 MAC 地址，因此通常不需要混杂模式，在一些限制 MAC 数量的环境里更容易落地。

可以编辑 /etc/docker/daemon.json 调整守护进程日志的详细程度（从详细到简略：debug、info（默认）、warn、error、fatal），改完记得重启 Docker：

{
  "debug": true,
  "log-level": "debug"
}

容器日志

通常用 docker logs 查看容器日志，Swarm 服务用 docker service logs。容器日志的前提是：应用作为 PID 1 运行，把日志写到 STDOUT、把错误写到 STDERR， 然后由日志驱动转发到配置的位置。json-file（默认）、local 和 journald 都支持 docker logs。 

{
  "log-driver": "local",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
⚠ 小心日志撑爆磁盘

默认的 json-file 驱动不限制日志大小，一个话痨容器可能把磁盘写满。生产环境务必像上面那样配置 max-size / max-file，或者使用自带轮转的 local 驱动。启动容器时也可以用 --log-driver 和 --log-opt 覆盖。

服务发现

除了核心网络，libnetwork 还提供服务发现：让所有容器和 Swarm 服务都能通过名字找到彼此，唯一的要求是它们在同一个网络上。 底层原理是 Docker 实现了一个内置的 DNS 服务器，并配置每个容器用它来解析名字。

  1. c1 执行 ping c2，容器的本地 DNS 解析器先查缓存，看有没有 c2 的 IP。每个 Docker 容器都有本地解析器。
  2. 缓存里没有，于是向 Docker 内置 DNS 服务器发起递归查询。所有容器都预先配置好了如何访问它。
  3. Docker DNS 服务器保存着所有用 --name 或 --net-alias 创建的容器的名字到 IP 的映射，所以知道 c2 的 IP。
  4. DNS 服务器把 c2 的 IP 返回给 c1 的本地解析器。如果 c1 和 c2 在不同网络上，就不会返回 —— 名字解析只对同一网络上的容器有效。
  5. c1 向 c2 的 IP 发送 ping 请求。

你还可以用 --dns 指定自定义 DNS 服务器，用 --dns-search 添加搜索域（当应用使用非完全限定的名字时用于补全）。 当应用需要解析 Docker 环境之外的名字（比如互联网服务）时，这两个选项很有用。它们的原理都是往容器的 /etc/resolv.conf 里写入条目： 

$ docker run -it --name custom-dns --dns=8.8.8.8 --dns-search=nigelpoulton.com alpine sh
/ # cat /etc/resolv.conf
# Generated by Docker Engine.
nameserver 8.8.8.8
search nigelpoulton.com

Ingress 负载均衡（Swarm）

这一节只适用于 Docker Swarm。Swarm 有两种把服务发布给外部客户端的方式：

ingress 模式是默认值：只要用 -p 或 --publish 创建服务，就是 ingress 模式。要用 host 模式，必须用 --publish 的长格式并加上 mode=host： 

$ docker service create -d --name svc1 \
    --publish published=5005,target=80,mode=host \
    nginx
  • published=5005：通过 5005 端口向外部客户端提供服务；
  • target=80：到达发布端口的请求会被映射到副本的 80 端口；
  • mode=host：只有请求到达运行着副本的节点时才能访问服务。

短格式（-p 5005:80）无法指定 host 模式。长格式是逗号分隔、逗号后没有空格的列表。绝大多数情况下你都会用 ingress 模式。

ingress 模式在幕后使用一个四层的路由网格（routing mesh）。看看一个外部请求是怎么走的：

  1. 外部客户端把请求发到节点 1 的 5005 端口；
  2. 节点 1 收到请求，知道 5005 端口的流量要交给 ingress 网络；
  3. ingress 网络把请求转发到运行着副本的节点 2；
  4. 节点 2 收到请求，把它交给副本的 80 端口。

Docker 在创建 swarm 时自动创建 ingress 网络并把所有节点接入其中。发布服务时，Docker 还会创建一条集群范围的规则：所有到达任意节点 5005 端口的流量，都经 ingress 网络路由到 svc1 副本的 80 端口。

本章小结

  • CNM 是 Docker 网络的设计规范，定义了沙箱、端点、网络三个构件；libnetwork 是它的开源实现，负责控制平面；驱动负责数据平面。
  • 单机 bridge 网络是最基础的网络类型，对应内核中的 Linux 网桥，容器通过 veth 接入；它不能跨主机，对外发布服务需要端口映射。
  • 自定义网络提供按名字的 DNS 解析，默认的 bridge 网络不提供；名字解析只在同一网络内有效。
  • MACVLAN 让容器拥有物理网络上的 IP 和 MAC，但需要混杂模式，公有云通常不支持。
  • Swarm 服务默认以 ingress 模式发布，通过路由网格让任意节点都能访问服务，并在副本间负载均衡。
  • overlay 网络是跨主机的容器网络，下一章详细讲。

✎ 动手练习

  1. 在默认 bridge 网络上启动两个容器，验证它们不能用名字互相 ping，但能用 IP ping 通；再在自定义网络上重复，验证名字解析可用。
  2. 创建两个自定义网络 net-a 和 net-b，各放一个容器，验证它们互不相通；然后用 docker network connect net-b <容器> 让其中一个容器同时连两个网络，再测试。
  3. 分别用 -p 8080:80 和 -p 127.0.0.1:8081:80 启动两个 NGINX，从局域网里的另一台设备访问这两个端口，观察区别。
  4. 给一个容器加上 --network-alias api，再从同一网络的另一个容器 ping api。
